# AWS 격리환경 구축에 필요한 요소

기준: [격리 환경 보안 설계](./isolation-security.md) §5.1·5.2·5.4·5.5·5.11·5.12·5.14·5.15, §7·8.
작성일: 2026-10-07. 실제 AWS 설정 시 필요한 인프라·실행환경·검증 항목을 추린 문서다. 적용 결과는 [작업 기록](./experiments/2026-10-07-aws-isolation-setup.md)에 남긴다.

**현재 적용 범위는 노트북 전용 SSH 접속과 오프라인 격리 실행환경이다.** Render 연결과 테스트 링크 목록은 보류했고, EC2의 새 외부 연결과 브라우저 외부 네트워크를 차단했다. 아래 표는 테스트 페이지와 Render를 연결할 때까지 포함한 전체 요구사항이다. 실제 의심 링크를 직접 여는 환경은 추가 조건을 갖춘 뒤 전환한다.

현재 배치는 **메인 서버 = Render, 격리 서버 = 기존 `ktc-server` EC2**다. 원문의 메인 서버 EC2·SG 참조·사설 IP 연결 전제를 이 배치에 맞춰 적용한다.

```text
메인 서버(Render) ── HTTPS + 토큰 ──▶ 격리 서버(ktc-server EC2) ──▶ 테스트 페이지 서버
관리자 PC ── SSH ──▶ 격리 서버
```

격리 EC2는 `i-0ddf82de2ba56da70`(서울, `t3.medium`)이며 현재 공인 IP는 `54.180.151.132`다. `ssh ktc-server`는 노트북 전용 키를 사용하는 직접 SSH로 변경했다. 와이파이가 바뀌면 저장소 루트에서 `powershell -NoProfile -File .\infra\isolation\connect.ps1`을 실행한다. 현재 공인 IPv4 `/32`로 기기별 SSH 규칙(`-Device`, 기본값 `notebook`) 하나를 교체하고 접속한다. IAM 역할을 제거하고 IMDS·SSM을 비활성화했다. Render의 수집 API 호출 경로는 추후 별도로 구성한다.

## 1. 구축 전에 정할 값

| 항목 | 필요한 값 |
| --- | --- |
| AWS 배치 | 리전, VPC ID, 격리 EC2를 둘 서브넷 ID, 연결할 라우팅 테이블 |
| 메인 서버 | Render 서비스의 Outbound IP CIDR 목록, 서비스 URL |
| 격리 서버 | 기존 EC2의 AMI·인스턴스 유형·SG, 설치된 SSH 공개키, 수집 API의 공인 주소/도메인·HTTPS 포트 |
| 테스트 페이지 | 허용할 호스트명, 고정 IP, HTTPS 443, 격리 서버에서 나갈 때의 출발지 IP |
| 실행 이미지 | 승인한 레지스트리 digest(`이미지@sha256:…`), 플랫폼, Playwright·Chromium 버전 |
| API 접속 | 공유 토큰, 격리 API 인증서·개인키, 메인 서버가 신뢰할 인증서 |
| 실행 상한 | CPU·메모리·PID·공유 메모리·tmpfs 크기, 작업 시간·응답 크기·동시 실행 수 |

인스턴스 유형과 자원 상한은 브라우저 실측으로 정한다. 원문에 등장하는 `t3.medium`을 확정 사양으로 보지 않는다. API 포트와 요청·응답 상한은 격리 담당자와 BE가 정해야 한다.

## 2. AWS에서 준비할 리소스와 설정

| 요소 | 구분 | 설정 |
| --- | --- | --- |
| 격리 전용 EC2 | 기존 서버 활용 | `ktc-server`에서 Docker와 수집기를 실행한다. 메인 서버는 Render에 있어 추가 격리 EC2를 만들 필요 없다 |
| 전용 보안 그룹(SG) | 필수 | 메인 서버의 HTTPS 요청과 관리자 SSH만 받고, 새 아웃바운드 연결은 테스트 페이지 IP:443만 허용한다 |
| VPC·서브넷·라우팅 | 필수 | Render → 격리는 인터넷을 통한 공인 HTTPS로 연결한다. 테스트 페이지까지의 실제 경로도 확보한다. 서브넷 이름만으로 격리가 되지는 않는다 |
| 전용 NACL·서브넷 분리 | 1단계 권장, 실제 링크 단계에서 VPC 대역 차단 필수 | Render 요청·응답과 관리자 SSH 등 필요한 예외를 허용하고 VPC 내부 접근을 거부한다. VPC에 다른 서버가 있다면 서브넷도 분리한다 |
| 인터넷 경로 | 필수 | Render가 접속할 수 있도록 격리 EC2 공인 IPv4와 IGW 경로를 확인한다. NAT만으로는 외부의 수집 API 호출을 받을 수 없다 |
| SSH 키 페어·관리 경로 | 필수 | 관리자 고정 IP 또는 기존 관리 서버에서 TCP 22로 키 인증. 전 세계 SSH 개방은 금지한다 |
| IAM 인스턴스 프로파일 | 미부착 적용 | 직접 SSH를 검증한 뒤 기존 SSM용 역할을 제거했다. 수집 실행 시 AWS 권한·액세스 키를 두지 않는 것이 원문 기준이다 |
| IMDS | 비활성화 적용 | `HttpEndpoint=disabled` 적용. 재부팅 시 초기화가 다시 실행되지 않도록 cloud-init도 비활성화했다. 새 EC2는 초기 부팅과 SSH 키 설치를 마친 뒤 적용한다 |
| 테스트 페이지 서버 | 필수 | 고정 IP와 HTTPS를 제공하고 격리 서버의 실제 출발지 IP만 허용한다. 기존 호스팅이 이를 지원하면 새 EC2는 필요 없다 |
| 이미지 공급 경로 | 필수 | 승인 이미지를 초기화 때 준비한다. 운영 중 레지스트리에 자유롭게 접속할 필요가 없도록 한다 |
| VPC Flow Logs·CloudWatch | 권장 | 격리 ENI/서브넷의 거부 트래픽과 경보를 AWS 측에서 관찰한다. 격리 EC2에 로그 전송용 AWS 키를 넣지 않는다 |

IGW를 통한 IPv4 인터넷 접속에는 라우팅과 공인 IPv4가 모두 필요하다. 테스트 서버의 IP 허용 규칙에는 격리 EC2의 공인 IP 또는 NAT의 출발지 IP를 넣는다. 주소를 계속 고정해야 할 때 EIP를 사용한다. [AWS 인터넷 게이트웨이 안내](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html).

Render 대시보드의 해당 서비스 → **Connect → Outbound**에서 CIDR 목록을 확인한다. 일반 Outbound 범위는 같은 리전의 다른 Render 서비스와 공유되므로, IP 허용만으로 우리 메인 서버를 인증할 수 없다. HTTPS와 공유 토큰 검증을 함께 적용한다. [Render Outbound IP 안내](https://render.com/docs/outbound-ip-addresses).

## 3. 보안 그룹 규칙

`API_PORT`는 합의한 HTTPS 포트, `TEST_IP`는 테스트 페이지의 고정 IP다.

| 대상 SG | 방향 | 허용 규칙 |
| --- | --- | --- |
| 격리 SG | 인바운드 | TCP `API_PORT`, 출발지 = 해당 Render 서비스의 Outbound CIDR 목록 |
| 격리 SG | 인바운드 | TCP 22, 출발지 = 관리자 공인 IP `/32` 또는 기존 관리 서버 SG |
| 격리 SG | 아웃바운드 | TCP 443, 목적지 = `TEST_IP/32` |
| 테스트 서버 SG/접근 정책 | 인바운드 | TCP 443, 출발지 = 격리 서버의 실제 출발지 IP `/32` |

- 격리 SG의 기본 전체 아웃바운드 허용을 제거한다. EC2에 붙은 **모든 SG**를 확인한다. 다른 SG에 전체 허용이 남으면 제한이 풀린다.
- SG는 연결 상태를 기억하므로 메인이 시작한 API 연결과 관리자 SSH의 응답을 위해 별도 전체 아웃바운드를 열지 않는다.
- Render 메인 서버에는 AWS SG를 지정하지 않는다. EC2 공인 주소/도메인으로 HTTPS를 호출한다.
- IPv6를 사용하지 않는 구성으로 맞추고, IPv6 전체 허용 규칙도 남기지 않는다.

SG는 허용 규칙만 지원하며, 여러 SG의 허용 규칙은 합쳐진다. IMDS와 Amazon DNS 트래픽도 SG로 차단할 수 없다. [AWS 보안 그룹 규칙](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html).

**NACL을 적용한다면:** 인바운드 API·SSH 포트뿐 아니라 아웃바운드 응답의 클라이언트 임시 포트도 허용한다. 테스트 서버로 보내는 443과 돌아오는 격리 서버 임시 포트도 필요하다. 실제 OS의 임시 포트 범위와 상대 IP로 좁히고, 예외 규칙 번호를 VPC 대역 거부보다 앞에 둔다. NACL은 상태를 기억하지 않고 같은 서브넷 안의 통신은 필터링하지 않는다. [AWS NACL 안내](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html).

## 4. EC2 내부에서 필요한 설정

AWS 리소스 설정과 함께 적용해야 하는 실행환경 항목이다.

| 요소 | 필요한 설정 |
| --- | --- |
| 호스트 방화벽 | 컨테이너 전달 트래픽, 호스트로 들어오는 트래픽, 호스트가 내보내는 트래픽을 각각 제어한다 |
| 컨테이너 외부 접속 | 테스트 페이지 IP:443만 허용. Render 메인 서비스, 격리 서버 공인 IP, 내부망, 호스트 게이트웨이·관리 서비스로 새 연결 금지 |
| DNS | 테스트 호스트를 `--add-host` 등으로 고정하고 컨테이너의 TCP·UDP 53을 막는다. Docker 내장 DNS를 통한 우회도 검증한다 |
| 메타데이터 | IMDS를 끄고 호스트·컨테이너에서 차단을 확인한다. 컨테이너의 링크로컬 접근도 방화벽으로 차단한다 |
| 호스트 관리 통신 | OS 유지에 필요한 통신은 호스트에만 좁게 허용한다. 이미지·패키지 갱신은 수집을 중지한 관리 시간에 하고 다시 제한한다 |
| 컨테이너 권한 | non-root UID, Chromium용 seccomp, `--cap-drop=ALL`, `--security-opt no-new-privileges` |
| 파일시스템 | `--read-only`, 쓰기는 크기를 제한한 tmpfs. Docker 소켓·호스트 경로·외부 데이터 볼륨 마운트 금지 |
| 호스트 공유 금지 | `--privileged`, `--network=host`, `--ipc=host` 금지. 공유 메모리는 `--shm-size`로 확보 |
| 자원 제한 | `--memory`, `--cpus`, `--pids-limit`, `--shm-size`, tmpfs 크기 설정. 동시 브라우저는 원문 기준 최대 2페이지 |
| 브라우저 | `chromium_sandbox=True`, `--no-sandbox` 금지. `accept_downloads=False`, `service_workers="block"` |
| 비밀값 | LLM·urlscan·카카오·VirusTotal 키와 AWS 자격증명 없음. 수집 API 토큰과 TLS 개인키만 필요한 서비스에 두고 브라우저 환경변수에서 제외 |
| 이미지·초기화 | 승인 digest와 플랫폼 고정. 요청마다 새 브라우저 컨텍스트, 정한 주기에 브라우저 재시작·컨테이너 재생성 |

Docker의 iptables 방식에서는 `DOCKER-USER`가 전달 트래픽을 제어한다. 호스트의 `INPUT`·`OUTPUT`은 별도로 설정해야 하며, nftables 방식이면 해당 방식의 규칙을 작성한다. [Docker 방화벽 안내](https://docs.docker.com/engine/network/firewall-iptables/).

브라우저와 수집 API가 같은 컨테이너에 있으면 루프백 호출은 호스트 방화벽을 지나지 않는다. **로컬 호출도 토큰 없이는 거부**해야 한다. Chromium 샌드박스와 seccomp는 선택한 AMI·Docker 환경에서 함께 동작하는지 확인한다. [Playwright Docker 안내](https://playwright.dev/python/docs/docker).

## 5. 메인 서버와 연결할 때 필요한 설정

| 요소 | 필요한 설정 |
| --- | --- |
| HTTPS | 격리 API에 TLS 적용. 자체 서명 인증서를 쓰면 메인 서버에 그 인증서를 신뢰 대상으로 고정하고 호스트명/IP도 검증한다. 인증서 검증을 끄지 않는다 |
| 요청 인증 | 메인 → 격리 공유 토큰 확인. 누락·불일치는 거부. 토큰은 저장소·이미지·user data에 넣지 않는다 |
| 대상 제한 | 수집 요청과 리다이렉트·하위 자원이 테스트 허용 목록 안인지 검사한다. 목록 밖 주소로 요청을 보내기 전에 차단한다 |
| 작업 한도 | 원문 기준 httpx 3초, 브라우저 6초, 리다이렉트 5홉. 응답 크기·대기열·전체 마감도 설정하고 초과 작업은 종료한다 |
| 응답 검증 | 메인이 수신 중 바이트 상한을 적용하고 UTF-8·필드·타입·길이를 검증한다. 수집 실패를 안전으로 처리하지 않는다 |
| Render 설정 | 격리 API의 공인 HTTPS 주소, 신뢰할 인증서, 공유 토큰을 메인 서비스에 설정한다. 원문의 메인 EC2 IMDS 설정은 Render에는 적용하지 않는다 |

IMDS 비활성화 시 메타데이터에 의존하는 프로그램은 작동하지 않는다. 이 구성의 격리 서버는 Session Manager나 EC2 Instance Connect에 기대지 않고 설치한 SSH 공개키로 관리한다. 공개키 주입이 IMDS를 사용하는 AMI라면 첫 부팅을 완료한 뒤 꺼야 한다. [AWS IMDS 설정](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html), [AMI 공개키 설치](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/building-shared-amis.html).

현재 SG는 노트북이 사용하는 공인 IP `/32`의 TCP 22만 받으며 아웃바운드 허용 규칙은 없다. 호스트 방화벽도 새 외부 연결·전달·DNS를 차단한다. SSH 응답과 루프백, 호스트의 DHCP·Amazon Time Sync는 유지한다. SSH 인증은 `isolation-admin` 계정의 노트북 전용 공개키 하나로 제한했다. 같은 와이파이의 다른 기기는 같은 공인 IP를 공유할 수 있으므로 IP 규칙과 키 인증을 함께 적용한다.

## 6. 설치 순서와 운영 준비

1. 위 표의 주소·포트·AMI·이미지·상한을 정하고 테스트 페이지를 준비한다.
2. 로컬 Session Manager 플러그인을 설치하고 `ssh ktc-server` 접속을 확인한다. 기존 EC2를 활용한다.
3. 관리자 IP `/32`에서 격리 EC2로 직접 SSH 접속하는 경로를 확보하고 새 세션에서 확인한다. Docker·승인 이미지·방화벽 설정을 준비한다. 아직 수집은 시작하지 않는다.
4. 토큰과 인증서를 안전하게 설치한다. 서버 관리 정책상 변경이 가능하면 SSM용 역할을 제거하고 IMDS를 끈다. 임시 네트워크 허용을 제거하고 브라우저·컨테이너 제한을 적용한다. SSM 권한·외부 통신을 유지해야 한다면 원문 기준과의 차이를 기록하고 수집 시작 전에 팀이 정한다.
5. Render Outbound CIDR의 HTTPS 접근을 허용하고 메인 서비스의 인증서·토큰·응답 검증 설정을 연결한다. 아래 검증을 수행한다.
6. 생성·설치·재생성 절차를 스크립트로 남기고 EC2 교체를 한 번 연습한다. AMI·SG·방화벽·이미지 digest·플랫폼·검증 결과를 기록한다.

필수 관찰 값은 방화벽 차단 패킷 수, 토큰 거부 횟수, 메인 서버 응답 검증 실패, 컨테이너 재시작·OOM 종료다. 외부 로그 전송이 막힌 구성에서는 관리자 측 조회와 메인 서버 기록을 사용한다. 로그에는 문자 원문·URL 쿼리·토큰을 남기지 않는다.

침해가 의심되면 수집을 끄고 격리 EC2를 폐기·재생성하며 토큰과 인증서를 교체한다. 컨테이너 재시작만으로 초기화하지 않는다. VPC Flow Logs는 추가 관찰 수단이며, 컨테이너 내부·IMDS·Amazon DNS 차단 검증을 대신하지 않는다. [원문 복구 절차](./isolation-security.md#512-뚫린-것을-알아채고-되돌리기).

## 7. 실제 AWS에서 확인할 완료 조건

아래는 실행해야 할 확인 목록이다. 결과는 [실험 기록 디렉터리](./experiments/)에 남긴다.

- [ ] 메인 서버의 고정 인증서·정상 토큰을 사용한 HTTPS 수집 요청이 성공한다.
- [ ] 허용한 Render CIDR 밖의 수집 API 접근과 평문 HTTP는 연결 실패한다. 공유 CIDR 안의 요청도 잘못된 토큰이면 거부한다. 잘못된 인증서는 메인이 거부한다.
- [ ] 토큰 없는 요청은 로컬 루프백 호출을 포함해 거부한다.
- [ ] 호스트·컨테이너 모두 `169.254.169.254` 메타데이터에 접속하지 못한다.
- [ ] 테스트 페이지 IP:443만 성공하고, 목록 밖 사이트·DNS·IPv6 우회는 실패한다.
- [ ] 브라우저에서 Render 메인 서비스, 격리 공인 IP, VPC 내부망, 호스트 게이트웨이·관리 서비스로 새 연결이 실패한다.
- [ ] 목록 밖 리다이렉트·하위 자원을 보내기 전에 차단하고 방화벽 차단 신호를 확인한다.
- [ ] non-root·샌드박스·seccomp·권한 제거·읽기 전용·마운트·자원 제한을 실제 실행 상태에서 확인한다.
- [ ] 크롬 프로세스 환경에 토큰·API 키·AWS 자격증명이 없다.
- [ ] 크기·시간·동시 실행 초과는 제한에서 중단되고, 다음 요청이 정상 처리된다.
- [ ] 브라우저 다운로드는 기록만 남기고 파일을 저장하지 않는다.
- [ ] 승인 digest·플랫폼과 실행 이미지를 비교하고, 새 컨텍스트에 이전 쿠키가 남지 않는다.
- [ ] 스크립트로 EC2를 교체하고 토큰·인증서를 갱신한 뒤 같은 검증을 통과한다.

전체 보안 확인 항목은 [원문 §8](./isolation-security.md#8-보안-확인-목록)을 따른다.

## 8. 실제 의심 링크를 열 때 추가할 조건

| 항목 | 전환 조건 |
| --- | --- |
| 인터넷 목적지 정책 | 고정 IP 허용 목록을 바꾸기 전에 사설·예약·링크로컬 대역과 메인·격리 공인 IP 차단, IPv6 차단을 적용한다 |
| 서브넷 경계 | 별도 서브넷·NACL의 VPC 대역 거부와 필요한 요청·응답 예외를 검증한다 |
| DNS·브라우저 경로 | DNS 리바인딩, WebSocket, 리다이렉트, 하위 자원을 실제 인터넷 연결 상태에서 다시 검증한다 |
| 추가 격리·탐지 | gVisor는 샌드박스 호환성·성능을, IPS는 검사 경로·HTTPS 가시성·오탐·장애 정책을 검토한다. 둘 다 1단계 필수 리소스가 아니다 |
| 방문 정책 | 링크 방문이 공격자에게 사용자 반응 신호를 주는 문제를 팀이 결정한다 |

새 VPC, NAT Gateway, ALB, ECR, S3, GuardDuty, IPS를 일괄 추가할 필요는 없다. 현재 경로와 승인 이미지 공급 방식으로 요구사항을 충족하는지 먼저 확인한다. APK 상세 분석·조사 에이전트·카카오/urlscan 기능 수정은 이 구축 요소 정리의 범위 밖이다.
