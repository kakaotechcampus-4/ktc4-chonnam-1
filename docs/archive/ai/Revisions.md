# 문서 설명

이 문서는 BE와의 통신에 사용할 스키마에 대한 정의를 메인으로 담고 있다. 현재 문서의 내용과 일치하지 않는 문서와 코드들에 대해 수정하기 위해 작성되었다.

## 스키마

### BE -> AI : urlscan(임시) API 결과 반환
스미싱 메시지에 포함된 링크만을 분석한 결과이다.

현재는 외부 API인 `urlscan을 이용한 결과값을 도출하고, 추후 고유 시스템 개발을 통해 urlscan API의 반환값 중 AI 파트로 넘기는 요소들과 동일한 요소 추출을 목표로 한다.

```json
{
    final_url : "https://xxxx.xxx.xxx/xxx/xxxx",
    domain : "https://xxxx.xxx.xxx",
    official : true/false
}
```

- `final_url` : 최종 목적지 url
- `domain` : 도메인 주소
- `official` : BE가 urlscan의 악성 위험도 점수(`score`)를 임계값과 비교하여 2차 가공한 boolean. `true`이면 이 워크플로우의 안전 분기로, `false`이면 메시지·격리 환경 결과를 종합하는 분기로 진행한다. 필드명은 유지하지만, 화이트리스트 대조에 따른 공식 도메인 확인을 뜻하지는 않는다.

#### BE의 score 2차 가공

- urlscan의 `score`는 `-100`부터 `+100`까지의 악성 위험도 값이다.
- BE는 임계값 `T`를 정하여 `score <= T`이면 `true`, `score > T`이면 `false`로 가공해 `official` 필드로 AI에 전달한다. 임계값과 같은 점수는 `true`에 포함한다. 구체적인 임계값은 BE 측에서 결정한다.
- 점수 조회와 임계값 비교는 BE의 책임이다. AI는 원본 `score`나 임계값을 입력받지 않고, `final_url`, `domain`, `official`을 입력받는다.
- 사용할 score 필드의 정확한 경로와 점수 누락·조회 실패·범위 초과 시 처리 규칙은 BE 연동 계약에서 확정해야 한다.

**점수 방향과 워크플로우:** [urlscan Result API 문서](https://urlscan.io/docs/result/)는 `verdicts.urlscan.score`의 `-100`을 정상, `+100`을 악성으로 설명한다. 낮은 점수가 `official=true`에 대응하며, AI는 `true`이면 메시지·격리 환경 분석 결과를 기다리지 않고 `result=true`를 반환한다. `false`이면 세 분석 결과를 종합한다. 아래 urlscan 워크플로우의 '공식 도메인' 표현은 이 점수 기반 분기 조건을 가리킨다.

### AI -> BE : 최종 분석 결과 반환
다음 3개의 요소를 종합적으로 분석한 결과이다.
- BE -> AI의 메시지 링크 분석(현재는 urlscan 분석 사용 중)
- 메시지 내용 분석(BE 측에서 원본 메시지 중 url만을 제거한 내용)
- 격리 환경 분석 결과(격리 환경 측에서 구조화 후 반환 예정)

격리 환경 분석 결과 스키마는 다음과 같다.
```json
{
    brand : "xx택배",
    category : "택배",
    info : "택배 배송 조회, etc...",
}
```

- `brand` : 사이트 관련 회사 (ex. 한진 택배, 로젠 택배, KB국민은행 등등)
- `category` : 사이트 관련
- `info` : 실제 페이지 속 요소 전문(`html` 형태)

최종 스키마는 다음과 같다.

```json
{
    url : {
        final_url : "",
        domain : "",
        official : false
    },
    message : {
        brand : "",
        category : "",
        answer : true,
        details : {
            doubt : "",
            reason : ""
        }
    },
    env : {
        brand : "",
        category : "",
        answer : true,
        details : {
            doubt : "",
            reason : ""
        }
    },
    result : false
}
```

`url` : 링크 분석 결과
- `final_url` : 최종 목적지 url (ex. https://xxx.xxx.xxx/xxx/xxx)
- `domain` : 도메인 (ex. https://xxx.xxx.xxx/)
- `official` : BE가 전달한 점수 기준 통과 여부(`true/false`). 입력값을 그대로 유지한다.

`message` : 메시지 내용 분석 결과
- `brand` : 메시지 내용 관련 회사 (ex. 한진택배, 로젠택배, KB국민은행 등등)
- `category` : 메시지 내용 관련 종류 (ex. 택배, 은행, 배달 등등)
- `answer` : 해당 분석 범위의 결과(`true` - 안전 / `false` - 의심 근거가 있거나 분석 실패로 확인하지 못하여 의심 처리 / `null` - 조기 반환으로 분석 결과 미제공)
- `details` : 신뢰도 관련 내용
- `doubt` : 문자에 명시된 링크 접속 목적·요구 (ex. 배송 조회, 주소 확인, 앱 설치). `MessageDoubt` 목록에서 선택한다.
- `reason` : 해당 해석을 뒷받침하는 실제 문자 표현. 페이지에서만 확인한 요소를 문자에서 요구했다고 설명하지 않는다.

`env` : 격리 환경 분석 결과
- `brand` : 실제 페이지 속 관련 회사 (ex. 한진택배, 로젠택배, KB국민은행 등등)
- `category` : 실제 페이지 속 관련 종류 (ex. 택배, 은행, 배달 등등)
- `answer` : 해당 분석 범위의 결과(`true` - 안전 / `false` - 의심 근거가 있거나 분석 실패로 확인하지 못하여 의심 처리 / `null` - 조기 반환으로 분석 결과 미제공)
- `details` : 신뢰도 관련 내용
- `doubt` : 전달된 페이지 자료에서 확인한 요소·요구 내용 (ex. 앱 다운로드 링크, 로그인·인증 입력폼, 결제 요청 요소). `EnvDoubt` 목록에서 선택한다.
- `reason` : 해당 해석을 뒷받침하는 HTML 요소나 별도로 전달된 관측 사실. HTML에 폼이 정의된 사실과 실제 화면 노출·제출·다운로드가 수행된 사실을 구분한다.

`result` : 최종 판단 결과(`true` - 이 서비스의 기준상 안전 / `false` - 의심). `false`는 악성 또는 스미싱이 확정되었다는 뜻이 아니다.

### 최종 결과 결정 규칙

유효한 boolean `url.official`을 입력받은 경우, 최종 `result`는 항상 `url.official`과 같다. LLM, RAG 유사도, 메시지·격리 환경 분석 결과가 이 값을 뒤집지 않는다.

| url.official | message / env | result | 처리 |
|---|---|---|---|
| `true` | 분석 결과를 사용하지 않음 | `true` | 내부 구조를 유지하고 말단 값을 모두 `null`로 조기 반환 |
| `false` | 둘 다 안전으로 분석됨 | `false` | 의심 유지, 각 분석 결과와 근거 제공 |
| `false` | 하나 이상에서 의심 근거가 확인됨 | `false` | 의심 유지, 확인된 근거 제공 |
| `false` | 분석 실패 또는 타임아웃 | `false` | 의심 유지, 확보한 결과만 사용하며 실패를 악성 근거로 만들지 않음 |

메시지·격리 환경 분석의 역할은 의심 사유와 관측 근거를 구체화하는 것이다. 두 분석에서 추가 의심 근거가 발견되지 않아도 URL 점수 기준 미통과 사실을 무효화하지 않는다. 각 `answer`는 해당 분석 범위의 결과이며 최종 `result`와 다를 수 있다. 분석 실패 시에는 아래 '분석 실패와 타임아웃 처리' 규칙을 적용한다.

사용자에게는 `result=false`를 '의심'으로 안내하고, 이를 '악성 확정'이나 '스미싱 확정'으로 바꾸어 표현하지 않는다. 현재 점수 기반 `official=false`만으로 실제 공식 도메인이 아니라는 사실까지 확인했다고 설명하지 않는다.

### 조기 반환 시 null 처리

`official=true`로 조기 반환할 때는 `message`, `env` 및 각각의 `details` 객체와 모든 키를 유지한다. 두 분석 객체의 `brand`, `category`, `answer`, `details.doubt`, `details.reason` 값은 모두 `null`로 반환한다. JSON에 없는 `undefined`를 사용하거나 키를 생략하지 않으며, `message`나 `env` 객체 전체를 `null`로 바꾸지 않는다. 분석이 이미 일부 진행되었더라도 조기 반환 응답에는 해당 값을 포함하지 않는다.

다음은 조기 반환 응답의 예시다. `url`은 BE가 전달한 링크 분석 결과를 유지하고, `result`는 `true`다.

```json
{
    "url": {
        "final_url": "https://example.com/track",
        "domain": "example.com",
        "official": true
    },
    "message": {
        "brand": null,
        "category": null,
        "answer": null,
        "details": {
            "doubt": null,
            "reason": null
        }
    },
    "env": {
        "brand": null,
        "category": null,
        "answer": null,
        "details": {
            "doubt": null,
            "reason": null
        }
    },
    "result": true
}
```

이때 `null`은 조기 반환으로 해당 분석 결과를 제공하지 않는다는 뜻이다. 분석을 수행했지만 브랜드나 분류 등을 식별하지 못했을 때의 `unknown`과 구분한다. 분석 실패·타임아웃은 아래 규칙에 따라 `answer=false`로 처리한다.

### 분석 실패와 타임아웃 처리

`official=false`인 분석 경로에서 메시지 분석 실패, 페이지 접속 실패, 수집 실패, 분석 타임아웃 등이 발생하면 해당 분석의 `answer=false`로 처리한다. 안전을 확인하지 못한 경우도 의심으로 취급하는 정책이다. 최종 `result=false`는 유지한다.

- `answer=null`은 `official=true`인 조기 반환에만 사용한다. 분석을 시도했지만 실패한 경우와 구분한다.
- `details.reason`에는 실제로 확인한 실패 사실과 의심 처리 이유를 기록한다. 예: '페이지 접속에 실패하여 내용을 확인하지 못했으므로 의심으로 처리했습니다.'
- 확인한 `brand`, `category`, `doubt` 값과 근거는 유지한다. 확인하지 못한 정형 값은 `unknown`으로 표현하며, 실패를 근거로 브랜드나 위험 행동을 추측하지 않는다.
- 실패만으로 '악성 확정', '스미싱 확정', '분석 회피 확인'이라고 설명하지 않는다. 분석 회피 여부는 별도 관측 근거가 있을 때만 언급한다.
- 한 분석이 실패해도 다른 분석에서 확보한 결과는 보존한다. 실패 사유 설명은 LLM이 실패해도 결정적 템플릿으로 반환할 수 있어야 한다.
- `official=true`가 확인되어 조기 반환하는 경우에는 이미 발생한 개별 분석 실패보다 조기 반환 규칙이 우선하며, 두 분석의 말단 값을 모두 `null`로 반환한다.

다음은 페이지 분석에 실패했고 확인한 추가 정보도 없는 경우의 `env` 예시다.

```json
{
    "brand": "unknown",
    "category": "unknown",
    "answer": false,
    "details": {
        "doubt": "unknown",
        "reason": "페이지 접속에 실패하여 내용을 확인하지 못했으므로 의심으로 처리했습니다."
    }
}
```

## 워크플로우

BE 측에서 원본 메시지를 전달받았을 때, BE는 이를 2가지로 분리한다.

1. 메시지 속 url : url 분석 단계에서 사용. 현재는 urlscan API로 분석 구현.
2. url을 제외한 메시지 내용 : 메시지의 텍스트 내용만 RAG로 스미싱 문자와 유사한지 구분함

분리 이후에는 3개의 단계를 동시 진행한다.

- url 분석 : 현재 `urlscan` API로 임시 구현
- 메시지 내용 분석 : `RAG`를 활용하여 기존 스미싱 문자 유형과 유사한지 분석.
- 격리 환경 분석 : 분리된 url을 입력받은 후, 격리 환경에서 실제 페이지에 접속한 후, 페이지 요소 분석.

이 과정에서 전달되는 요소의 위치는 다음과 같다.

- url : url 분석, 격리 환경 분석
- 메시지 내용(원본 메시지 X) : 메시지 내용 분석

3개의 단계를 동시에 진행하되, 실제 핵심 흐름을 주도하는 것은 url 분석이다.

url 분석 결과가 BE의 점수 기준을 통과하면(`official=true`), 이 서비스의 정책에 따라 안전 분기로 처리하고 메시지 내용 분석과 격리 환경 분석 결과를 기다리지 않는다.
그렇기에 `official=true`이면 메시지 내용 분석과 격리 환경 분석을 중단하고, 위 '조기 반환 시 null 처리' 규칙에 따라 `message`, `env`의 내부 객체와 키를 유지하면서 모든 말단 값을 `null`로 처리한 후, `result=true`인 결과값을 즉시 도출한다.
값들을 `null`로 처리하는 목적은 동일한 스키마 형태를 유지하면서 분석 결과를 제공하지 않음을 표현하는 것이다.

URL 점수 기준을 통과하지 못하면(`official=false`) 메시지 내용 분석 결과와 격리 환경 분석 결과를 호출한다. 이후, url 분석 결과를 포함한 3개의 분석 결과를 메인 서버의 AI에게 넘겨서 최종 스키마 형태로 결과값을 도출한다. `result=false`는 유지하며, 나머지 분석은 추가 근거와 설명을 제공한다. 두 분석이 모두 안전으로 나오더라도 최종 결과를 `true`로 바꾸지 않는다.


최종 스키마 형태로 결과값이 도출되면 AI 측에서 BE로 결과값을 반환하고, BE 측에서 실제 메시지에 가까운 형태로 가공한 후, FE에게 전달한다.


만약 url 분석 단계를 `urlscan`이 아닌, 직접 개발한 고유 시스템으로 대체하게 된다면 워크플로우가 일부 수정될 예정이다. 일단 처음 시작 시 동시 진행하는 단계가 2개로 줄어든다.

- 메시지 내용 분석
- 격리 환경 분석

격리 환경 분석 과정에서 최종 목적지에 도달한 순간, `final_url`과 `domain`을 도출해서 즉시 BE로 전달한다. BE 측에서는 전달받은 두 요소를 기반으로 링크 구조 분석을 수행하여 공식 도메인 여부를 판단한다.

공식 도메인 여부가 `true/false`로 결정되면 `urlscan`에서의 공식 도메인 여부에 따른 두 가지 케이스의 워크플로우가 동일하게 수행된다.

## 고려사항

1. 격리 환경에서 페이지 요소(`html`)를 분석용 AI에게 전달하고, AI가 그것을 분석하는 과정에서 격리 환경이 뚫릴 가능성은 없는 것인가?
2. 최종 AI -> BE 스키마에는 실제 값 또는 `boolean` 형태의 값 말고도 `brand`, `category`, `doubt` 등 기존 케이스로부터 얻을 수 있는 정형화 된 값 중 하나를 가지게 하는 요소가 존재한다. 이 요소들로는 어떤 것을 넣을 것인가? 기존 케이스들을 분석해서 값들을 도출해보자.(판단 불가에 해당하는 `unknown` 반드시 필요)
3. BE -> AI, AI -> BE 등으로 전달되는 스키마는 `JSON` 형태를 가지는데, 이것들을 코드로 구현 시 타입 객체로 구현했는가?

## 정형값 설계안 — 사례 본문 기반 검토안

이 절은 2026-09-23 브레인스토밍에서 도출한 설계안이다. 문자·페이지의 `doubt` 정의, 허용 목록과 대표값 선택 규칙을 분리하는 방향을 합의하여 반영했다. 브랜드·분야 후보는 검토안이며, 페이지 요소 목록은 실제 HTML 사례로 검증할 설계 후보임을 구분한다. 코드와 기존 사례 파일에는 아직 적용하지 않았다.

### 확인한 자료와 설계 방향

- `ai/src/ai/kb/case_examples/CE-*.md` 297개 중 `curated` 사례는 296개이며 본문 변종은 360개다. `CE-0001`은 미검토 초안으로 제외했다.
- 296개 모두 `categories: []`, `claimed_brand: ""`다. 아래 목록은 저장된 정답 라벨이 아니라 사례 본문을 읽고 도출한 후보다. 사례 수집 상태가 `curated`라는 사실을 브랜드·분류 라벨의 검증 완료로 해석하지 않는다.
- 현재 자료는 메시지 본문이며 실제 HTML 관측 자료가 아니다. 문자용 `MessageDoubt` 목록과 페이지용 `EnvDoubt` 목록의 근거 자료와 검증을 분리한다.
- 추천안은 문서 예시처럼 JSON 값에 한글 표준명과 `unknown`을 사용하는 닫힌 목록이다. 타입은 Enum으로 제한하되 `null`은 조기 반환용으로 별도 허용한다. 자유 문자열은 표현 편차가 크고, 영어 코드와 한글 표시명을 별도로 두는 방식은 BE·FE 매핑이 추가로 필요하므로 이번 초안에서는 채택하지 않는다.
- `brand`는 본문이나 페이지가 주장하는 회사·기관·서비스, `category`는 내용의 분야다. `message.details.doubt`는 문자의 접속 목적·요구, `env.details.doubt`는 페이지에서 확인한 요소·요구 내용을 나타낸다. JSON의 외부 구조는 유지하지만 두 `doubt`의 Enum과 검증 규칙은 분리한다. 어느 라벨도 그 자체만으로 진위나 위험을 확정하지 않는다.

| 표준 값 | 필요한 근거 | 확대 해석하지 않을 내용 |
|---|---|---|
| `앱 다운로드 링크` | 앱 다운로드를 안내하는 문구와 연결된 링크 | 실제 다운로드·설치·실행 여부 |

메시지에서 앱 설치를 요구했더라도 페이지 자료에 다운로드 링크가 없으면 `env.details.doubt=앱 다운로드 링크`로 채우지 않는다. HTML의 '배송 조회' 문구만으로 작동하는 조회 기능이 있다고 주장하지 않으며, 실제로 확인한 입력란·상태 표시 등으로 설명을 제한한다. HTML에 존재하지만 화면 표시 여부를 확인하지 못한 요소는 'HTML에서 확인됨'으로 표현한다.

### 출처별 대표값 선택

두 필드 모두 단일 문자열을 유지하되, 내부 후보와 근거는 각각 여러 개 보존한다. 공통 위험도 순서나 두 목록을 합친 전역 우선순위는 사용하지 않는다.

문자는 구체적으로 명시한 요구를 우선한다. 같은 요구에 대한 '주소를 수정하세요'와 '확인하세요'는 `주소 입력·수정`으로 표현하며, 더 일반적인 `주소 확인`, `상세 내용 확인`, `링크 접속`으로 중복 대표 표시하지 않는다. '본인 확인을 위해 번호 입력'은 실제 요구가 더 구체적인 `정보 입력`이다. 서로 독립적이고 구체적인 요구가 여러 개 남으면 원문에서 먼저 등장한 요구를 대표로 두고 나머지는 `message.details.reason`에 함께 남긴다. CE-0114는 앱 다운로드 요구가 주소 확인보다 먼저 명시되어 대표 `message.details.doubt=앱 설치`이며 주소 확인도 설명에 포함한다.

페이지는 추상적인 제목보다 확인한 구체적 요소를 우선한다. '본인 확인'이라는 제목 아래 계정·비밀번호 입력폼이 있으면 `로그인·인증 입력폼`이다. 주소 입력란은 일반적인 `개인정보 입력폼`보다 구체적인 `주소 입력폼`으로 표현한다. 서로 독립적인 요소가 여러 개 남으면 전달된 HTML의 소스 순서상 먼저 나온 요소를 대표로 두고 나머지는 `env.details.reason`에 함께 남긴다. 소스 순서를 실제 화면의 배치·노출 순서라고 설명하지 않는다.

이 선택은 대표 표시 규칙이며 `answer`나 최종 `result`를 결정하는 위험도 순위가 아니다. 개별 `answer` 판정에는 대표값 외에 확보한 다른 근거도 보존하여 사용한다. 유효한 후보가 있으면 `없음`을 선택하지 않는다. 분석 실패 시 확보한 후보가 없으면 `unknown`이며, `없음`으로 실패를 숨기지 않는다.

### 문자 목적과 페이지 요소가 다른 경우

두 필드의 값이 서로 달라도 유지한다. 아래는 차이를 설명하기 위한 가상 입력의 `details` 부분 예시이며, 실제 수집 HTML 사례가 아니다.

```json
{
    "message": {
        "details": {
            "doubt": "배송 조회",
            "reason": "문자에서 '배송 현황을 확인하세요'라고 안내했습니다."
        }
    },
    "env": {
        "details": {
            "doubt": "로그인·인증 입력폼",
            "reason": "전달된 HTML에서 계정과 비밀번호 입력을 요구하는 폼을 확인했습니다."
        }
    }
}
```

문자가 내세운 목적과 페이지에서 확인한 요구의 차이를 설명할 수 있다. 다만 배송 조회에 로그인이 필요한 경우도 있으므로 두 값의 불일치만으로 악성이나 사칭을 확정하지 않는다. 현재 정책에서 최종 `result`는 계속 `url.official`에 따르며, 불일치를 이유로 이 값을 뒤집지 않는다.

### unknown, 없음, null의 구분

| 값 | 사용 위치 | 의미 |
|---|---|---|
| `unknown` | brand, category, doubt | 식별 불가, 허용 목록 밖 또는 실패로 확인하지 못함 |
| `없음` | message.details.doubt | 문자 분석이 완료되었으며 명시적 행동 요구가 없음 |
| `없음` | env.details.doubt | 제공된 페이지 자료 분석이 완료되었으며 분류 대상 요소·요구가 없음 |
| `null` | 조기 반환의 모든 말단 값 | 정책에 따라 해당 분석 결과 미제공 |

LLM이 해당 출처의 허용 목록 밖 값을 내면 정형 필드는 `unknown`으로 정리한다. `MessageDoubt`의 값이 `EnvDoubt`에도 자동으로 허용되는 것은 아니며, 반대도 마찬가지다. 자유로운 새 분류를 그대로 응답하지 않는다. 전체 응답 파싱 실패나 타임아웃은 확정된 실패 정책에 따라 `answer=false`로 처리한다. 특정 브랜드를 식별하지 못한 사실만으로 전체 분석 실패를 뜻하지는 않는다.

### 근거와 answer의 관계

- 메시지 근거는 현재 메시지 본문의 실제 표현이어야 한다. 구분자를 제거해 라벨을 고르더라도 근거 인용은 원문 형태를 보존한다.
- 페이지 근거는 전달받은 HTML과 확인된 수집 결과에 한정한다. 메시지에 있는 설치 요구를 페이지에서도 확인했다고 쓰지 않는다.
- 두 `doubt`의 추출과 근거 검증을 분리한다. 한쪽에만 존재하는 문구·요소를 다른 쪽의 근거로 채택하지 않는다. 로그인 폼이나 결제 요청 요소의 존재 자체를 악성 확정으로 표현하지 않는다.
- RAG 사례는 비교 자료다. 검색된 사례의 행동·브랜드를 현재 입력에서 관측한 사실처럼 복사하지 않는다. 현재 자료에 정답 분류가 없으므로 `CaseMatch.categories`만 읽어 새 분류를 채울 수 없다.
- `doubt`가 `없음` 또는 일반 조회 행동이라는 이유만으로 `answer=true`를 자동 부여하지 않는다. 개별 `answer`는 분석 완료 여부와 검증된 의심 근거에 대한 별도 결정적 규칙으로 정한다. 주제 분류나 문자열의 유사도만으로 안전을 확정하지 않는다.
- 최종 `result = url.official`, 실패 시 해당 `answer=false`, 조기 반환 시 말단 `null` 정책은 이 분류와 무관하게 유지한다.

### 구현으로 옮길 때의 범위와 검증

1. `ai/src/ai/types.py`에 외부 응답용 필드와 Enum을 정의한다. `MessageDoubt`, `EnvDoubt`를 분리하고 각각의 `details` 타입에서 해당 Enum과 조기 반환용 `null`만 허용한다. JSON 키와 중첩 구조는 유지한다. 기존 `CategoryCode`는 추출·검색에서 사용하는 내부 의미를 유지하고 새 분야 분류와 명시적으로 변환한다.
2. 기존 메시지 추출·검색을 재사용하여 문자 본문의 후보와 근거를 얻는다. 페이지 요소 추출에는 별도 목록과 검증을 적용한다. 라벨 허용 목록, 별칭, 출처별 대표값 선택은 `ai/`의 코드로 구현한다. 사례 Markdown이나 기존 프롬프트 문서를 수정해야 하는 경우 이번 코드 전용 범위를 별도로 검토한다.
3. HTML 분석은 실행·외부 접속 없이 전달된 자료에서 후보를 추출하고 검증한다. 새 파이프라인은 두 출처의 `doubt`와 근거를 덮어쓰지 않고 조립한다.
4. `ai/tests/`에서 별칭 정규화, 변형 브랜드의 오교정 방지, 출처별 다중 후보 선택, 반대 출처의 라벨·근거 혼입 방지, 관측 범위를 넘는 추론 제거, 조기 반환·실패 구분, JSON 왕복을 검증한다. 아래 문자 사례들은 의미 검증용 회귀 사례이며 모델 정확도 평가셋으로 간주하지 않는다. HTML 시나리오는 별도 합성 입력으로 검증하고 실제 관측 사례로 표시하지 않는다.
