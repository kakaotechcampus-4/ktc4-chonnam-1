# 자체 URL 점수기 설계 (urlscan 점수 대체)

작성일: 2026-09-29

상태: 설계 합의 완료, 구현 전. 가중치·기준값·시간 목표는 비교 기간 측정으로 확정하는 초기 가설값이다.

## 목적

urlscan 은 결과 조회까지 약 30초가 걸려 카카오 응답 흐름의 가장 큰 지연 요인이다. urlscan 이 주던
악성 점수를 자체 시스템으로 대체해 **URL 입력부터 점수 도출까지 5~10초 이내**로 줄인다.

- 반환 형태는 공급자와 무관하게 같다: `url.scan = { score, scanned_at }` (`scheme.md` §1).
- 점수 범위는 urlscan 과 같은 -100(정상) ~ 100(악성).
- 점수는 판정(`result`)에 쓰지 않는 기록·비교용 값이다. 판정은 `url.official` 과 `message`·`env` 의 검증된 근거로만 한다.
- 설계 범위 안의 정확도는 포기하지 않는다. 필수 입력이 빠지면 일부 특징으로 점수를 내지 않고 `null` 을 반환한다.

## 범위

| 우선순위 | 항목 |
|---|---|
| Must | 점수 계산(입력 도착 → 점수) 상한 3초, 목표 1초 미만 |
| Must | 격리 서버 수집 목표 7초, 전체 소요 p95 10초 이하 |
| Must | urlscan 과 병행 비교 후 전환 기준 충족 시 교체 |
| Won't (이번 범위 제외) | 이미지 분석 — 로고 이미지·스크린샷 기반 브랜드 판별. 시간이 남으면 이후 추가 |

## 1. 구조와 데이터 흐름

```text
                        ┌─ ① URL 특징 조회 (메인 서버) ─────────── 1~2초 ─┐
URL ─ BE 오케스트레이터 ─┤                                                  ├─▶ ③ 페이지 특징 추출 ─▶ ④ 점수기 ─▶ url.scan
                        ├─ ② 격리 서버 수집 ──────────────────── ≤7초 ──┘      (< 500ms)            (< 1ms)
                        │
                        └─ ⑤ urlscan (백그라운드, 비교 기간만) ─ ~30초 ─▶ ⑥ 비교 기록 (응답을 기다리게 하지 않음)
```

| 구성 요소 | 역할 | 위치 | 입력 → 출력 |
|---|---|---|---|
| ① URL 특징 조회 | WHOIS·RDAP·DNS·위협 피드(로컬 미러) 조회, URL 문자열 파싱. 도메인 단위 캐시 | `backend/src/server/scanner/url_features.py` | 도메인 문자열 → URL 특징 |
| ② 격리 서버 수집 | 웜 풀 브라우저, 이미지·폰트·미디어 차단, 리다이렉트 최대 5홉, 폼 출현 또는 1~2초 네트워크 유휴 시 수집 종료 | 격리 서버 (ADR 0002) | URL → 리다이렉트 경로, 최종 URL, HTML, 폼 전송 대상, 다운로드 여부 |
| ③ 페이지 특징 추출 | 수집 HTML 을 특징으로 변환. `ai/src/ai/page.py` 의 검사 제한을 재사용 | `backend/src/server/scanner/page_features.py` | 수집 결과 → 페이지 특징 |
| ④ 점수기 | 특징 × 가중치 → 점수. I/O 없는 결정적 순수 함수 | `backend/src/server/scanner/scorer.py`, `weights/v1.yaml` | 특징 → -100~100 또는 `null` |
| ⑤ urlscan | 기존 `urlscan_service.py` 를 백그라운드 호출 | 기존 | URL → urlscan 점수·`malicious` |
| ⑥ 비교 기록 | 두 점수·특징값·단계별 시간 저장, 판정 일치율 집계 | BE 작업 저장소 | → 일치율 |

원칙:

- 점수기(④)는 네트워크·LLM·이미지 모델을 쓰지 않는다. 3초 상한을 구조로 보장하고 같은 입력에 같은 점수를 낸다.
- 의심 URL 에 접속하는 곳은 ② 뿐이다. ① 은 도메인 문자열로만 조회하고, ③·④ 는 받은 자료를 데이터로만 다룬다.
- 점수기를 메인 서버에 두어 격리 서버의 분석 부하를 줄인다.
- `ai/` 는 바뀌지 않는다. BE 가 `url.scan` 을 채워 넘긴다 (`backend` → `ai` 단방향, ADR 0002).
- 사용자 응답은 ⑤ 를 기다리지 않는다. 전체 시간 ≈ max(①, ②) + ③ + ④.
- `url.scan` 은 판정에 쓰지 않으므로 페이지 특징을 점수에 넣어도 `env` 와 이중 반영되지 않는다.

### 격리 서버 7초 목표를 위한 조치

| 조치 | 절감 | 정확도 영향 |
|---|---|---|
| 브라우저 웜 풀 | 컨테이너·브라우저 기동 1~3초 | 없음 |
| 이미지·폰트·미디어 차단 | 페이지 로드 수 초 | 로고 이미지 미확인 (Won't 항목과 일치). 텍스트 기반 브랜드 판별은 유지 |
| 폼 출현 또는 1~2초 유휴 시 종료 | 광고·추적 스크립트 대기 | JS 로 늦게 그리는 폼도 포착 |
| URL 단위 결과 캐시 | 반복 요청 거의 0초 | 없음 |
| 리다이렉트 최대 5홉 | 무한 리다이렉트 차단 | 없음 (`docs/latency-budget.md` 규칙) |

## 2. 특징과 점수 계산

```text
score = clamp( Σ 걸린 특징의 가중치, -100, 100 )
```

- 걸린 특징이 없으면 0.
- 위험 특징은 +, 정상 특징은 − 가중치.
- 가중치는 `weights/v{N}.yaml` 에 둔다. 값을 바꾸면 버전을 올리고 작업 기록에 사용 버전을 남긴다.

### 특징과 초기 가중치 (가설값)

URL 특징 (①):

| 코드 | 조건 | 가중치 | 필수 |
|---|---|---|---|
| `threat_feed` | 상업적 사용이 허용된 위협 피드 등재 (1순위 후보: 공공데이터포털 KISA 피싱사이트 URL) | +100 | ✅ |
| `new_domain` | 도메인 생성 30일 이내 | +40 | ✅ (WHOIS/RDAP 조회 성공) |
| `old_domain` | 도메인 생성 2년 이상 | −20 | ✅ (같은 조회) |
| `popular_domain` | Tranco 상위 10만 (로컬 파일) | −30 | |
| `ip_or_port` | IP 직접 접속 또는 비표준 포트 | +30 | |
| `homoglyph` | 퓨니코드 또는 화이트리스트 도메인과 문자 유사도 높음 | +30 | |
| `abused_tld` | 남용 다수 TLD 목록 | +15 | |
| `url_shortener` | 입력 URL 이 단축 URL | +15 | |
| `reported_before` | 자체 신고 이력 (로컬 DB) | +50 | |

페이지 특징 (③, ② 수집 결과 기반):

| 코드 | 조건 | 가중치 | 필수 |
|---|---|---|---|
| `credential_form` | 비밀번호·인증번호 입력 필드 | +40 | ✅ (HTML 전체 수집·검사 성공) |
| `app_download` | APK·실행 파일 다운로드 링크 또는 자동 다운로드 | +50 | |
| `cross_domain_form` | 폼 전송 대상이 페이지와 다른 도메인 | +25 | |
| `brand_on_page` | 페이지 제목·본문의 브랜드명과 도메인 불일치 | +30 | |
| `cross_domain_redirect` | 리다이렉트 중 도메인 변경 | +20 | |

### 필수 특징 규칙

- 필수(✅) 특징의 존재 여부를 하나라도 확인하지 못하면 `score = null`.
- 필수가 아닌 특징을 확인하지 못하면 0 으로 계산하고 작업 기록에 남긴다.

### 비교용 악성 기준

판정 일치율 계산에만 `score >= 50` 을 악성으로 본다. urlscan 은 자체 `malicious` 값을 쓴다.
기준값은 wire 에 싣지 않는다. `threat_feed` 는 단독으로, 나머지는 두 개 이상 겹쳐야 기준을 넘도록 초기 가중치를 잡았다.

### 2단계 (라벨 누적 후)

라벨된 불일치 사례가 수백 건 쌓이면 가중치를 로지스틱 회귀로 학습한다. 확률 p 는 `(2p − 1) × 100` 으로 같은 범위에 맞춘다.
입력 특징은 위 표를 그대로 써서 항목별 설명 가능성을 유지한다.

## 3. 비교 기간 운영과 전환

### 작업별 기록 (BE 작업 저장소, wire 밖)

| 분류 | 항목 |
|---|---|
| 자체 점수 | `score`, 가중치 버전, 특징별 값·가중치, `null` 이유 |
| urlscan | `score`, `malicious`, 조회 시각 |
| 시간 | ①~④ 단계별, 전체 |
| 판정 | 자체(`score >= 50`) vs urlscan `malicious` 일치 여부 (둘 다 값이 있을 때만) |

특징값을 저장하므로 가중치를 바꾸면 재수집 없이 저장 특징으로 재계산한다. 스미싱 페이지는 수 시간 내 사라지는 경우가 많아 재수집에 의존하지 않는다.

### 불일치 처리

판정이 어긋난 건만 사람이 확인해 `smishing` / `benign` / `unknown` 으로 라벨한다.
라벨은 가중치 조정·2단계 학습 자료와, 불일치 건에서 어느 공급자가 맞았는지의 근거로 쓴다.

### 비교 URL 확보

- 스미싱: KISA 공개 사례, 위협 피드 최신 URL. 수집 당일 처리.
- 정상: 화이트리스트 택배사 URL, 목록에 없는 정상 제휴사 URL.
- 목표: 두 점수가 모두 나온 쌍 200 이상.

### 전환 기준 (모두 충족)

| 기준 | 값 |
|---|---|
| 판정 일치율 | 200쌍 이상에서 90% 이상 |
| 불일치 건 정답률 | 라벨이 `unknown` 이 아닌 불일치 건 중 자체 점수기가 맞은 비율 50% 이상 |
| 점수 계산 시간 | p50 1초 미만, p95 3초 이하 |
| 전체 소요 시간 | p95 10초 이하 |
| `null` 비율 | 5% 이하 |

### 전환 후

설정 `SCAN_COMPARE` 를 끄면 ⑤·⑥ 이 멈춘다. 가중치 버전을 올릴 때 다시 켜서 비교할 수 있도록 코드는 남긴다.
사용자 응답 경로는 비교 기간과 같다.

## 4. 오류 처리

| 상황 | 처리 | `score` |
|---|---|---|
| WHOIS 2초 초과 | RDAP 1초 재시도, 실패 시 포기 | `null` |
| 위협 피드 조회 실패 | 1시간 주기 로컬 미러에서만 조회하므로 런타임 외부 의존 없음. 미러 로드 실패 시 | `null` |
| 격리 서버 7초 초과·수집 실패 | `env` 는 기존 규칙대로 `failed` + `collection_failed` | `null` |
| HTML 크기 제한으로 잘림 | 뒷부분 미검사로 `credential_form` 부재를 확정할 수 없음 | `null` |
| 필수 아닌 특징 실패 | 0 처리, 기록 | 계산 |
| 가중치 파일 오류 | 서버 기동 시 검증, 실패하면 기동하지 않음 | — |
| urlscan 실패 (비교 기간) | 기록 후 일치율 계산에서 제외. 응답 영향 없음 | 영향 없음 |

`null` 이유는 wire 에 싣지 않고 작업 기록에 남겨 비교 기간에 비율·원인을 집계한다.

## 5. 보안

- 격리 서버가 넘긴 HTML 은 신뢰하지 않는다. 파싱만 하고 그 안의 URL 로 접속하지 않는다. 크기·처리 시간 제한은 `page.py` 기준을 따른다.
- WHOIS 응답은 외부 텍스트로 취급해 생성일만 파싱한다.
- 네트워크 조회는 ① 에만 둔다. ③·④ 는 네트워크를 쓰지 않는다.

## 6. 테스트

| 대상 | 방법 |
|---|---|
| 점수기 | 표 기반 단위 테스트: 특징별 가중치, clamp, 필수 누락 시 `null`, 가중치 버전 로딩 |
| 페이지 특징 | HTML 픽스처: 비밀번호 폼, APK 링크, 다른 도메인 폼, 브랜드 불일치, 잘린 HTML |
| URL 특징 | 파싱 케이스(IP, 포트, 퓨니코드, 단축 URL). WHOIS·RDAP·피드는 mock, 시간 초과 경로 검증 |
| 시간 상한 | 128KiB HTML 로 특징 추출 + 점수 계산 500ms 이내 |
| 재계산 | 저장 특징으로 재계산 시 동일 점수 |
| 통합 | 가짜 격리 서버 + 30초 걸리는 가짜 urlscan 에서 `SCAN_COMPARE` 가 켜져도 응답 10초 이내, `url.scan` 채워짐 |

실제 WHOIS·격리 서버 왕복 시간은 테스트로 증명하지 않고 비교 기간 측정(§3 전환 기준)으로 확인한다.

## 7. 알려진 위험과 열린 질문

- `.kr` WHOIS 가 느리거나 차단되면 필수 특징 실패로 `null` 이 늘 수 있다. RDAP 대체와 도메인 캐시로 완화하고 비교 기간에 비율을 잰다.
- 격리 서버 7초 목표는 아직 측정 전이다. `docs/latency-budget.md` 의 현재 예산(8~12초)보다 짧다.
- 격리 서버의 반환 항목(리다이렉트 경로, 폼 전송 대상, 다운로드 여부)은 `IsolatedPage` 입력 계약과
  `docs/ai/html-collection-handoff.md` 에서 격리 담당자와 합의해야 한다.
- 서비스를 판매할 예정이므로 외부 데이터는 상업적 사용이 확인된 것만 쓴다 (2026-09-29 확인):
  Google Safe Browsing(비상업 전용)·OpenPhish Community(상업 불가)는 쓰지 않는다. Tranco 는 비상업 출처(Cloudflare Radar)를 뺀
  사용자 정의 목록만 쓴다. KISA 공공데이터의 공공누리 유형과 urlscan 의 상업적 이용 조건은 확인이 필요하다.
  라이선스가 확인된 위협 피드가 생기기 전까지는 `threat_feed` 를 확인할 수 없어 점수가 `null` 이다.
- 남용 TLD 목록의 출처는 구현 전에 정한다.
- PRD 의 수렴 기록 "위험도 점수 → 조사 과정" 과의 관계: 이 점수는 판정·사용자 안내에 쓰지 않는 공급자 비교용 관측값이므로
  조사 과정 중심 원칙을 바꾸지 않는다.
