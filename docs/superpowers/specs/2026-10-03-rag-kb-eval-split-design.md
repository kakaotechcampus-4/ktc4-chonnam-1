# RAG KB·평가 데이터 분할 설계

작성일: 2026-10-03

상태: 설계 합의 단계. 구현 전이다.

선행 설계: [RAG 사례 검색 평가·개선 설계](2026-10-02-rag-eval-improvement-design.md). 지표 정의, 운영 지점, 잠정 목표치와 변경 규칙은 그 문서를 그대로 따른다. 이 문서는 데이터를 나누는 방법만 바꾼다.

## 배경

선행 설계의 실행 결과(`ai/eval/reports/2026-10-03-rag-tfidf.md`)에서 test 스미싱 hit@3 은 20.2%였다.

- hit@3 실패 79건 중 61건이 KB 사례가 0~2건인 유형에서 나왔다.
- KB 사례가 0건인 유형 때문에 hit@3 상한이 63.6%다.

KB(택배 위주)와 테스트셋(14개 유형 균등)을 따로 모아 유형 분포가 다르다. 그래서 지금 수치는 검색 품질보다 KB 의 유형 공백을 잰다. 둘이 겹치지 않는지는 검사하지만, 처음부터 계획해서 나눈 데이터가 아니다.

결정: 테스트셋 스미싱을 유형별로 **KB(검색 대상) : 평가 = 5 : 2** 로 나눈다.

## 분할 대상

- 테스트셋 스미싱 215건만 나눈다.
- 정상·hard negative 560건은 KB 에 넣지 않는다. KB 는 피해 사례 모음이다. 지금처럼 기준값 결정(dev)과 성적(test)에만 쓴다.
- `smishing.jsonl` 127건은 유형 라벨이 없어 이번 범위 밖이다.

## 비율과 배정 규칙

평가 몫 2를 dev 와 test 로 반씩 나눈다. 결과적으로 **KB : dev : test = 5 : 1 : 1** 이다.

유형별로 n건이면 dev 와 test 를 각각 `max(1, round(n / 7))` 건, 나머지를 KB 로 한다. 작은 유형도 dev·test 에 최소 1건씩 남긴다.

| 유형 | 전체 | KB | dev | test |
|---|---|---|---|---|
| delivery · address_correction · payment · penalty · card_or_account · health_check · invitation | 각 20 | 각 14 | 각 3 | 각 3 |
| account_security | 16 | 12 | 2 | 2 |
| prize_or_event | 15 | 11 | 2 | 2 |
| public_support | 14 | 10 | 2 | 2 |
| acquaintance_impersonation · obituary | 각 9 | 각 7 | 각 1 | 각 1 |
| telecom_refund | 7 | 5 | 1 | 1 |
| public_refund | 5 | 3 | 1 | 1 |
| **합계** | **215** | **153** | **31** | **31** |

출처 단위로 묶는다.

- 같은 `source` URL 의 행은 같은 몫에 넣는다. 같은 게시물의 문구끼리는 비슷하기 때문이다. 출처는 194곳이고 그중 8곳이 2건 이상이다.
- 배정 순서: `CategoryCode` 정의 순서로 유형을 돈다. 유형마다 출처 묶음을 `source` 의 SHA-256 순으로 정렬하고 test, dev, KB 순으로 목표 건수까지 채운다. 결정적이라 다시 돌려도 같다.
- 세 출처는 여러 유형에 걸친다(`blog.alyac.co.kr/5240`, `/5260`, `idxno=315779`). 먼저 처리한 유형에서 정한 몫을 뒤 유형에서도 그대로 쓰고, 그 유형의 건수에 넣는다. 그래서 유형별 건수가 위 표와 1건 정도 다를 수 있다.

배정 결과는 데이터에 남긴다.

- `rag_testset.jsonl` 의 모든 행에 `split` 필드(`"dev"` | `"test"`)를 더한다.
- 정상·hard negative 는 지금의 템플릿 해시 결과를 그대로 적는다. 이 행들의 dev/test 는 바뀌지 않는다.
- `rag_metrics.is_dev` 는 해시 대신 `split` 필드를 읽는다. 분할 스크립트는 일회성이며 저장소에 넣지 않는다. 기록은 데이터가 맡는다.
- 테스트로 지킨다: 모든 행에 `split` 이 있다. 같은 출처의 평가 행은 같은 `split` 이다. 유형마다 스미싱 dev·test 가 1건 이상이다. KB 레코드의 `source` 와 평가 행의 `source` 가 겹치지 않는다.

## KB 편입

KB 몫의 행은 `rag_testset.jsonl` 에서 빼서 KB 레코드(`CE-0298` 부터)로 옮긴다. 기존 겹침 검사(`test_eval_dataset_is_disjoint_from_kb`)를 바꾸지 않아도 통과한다.

레코드 frontmatter:

```yaml
id: CE-0298
status: curated
origin: web_public
source: <테스트셋 source URL>
testset_id: <원래 테스트셋 id>
collected_at: 2026-10-02
reviewer: rag-testset-2026-10-02
normalized: "<normalize(첫 variant)>"
variants:
  - "<링크 표기를 지운 본문>"
categories: [<테스트셋 category>]
claimed_brand: ""
```

- 게시일은 테스트셋에 없어 적지 않는다. 기존 팀 수집 레코드도 같다.
- **링크 표기를 지운다.** 운영 검색 질의는 링크를 뺀 본문이고(`ai/src/ai/kb/README.md`), 기존 KB 레코드 296건에도 링크가 없다. 테스트셋 스미싱 215건 중 67건에 `hxxps://…`, 가린 도메인 같은 링크 표기가 있다. 지운 결과가 6자 미만이면 편입하지 않고 PR 에 목록을 남긴다.
- 기존 KB 테스트(개인정보, 레코드 간 중복, `normalized` 필드, 유형 형식)가 새 레코드에도 그대로 적용된다.

## 근접 중복 점검

출처로 묶어도 같은 캠페인 문구가 다른 출처에 실려 KB 와 평가로 갈라질 수 있다. 평가 행마다 새 KB 레코드와의 top-1 유사도를 재서 0.8 이상인 행을 PR 본문에 목록으로 남긴다. 머지 전에 사람이 보고, 사실상 같은 문자면 그 평가 행을 KB 쪽으로 옮긴다.

## 평가 변경

- 평가 스미싱은 62건(dev 31 / test 31)이다. test 1건이 약 3.2%p 다. 유형별 test 는 1~3건이라 선행 설계대로 건수로만 적는다.
- 리포트의 운영 지점 hit@3 줄에 95% 신뢰구간(Wilson)을 함께 적는다. 31건에서 20% 근처면 구간이 대략 9~37% 로 넓다. 목표 대비 판단에 이 폭이 필요하다.
- KB 가 바뀌므로 TF-IDF 설정과 기준값을 다시 정한다: dev 에서 6개 조합 비교 → 기본값 확정 → test 1회. 새 test 는 이전과 다른 행이므로 이번 test 1회는 선행 설계의 "test 는 한 번만" 규칙과 충돌하지 않는다.
- 이전 리포트는 기록으로 둔다. 평가 행이 달라 이전 수치와 직접 비교하지 않고, 리포트에 그 점을 적는다.

## 진행 순서

1. 분할 PR: `split` 필드 추가, KB 몫 이동(KB 레코드 생성), 테스트 추가. 커밋은 "평가셋 split 필드"와 "KB 편입"(유형별)으로 나눈다. PR 본문에 유형별 배정표, 링크를 지운 행 목록, 근접 중복 목록을 싣는다. 사람 검토 후 머지한다.
2. 평가 도구: `is_dev` 를 `split` 필드로 바꾸고 Wilson 구간을 리포트에 더한다.
3. 재조정: dev grid → 기본값 → test 1회 → 리포트·해석 → 지연 예산 문서 갱신.

## 범위 밖

- `smishing.jsonl` 127건의 유형 라벨링과 편입.
- 평가 질의의 링크 제거. 지금 평가는 링크 표기가 남은 원문으로 검색해 운영 질의와 다르다. 링크 제거는 BE 가 하고 `ai/` 에는 그 함수가 없다. 별도로 다룬다.
- 교차검증. 평가 표본이 작은 문제는 구간 표기로 드러내는 데서 멈춘다.

## 위험

- **작은 평가 표본.** test 스미싱이 31건뿐이라 설정끼리 차이가 1~2건이면 우열을 가릴 수 없다.
- **KB 성격 변화.** 편입 원문 대부분이 블로그 게시물 제목·보고서 문구라 실제 수신 문자보다 짧고 형식이 다르다. KB 의 약 1/3(153/449)이 이런 문구가 된다. 운영 질의(실제 문자)에서의 효과는 이 평가로 보장되지 않는다.
- **같은 출처의 평가·KB 분포.** 평가와 KB 가 같은 블로그에서 나와, 실제 문자보다 평가 점수가 후하게 나올 수 있다.
