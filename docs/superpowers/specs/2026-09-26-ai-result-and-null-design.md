# AI 종합 판정과 null 의미 변경 설계

작성일: 2026-09-26

상태: 사용자와 대화에서 합의한 요구사항을 정리한 구현 전 설계. 코드와 기존 연동 계약 문서는 아직 변경하지 않았다. BE와 합의된 계약으로 간주하지 않는다.

## 목적과 범위

`result`를 URL의 `official` 복사값에서 URL·메시지·격리 환경 분석을 종합한 신뢰 여부로 변경한다. 공식 여부와 최종 결과에 관계없이 확보한 분석 내용을 보존한다. `null`은 비정상적인 과정으로 값을 정상 산출하지 못한 경우에만 사용한다.

이번 작업은 `ai.pipeline`의 타입 검증, 부분 결과 생성, 최종 조립과 테스트·문서 변경이다. HTML 검사기의 수신·파싱 제한 강화는 후순위이며 포함하지 않는다. BE 코드, URL 검사기, 외부 수집, 카카오 출력, 기존 `decide()` API는 변경하지 않는다.

## 합의한 결과 의미

### 최종 result

| 개념상 상태 | 조건 | 이번 반환 | 향후 방향 |
| --- | --- | --- | --- |
| 신뢰 | URL 기준 통과, 메시지·환경 분석 모두 정상 완료 및 의심 근거 없음 | `true` | 문자열 상태 |
| 의심 | 필요한 분석이 완료되었고 세 요소 중 하나 이상 의심 | `false` | 문자열 상태 |
| 실패 | 필요한 자료 누락, 오류, 시간 초과, 부분 자료 등으로 필수 분석 미완료 | `false` | 문자열 상태 |

향후 문자열 상태의 정확한 직렬화 값과 도입 시점은 이번에 정하지 않는다. 이번에는 새 상태 필드를 추가하지 않는다. 의심 근거와 실패가 동시에 존재하면 전체 과정은 미완료이며, 확보한 의심 근거는 그대로 남긴다.

```python
result = (
    url.official is True
    and message.answer is True
    and env.answer is True
)
```

부분 결과 생성 단계는 미완료 분석에 `answer=True`를 반환해서는 안 된다. 따라서 위 규칙만으로 미완료 결과가 신뢰로 승격되는 것을 방지한다. 최종 판정은 결정적 코드가 수행하며 LLM이 최종 값을 정하지 않는다.

### 부분 분석의 answer

| 값 | 의미 |
| --- | --- |
| `true` | 해당 분석 정상 완료, 검증된 의심 근거 없음 |
| `false` | 해당 분석 정상 완료, 검증된 의심 근거 있음 |
| `null` | 해당 분석을 정상적으로 완료하지 못함 |

현재의 근거 검증·분류 기준은 유지한다. `doubt`에 로그인 폼·배송 조회 같은 요소가 분류되었다는 사실만으로 `answer=false`로 바꾸지 않는다. 현재 코드가 검증해 채택한 위험 신호를 의심 판정에 사용한다.

실패 중 일부 의심 근거를 발견한 경우에도 `answer=null`을 사용한다. 다만 확인한 `doubt`와 설명은 보존한다. 이는 실패가 근거를 지우거나, 근거가 있다는 이유로 미완료를 정상 완료처럼 처리하는 것을 모두 막는다.

### null과 unknown, none

- `null`: 해당 값을 산출하지 못했다. 공식 URL이라는 이유나 정상 판정이라는 이유로 사용하지 않는다.
- `unknown`: 정상적인 식별·분류 결과가 미상이다. 또는 이미 확보한 자료가 실제로 미상이라는 결과를 제공했다. 실패 기본값을 무조건 `unknown`으로 채우지 않는다.
- `MessageDoubt.NONE` / `EnvDoubt.NONE`: 정상적으로 검사했지만 해당 분류 대상이 없다. 기존 JSON 값은 `"없음"`이며 유지한다. 대화에서 사용한 `"none"`은 개념 설명이므로 새 직렬화 값으로 도입하지 않는다.
- 실패한 필드만 `null`로 둔다. 부분 결과 전체를 일괄 초기화하지 않는다.
- `details.reason`은 실패 시에도 구체적인 미완료 사유를 담는다. 실패만으로 악성을 발견했다거나 의심 근거가 있다고 표현하지 않는다.
- `url.official`은 기존의 필수 `StrictBool`이다. 이번 null 규칙은 AI가 생성하는 메시지·환경 결과에 적용한다.

정상 완료된 부분은 기존 5개 말단 필드(`brand`, `category`, `answer`, `details.doubt`, `details.reason`)를 모두 채운다. 미완료 부분은 `answer=null`과 실패 설명을 제공하고, 나머지 값은 확보한 범위만 채운다. 기본 생성된 빈 부분 객체는 최종 조립에서 자료 미제공 사유를 가진 실패 부분으로 정규화한다.

## 호출과 보존 규칙

1. `finalize_analysis()`는 공식 여부로 조기 반환하지 않는다.
2. 전달된 메시지 분석 결과를 재사용하며 재분석하지 않는다.
3. 전달된 페이지는 기존 `analyze_environment_part()`로 분석한다. 페이지가 없으면 기존 실패 경로를 사용하며 추가 네트워크 수집을 수행하지 않는다.
4. 수집 실패 코드와 부분 페이지가 함께 전달되면 실패 상태와 확보한 관측을 함께 보존한다.
5. `assemble_analysis()`는 메시지·환경 결과를 보존하고 종합 `result`만 계산한다.
6. `answer=null`인 부분이 들어왔다는 이유로 이미 있는 근거나 실패 설명을 기본 누락 결과로 덮지 않는다.
7. 요청 취소 `CancelledError`는 기존처럼 전파한다. 취소된 요청을 일반 실패 응답으로 바꾸지 않는다.

### 예시: 신뢰

```json
{
  "url": {"final_url": "https://example.com/track", "domain": "example.com", "official": true},
  "message": {
    "brand": "unknown", "category": "unknown", "answer": true,
    "details": {"doubt": "없음", "reason": "제공된 문자에서 명시적인 행동 요구를 확인하지 못했습니다."}
  },
  "env": {
    "brand": "unknown", "category": "unknown", "answer": true,
    "details": {"doubt": "없음", "reason": "제공된 HTML에서 분류 대상 요소를 확인하지 못했습니다."}
  },
  "result": true
}
```

예시 URL은 설명용이다. 특정 서비스의 실제 공식 주소 확인을 뜻하지 않는다. 정상 결과의 설명도 제공된 자료에서 확인한 범위만 말한다.

### 예시: 공식 URL이나 환경 자료 누락

```json
{
  "url": {"final_url": "https://example.com/track", "domain": "example.com", "official": true},
  "message": {
    "brand": "unknown", "category": "unknown", "answer": true,
    "details": {"doubt": "없음", "reason": "제공된 문자에서 명시적인 행동 요구를 확인하지 못했습니다."}
  },
  "env": {
    "brand": null, "category": null, "answer": null,
    "details": {"doubt": null, "reason": "페이지 자료를 전달받지 못해 환경 분석을 수행하지 못했습니다."}
  },
  "result": false
}
```

## 현재 코드에서 바꿀 지점

| 위치 | 현재 규칙 | 변경 |
| --- | --- | --- |
| `ai/src/ai/pipeline/finalize.py` | 공식이면 입력 분석 자료 무시 | 공식 여부와 무관하게 페이지 분석·조립 |
| `ai/src/ai/pipeline/results.py` | `result=official`, 공식이면 부분 초기화 | 부분 보존, 세 요소 종합 |
| 같은 파일의 부분 생성 함수 | 실패 시 `answer=false`, 미상 값과 의심 문구 | 실패 시 `answer=null`, 실제 확보 값과 실패 이유 |
| `ai/src/ai/types.py`의 부분 검증 | 모두 null 또는 모두 값 있음 | 정상 부분은 완전한 값, 실패 부분은 값과 null 혼합 허용 |
| 같은 파일의 응답 검증 | `result == official`, 공식이면 모두 null | 종합 판정 일치 검증, 공식이어도 내용 허용 |

브랜드·분류 보존은 출처를 기준으로 한다. 문자 추출이 완료됐다면 그 결과를 사용하고, 실패했더라도 원문 규칙으로 실제 식별한 값은 남긴다. 실패한 추출기의 기본 `unknown`만 존재하는 경우에는 `null`로 둔다. 환경도 성공한 페이지 분석값, 실제 HTML 관측, 유효한 수집 메타데이터를 구분한다. 메타데이터를 사용했다면 기존처럼 설명에 출처를 남긴다. 실패 상황에서 아무 출처도 없는 값을 만들어 채우지 않는다.

## 호환성 및 제외 범위

- 응답 키와 `result`의 boolean 타입은 유지하지만 의미와 허용되는 null 조합은 변경된다. BE와 의미상 호환이 자동 보장되는 변경은 아니다.
- 현재 `main.py`는 공식일 때 `finalize_analysis(url=...)`만 호출한다. 변경 후 이 호출은 문자·환경 누락으로 `result=false`가 된다. AI가 받지 못한 분석 자료를 복구할 수 없다.
- 현재 문서의 `official`은 BE의 점수 기준 통과 값이며 실제 공식 도메인 대조 결과가 아니다. 이번 변경은 이 입력을 그대로 사용한다. URL 판정 방식 자체를 변경했다고 표현하지 않는다.
- BE의 자료 전달, 오류 상태 전달 규격, 원본 점수 보존, FE 표시, 문자열 결과 전환은 별도 연동 작업이다.
- 기존 `decide()`와 그 테스트의 공식 도메인 정책은 이번 `ai.pipeline` 변경 대상이 아니다.

## 완료 기준

- 공식 URL + 정상 두 부분은 `result=true`이며 두 부분 내용이 유지된다.
- 공식 URL + 의심 부분은 `result=false`이며 의심·정상 결과 모두 유지된다.
- 필수 부분 누락·실패는 `answer=null`, `result=false`이며 실패 이유가 남는다.
- 실패 중 확보한 근거와 다른 부분의 정상 결과가 유지된다.
- 완료 후 분류할 내용이 없는 `unknown`/`none`은 null과 구별된다.
- JSON 왕복 검증에서도 null·근거·종합 판정이 보존된다.
- 기존 근거 검증, 클라이언트 소유권, 요청 취소 처리에 회귀가 없다.

구현 순서와 실행 가능한 검증 예시는 [구현 계획](../plans/2026-09-26-ai-result-and-null.md)을 따른다.
