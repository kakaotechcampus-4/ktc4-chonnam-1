# RAG 사례 검색 평가·개선 설계

작성일: 2026-10-02

상태: 설계 합의 단계. 구현·측정 전이다. 아래 목표치는 잠정값이며 통과 기준으로 확정되지 않았다.

## 목적과 범위

`ai/eval/datasets/rag_testset.jsonl`(775건)을 기준으로 피해 사례 검색(`ai/src/ai/kb/search.py`)의 품질을 재고, 검색 방식을 개선한다.

두 목표를 함께 다루되 A를 우선한다.

- **A. 참고 사례 관련성.** 스미싱 입력에 같은 유형의 사례가 상위에 나온다. 이 사례는 위험 신호 제안(`ai/src/ai/llm/signals.py` 의 `_reference_cases`)에 참고로 들어간다.
- **B. 정상 문자 비부착.** 정상 문자에는 사례가 붙지 않는다. "비슷한 피해 사례가 있다"는 인상을 주지 않기 위해서다.

테스트셋의 72%(560건)가 정상 문자다. 정상 문자 평가는 A 이후로 미루지 않고 처음부터 스미싱과 같은 비중으로 측정한다.

## 지켜야 할 제약

- 검색 결과는 판정을 바꾸지 않는다(CLAUDE.md 원칙 1). 유사도는 악성 확률이 아니다. 이 설계는 `decide()` 의 입력을 바꾸지 않는다.
- 사례 검색 예산은 1.0초다(`docs/latency-budget.md`). 결정적이어야 하고 외부 연결 없이 돌아야 한다.
- `ai/` 안에서 `server` 를 import 하지 않는다(원칙 4).
- 테스트셋의 정상·hard negative 문자는 합성이다. 이 데이터로 잰 수치를 실제 오탐률로 인용하지 않는다(`ai/eval/datasets/README.md`).
- 평가 README 규칙대로 각 지표의 분모·평가법·통과 기준을 명시한다. 합의되지 않은 수치와 미실행 항목을 통과로 처리하지 않는다.

## 기준선 측정 (2026-10-02, 임시 스크립트)

현재 `search_cases()`(문자 3-gram Jaccard)를 `min_similarity=0`, `top_k=3` 으로 테스트셋 전체에 돌렸다. KB 는 `status: curated` 로 읽힌 296건이다. 재현 가능한 평가 도구로 만들기 전의 값이므로 참고 기록으로만 쓴다.

| 항목 | 스미싱 (215) | 정상 (280) | hard negative (280) |
|---|---|---|---|
| top-1 유사도 중앙값 | 0.058 | 0.078 | 0.056 |
| top-1 이 현재 기준값 0.3 이상 | 8% | 0% | 0% |

| 항목 | 결과 |
|---|---|
| AUC (top-1 유사도로 스미싱 vs 정상) | 0.464 |
| AUC (스미싱 vs hard negative) | 0.560 |
| 유형 hit@1·hit@3 | 0/215. KB 296건 모두 `categories: []` 라 측정할 수 없다 |
| 문자 길이 중앙값 | KB 29자, 테스트셋 스미싱 47자·정상 43자·hard negative 68자 |

해석:

1. 스미싱의 92%는 기준값을 넘는 사례가 없어 참고 사례가 비어 있다.
2. 유사도가 스미싱 여부와 무관하다. 정상 문자가 오히려 KB 와 조금 더 비슷하다. `_similarity` 의 `ponytail:` 주석이 우려한 상황이다.
3. KB 에 유형이 없어 검색된 사례가 맞는 유형인지 확인할 수 없다. 이게 첫 번째 병목이다.

## 측정 설계

### 그룹별 질문과 지표

| 그룹 | 건수 | 질문 | 지표 |
|---|---|---|---|
| `smishing` | 215 (실물) | 같은 유형 사례가 상위에 나오는가 | hit@1, hit@3, MRR, 부착률. 유형별로도 산출 |
| `benign` | 280 (합성) | 사례가 붙지 않는가 | 부착률. 유형별로도 산출 |
| `hard_negative` | 280 (합성) | 가장 헷갈리는 정상 문자에도 사례가 붙지 않는가 | 부착률. 유형별로도 산출 |
| 스미싱 vs 정상 두 그룹 | — | 점수로 구분되는가 | AUC. 상대 그룹마다 따로 |

지표 정의:

- **부착**: top-1 점수가 기준값 이상이다. 기준값 미만 사례는 LLM 에 가지 않으므로 없는 것으로 친다.
- **hit@k**: 상위 k개 중 기준값 이상이면서 `categories` 에 행의 `category` 가 들어 있는 사례가 하나라도 있다. 분모는 해당 그룹의 행 수다.
- **MRR**: 위 조건을 만족하는 첫 사례 순위의 역수다. 상위 3개 안에 없으면 0이다.
- **AUC**: 스미싱 top-1 점수가 정상 top-1 점수보다 클 확률이다. 동점은 0.5로 센다. 기준값과 무관하다.

정상 문자에도 유형이 있으므로 "과태료 정상 문자가 과태료 스미싱 사례에 끌려온다"처럼 어느 유형에서 잘못 붙는지 볼 수 있다.

### 운영 지점

기준값을 낮추면 스미싱 hit 이 늘고 정상 부착도 는다. 검색 방식끼리 공정하게 비교하려고 운영 지점을 하나로 고정한다.

1. dev 절반에서 hard negative 부착률이 X 이하가 되는 가장 낮은 기준값을 고른다. 후보는 dev 에서 관측된 top-1 점수 전체다.
2. 그 기준값을 test 절반에 적용해 스미싱 hit@3 을 대표 수치로 삼는다. 정상 부착률과 hit@1, MRR 은 함께 보고한다.

### dev/test 분할

- 각 그룹을 반으로 나눈다. 앞 절반(dev)으로 기준값과 설정값을 맞추고, 뒤 절반(test)으로 성적을 낸다.
- 분할 키는 해시로 정해 매번 같다. 스미싱은 `id`, 정상·hard negative 는 `template` 을 키로 쓴다. 같은 템플릿에서 나온 행끼리 거의 중복이라 양쪽에 갈라지면 같은 문제로 시험을 보는 셈이기 때문이다. 템플릿 수는 정상 124개(템플릿당 최대 5행), hard negative 154개(최대 4행)다.
- 리포트에 그룹별 dev/test 행 수와 템플릿 수를 적는다.
- 유형별 test 표본은 2~10건 수준이다(스미싱 `public_refund` 는 전체 5건). 유형별 수치는 n 과 함께 적고, 유형별 백분율로 결론을 내지 않는다.

### 잠정 목표치

| 항목 | 잠정값 |
|---|---|
| X: 운영 지점의 hard negative 부착률 (dev) | 5% 이하 |
| 운영 지점의 스미싱 hit@3 (test) | 50% 이상 |

### 결과가 안 좋을 때 수치를 바꾸는 규칙

| 대상 | 예 | 조건 |
|---|---|---|
| 검색 설정값 | 기준값, n-gram 범위, TF 가중 방식, `top_k` | 언제든 바꿀 수 있다. dev 에서만 조정한다. test 는 최종 확인 때 한 번 본다 |
| 목표치 | X, hit@3 목표 | 바꿀 수 있다. 원래 값·바꾼 값·근거를 리포트에 남기고, 원래 기준의 결과도 지우지 않는다 |

목표치를 바꾸는 근거는 데이터에서 나와야 한다.

- 인정하는 근거: "유형 Y 의 KB 사례가 0~2건이라 hit 이 구조적으로 불가능하다." 이 경우 그 유형은 따로 보고하고 전체 목표는 유지한다.
- 인정하지 않는 근거: "45%가 나왔으니 목표를 45%로 내린다." 이 경우 실패 사례를 분석하고 임베딩 방식(범위 밖 항목 참조) 검토의 근거로 쓴다.

## 구성 요소

### 1. 평가 도구

| 파일 | 역할 |
|---|---|
| `ai/eval/rag_metrics.py` | 분할, hit@k, MRR, AUC, 부착률, 운영 지점 선택. 입출력 없는 순수 함수 |
| `ai/eval/rag_eval.py` | 테스트셋 읽기 → 분할 → 검색 → 지표 → 리포트 작성 |
| `ai/tests/test_rag_metrics.py` | 지표 함수 단위 테스트. 손으로 계산한 작은 예제로 검증한다 |

- 검색 함수는 `Callable[[str], list[CaseMatch]]` 로 받는다. 반환값은 점수 내림차순 상위 3개이며 기준값을 적용하지 않은 것이다. 기준값은 평가 도구가 적용한다. 현재 방식은 `search_cases(text, min_similarity=0.0, top_k=3).matches` 로 감싼다.
- 평가 코드는 런타임 패키지 `ai` 에 넣지 않는다. 테스트는 `ai/eval/rag_metrics.py` 를 파일 경로로 불러온다.
- 리포트는 `ai/eval/reports/YYYY-MM-DD-rag-<방식>.md` 에 남긴다. 담는 내용:
  - 코드 커밋, KB 건수와 유형별 KB 건수, 설정값, 운영 지점 기준값
  - 위 지표 전체(그룹별·유형별, dev/test 구분)
  - 질의 1건 소요 p50·p95와 첫 호출(KB 로드 포함) 소요
  - 실패 사례: 스미싱 중 hit@3 실패 상위 10건, 부착된 정상 문자 상위 10건의 원문과 붙은 사례
  - 합성 데이터 경고 문구
- **실행 환경 문제.** 현재 `ai/.venv` 는 저장소 경로의 한글 때문에 `uv run` 에서 `.pth` 파일을 cp949로 읽다가 실패한다. 기준선 측정은 `PYTHONUTF8=1 PYTHONPATH="src;.venv/Lib/site-packages" python ...` 로 돌렸다. 이 우회 방법을 `ai/eval/README.md` 에 적는다. venv 자체 수정은 범위 밖이다.

### 2. KB 유형 라벨링

- 대상은 `status: curated` 사례 296건의 `categories` 다. 다른 필드와 `status` 는 바꾸지 않는다.
- 테스트셋처럼 사례마다 대표 유형 하나만 붙인다. 여러 유형을 허용하면 hit 이 부풀려진다. 어느 유형에도 확신이 없으면 비워 둔다.
- 테스트셋 분류에 쓴 키워드 규칙은 저장소에 없다. `CategoryCode` 14개(`other`·`unknown` 제외)의 뜻에 맞춰 키워드 후보 규칙을 새로 쓴다. 후보는 Claude 가 원문을 읽어 확인한 뒤 frontmatter 에 바로 넣고, 사람 검토는 PR 리뷰로 한다.
- 키워드 후보 규칙은 일회성 도구로 다루고 검색 코드에서 쓰지 않는다. 검색과 라벨이 같은 규칙에 기대면 hit 이 부풀려진다.
- PR 하나로 올리고 커밋을 유형별로 나눈다. 리뷰어는 커밋마다 "전부 이 유형인가"만 확인하면 된다.
- PR 본문에 유형별 건수, 판단 근거 키워드, 비워 둔 사례 목록을 적는다.
- PR 승인을 사람 검토로 본다. 머지 전에는 이 라벨로 낸 수치를 평가 결과의 근거로 쓰지 않는다.
- 유형별 KB 건수를 평가 리포트에 함께 적어 "검색 실패"와 "KB 부족"을 구분한다.

### 3. 검색 방식 개선: TF-IDF 코사인

`_similarity` 의 문자 3-gram Jaccard 를 문자 n-gram TF-IDF 코사인 유사도로 바꾼다.

- 정규화는 기존 `normalize()` 를 그대로 쓴다.
- 문서 단위는 사례의 variant 하나다. IDF 는 KB 전체 variant 로 계산한다: `idf = ln((1 + N) / (1 + df)) + 1`.
- 질의에서 KB 에 없는 n-gram 은 `df = 0` 으로 계산해 질의 벡터의 크기에 넣는다. 질의 대부분이 KB 에 없는 표현이면 점수가 낮아져 정상 문자 부착을 줄이는 쪽으로 작동한다.
- 벡터는 L2 정규화한다. 가중치가 음수가 아니므로 점수는 0~1이다. BM25 를 쓰지 않는 이유는 점수 상한이 없어 0~1을 전제로 하는 `CaseMatch.similarity` 와 `min_similarity` 를 쓰는 곳까지 바꿔야 하기 때문이다.
- 사례 점수는 variant 점수 중 최댓값이다. 지금과 같다.
- dev 에서 조정할 설정값과 초기값:
  - n-gram 범위: 2~3 (후보 3~3, 2~2)
  - TF: 원 빈도 (후보 `1 + ln(tf)`)
- 새 의존성 없이 순수 파이썬 dict 로 구현한다.
- 색인(IDF, variant 벡터)은 KB 를 읽을 때 한 번 만든다. 기존 `_LOAD_LOCK` 과 `lru_cache` 구조를 그대로 쓴다. `load_cases()` 의 공개 동작은 유지한다.
- `search_cases()` 의 시그니처와 반환 타입은 그대로다. `analysis.py`·`signals.py` 는 고치지 않는다. 바뀌는 건 `min_similarity` 기본값뿐이며 운영 지점으로 정한 값을 넣는다.
- 옛 Jaccard 구현과 `ponytail:` 주석은 지운다. 비교 대상은 기준선 리포트가 맡는다.
- 기존 `ai/tests/test_search.py` 는 모두 통과해야 한다. 점수 값에 기대는 테스트는 의도(기준값 미만 제외, top_k 준수)를 유지한 채 고친다.

## 진행 순서

1. 평가 도구를 만들고 현재 코드로 기준선 리포트를 커밋한다. 유형 지표는 아직 0이다.
2. KB 유형 라벨링 PR 을 올리고 머지한다.
3. 라벨이 들어간 KB 로 현재 코드의 기준선을 다시 잰다. 이때 처음으로 hit@k 가 의미를 갖는다.
4. TF-IDF 코사인을 구현하고 dev 에서 설정값과 운영 지점을 정한다.
5. test 에서 한 번 재고 리포트를 쓴다. 목표에 못 미치면 수치 변경 규칙에 따라 실패 사례를 분석하고 임베딩 방식 검토 여부를 정한다.

## 범위 밖

- **임베딩 검색.** 의미가 같은데 표현이 다른 문자를 잡을 수 있지만, 외부 API 는 1초 예산 안의 네트워크 지연·실패와 본문 외부 전송 경로가 생긴다. 로컬 모델은 torch 같은 무거운 의존성과 콜드 스타트 비용이 든다. 5단계 결과가 목표에 못 미치고 실패 사례가 표현 차이로 설명될 때만 별도 설계로 다룬다.
- **질의 유형 추정 가산점.** 키워드 규칙으로 질의 유형을 추정해 같은 유형 사례에 점수를 더하는 방식은 라벨링 규칙과 엮여 수치를 부풀리므로 채택하지 않는다.
- 실물 정상 문자 수집과 `benign.jsonl` 확장.
- `ai/.venv` 의 한글 경로 문제 수정.
- 판정·설명 단계 변경.

## 위험

- **라벨 편향.** 테스트셋과 KB 를 비슷한 방식(키워드 1차 분류)으로 라벨링하므로 두 라벨이 같은 오류를 공유할 수 있다. PR 검토와 실패 사례 원문 확인으로 줄인다.
- **분포 차이.** 테스트셋 스미싱 대부분은 블로그 게시물 제목·보고서 문구라 실제 수신 문자보다 짧거나 다를 수 있다(예: "스마트이용대금명세다운로드"). 실물 문자로 확인되기 전까지 수치를 실제 성능으로 인용하지 않는다.
- **유형별 KB 부족.** 일부 유형은 KB 사례가 거의 없을 수 있다. 3단계에서 유형별 KB 건수를 확인하고, 부족한 유형은 검색 개선이 아니라 KB 수집 과제로 분리한다.
