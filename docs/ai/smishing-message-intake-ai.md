# 스미싱 메시지 분석 — AI 파트 설계

이 문서는 합의된 프로토타입의 역할, 분석 흐름, 데이터 계약의 의미를 정의한다.
구현 완료를 뜻하지 않는다. 구체적인 JSON 예시·필드명·Python 타입·함수 시그니처 작성은 보류한다.
기존 코드 예시는 아래의 서술형 계약으로 대체한다.

## 0. 범위와 담당 경계

프로토타입은 택배 사칭 의심 메시지를 대상으로 메시지 정보 추출, 피해 사례 검색,
백엔드 링크 분석을 수행한다. 자체 격리 환경 구축은 프로토타입에서 제외한다.

| 담당 | 책임 |
|---|---|
| 백엔드 | 텍스트·링크 분리, URL 해석, 공식 도메인 조회, urlscan 호출, 스캐너 결과의 공통 구조 변환, 작업 실행·저장·조회, 카카오 연동 |
| AI 파트 | 브랜드·주장 목적·요구 행동 추출, 피해 사례 검색 및 유사도 산출, 관측 내용 설명, 결과 정보 조립 |
| 결정적 판정 코드 | 검증된 공식 도메인과 관측 사실을 정해진 규칙으로 대조하여 최종 상태 결정 |
| LLM | 메시지 정보 추출과 설명. 최종 판정 권한은 없음 |

AI 담당 코드와 LLM은 같은 의미가 아니다. 결정적 판정 코드의 구체적인 모듈 배치는 별도 확정한다.
의존 방향은 백엔드에서 AI로만 향한다. AI 파트는 서버 모듈을 import하거나 카카오 payload·카드를 구성하지 않는다.
스캐너 호출과 DB 접근은 백엔드가 담당하고, AI 분석 로직은 제공받은 데이터와 의존성을 사용한다.
BE↔AI는 기존 로컬 패키지 ADR을 유지한다. 구조화된 결과 전달이 별도 HTTP 서버 도입을 의미하지 않는다.

### 판정 원칙

1. 최종 판정은 결정적 코드가 한다. LLM에게 스미싱 여부를 결정하도록 맡기지 않는다.
2. 공식 도메인은 사람이 검증한 목록만 사용한다. 검증자가 없는 도메인 정보는 공식 판정에 사용하지 않는다.
3. 공식 도메인 일치는 해당 도메인이 등록된 공식 도메인이라는 뜻이다. 메시지 전체나 사이트 내용의 안전을 보증하지 않는다.
4. RAG 유사도는 참고 정보다. 판정을 변경·확정하거나 추가 검사를 결정하는 임계값으로 사용하지 않는다.
5. urlscan의 점수·categories·brands를 최종 판정에 사용하지 않는다. 스캐너 점수와 RAG 유사도를 결합하지 않는다.
6. 관측 사실, 모델의 해석, 확인하지 못한 사항을 구분한다. 근거가 부족하면 결론을 강제하지 않는다.
7. 모델이나 검색이 실패해도 확보한 근거로 응답한다. 실패한 부분을 명시하며 설명 생성 실패 시 템플릿으로 폴백한다.

### 다른 문서와의 정합성

이 문서는 이번 합의를 먼저 반영한 설계다. AGENTS.md·CLAUDE.md의 기존 LLM 역할 제한,
다른 문서의 콜백 전제와 이전 판정 라벨 등은 별도 동기화가 필요하다.
이 문서만으로 저장소 전체의 문서나 구현이 갱신되었다고 간주하지 않는다.

## 1. 백엔드와의 계약

### 메시지 전달

백엔드는 메시지에서 텍스트와 링크를 분리하고, 링크를 제외한 텍스트를 AI에 전달한다.
AI는 도메인 문자열을 보고 메시지의 브랜드나 목적을 추측하지 않는다.
키워드 압축 기능은 두지 않는다. 메시지 정보 추출과 사례 검색은 링크를 제외한 본문을 사용한다.
개인정보는 모델·검색 입력과 로그에 사용하기 전에 마스킹한다.

### 링크 분석 결과의 공통 구조

백엔드는 urlscan과 향후 자체 스캐너의 결과를 동일한 의미의 공통 구조로 변환한다.
AI는 공급자별 원본 응답에 직접 의존하지 않는다.

| 정보 묶음 | 전달할 내용 |
|---|---|
| 분석 상태 | 완료·부분 완료·실패·미실행 여부 |
| URL 정보 | 최종 URL, 정규화된 도메인, 리다이렉트 경로 |
| 페이지 정보 | 수집 가능한 제목·페이지 텍스트·스크린샷 참조 |
| 관측 사실 | 설치 파일 링크, 개인정보 입력 필드 등 실제 검사에서 확인한 정보 |
| 수집 출처 | 스캐너, 수집 시각, 근거 자료 참조 |
| 미확인 항목 | 지원하지 않거나 실패하거나 실행하지 않은 검사와 사유 |

각 검사 결과는 다음 세 의미를 구분한다.

- **발견:** 검사에서 해당 요소를 확인했다.
- **검사했으나 미발견:** 명시된 검사 범위에서 해당 요소를 찾지 못했다.
- **미확인:** 검사 미지원·실패·미실행 등으로 존재 여부를 알 수 없다.

빈 목록이나 접속 성공만으로 미발견을 추론하지 않는다. 접속에 성공해도 일부 검사는 실패할 수 있다.
자체 스캐너가 제공하지 못하는 정보는 미확인으로 전달하며, LLM이 누락된 사실을 채우지 않는다.
스캐너 교체로 관측 범위가 줄어들면 판단 보류나 분석 불가가 늘 수 있다. 동일 결과를 억지로 보장하지 않는다.

공식 도메인 조회 결과와 메시지에서 추출한 브랜드의 출처도 구분한다.
스캐너의 brands가 없다는 이유로 안전이나 사칭 여부를 추론하지 않는다.
상세 필드, 직렬화 방식, 계약 정의의 저장 위치는 후속 합의 사항이다.

## 2. 프로토타입 분석 흐름

1. 백엔드가 메시지의 텍스트·링크를 분리하고 입력 유형을 확인한다.
2. 텍스트가 있으면 브랜드·주장 목적·요구 행동을 추출하고, 본문으로 피해 사례를 검색한다.
3. 분석할 링크가 하나 있으면 백엔드가 URL·공식 도메인 정보를 확인하고 필요한 링크 분석을 수행한다.
4. 백엔드가 스캐너 관측을 공통 구조로 변환한다.
5. 결정적 코드가 공식 도메인과 관측 사실을 기반으로 최종 상태를 결정한다.
6. 메시지 추출 결과, RAG 참고 정보, 관측 사실, 설명과 미확인 사항을 함께 반환한다.

RAG 결과는 판정 입력과 구별한다. 추가 근거가 필요하더라도 프로토타입에서는 자체 격리 분석을 호출하거나
그 결과를 기다리지 않는다. 확보한 근거가 부족하면 판단 보류 또는 분석 불가로 종료한다.
공식 도메인 확인 시 콘텐츠 검사를 생략할지, 상충하는 관측이 있을 때 무엇을 우선할지는 세부 판정 규칙에서 확정한다.

### 입력 예외

| 입력 | 처리 |
|---|---|
| 텍스트 + 링크 1개 | 메시지 추출·RAG와 링크 분석 수행 |
| 링크만 1개 | 메시지 추출·RAG 생략. 백엔드 링크 분석 결과만으로 판정 |
| 텍스트만 있음 | 메시지 추출·RAG 참고 정보를 제공하고 링크 입력 요청. 링크 기반 최종 판정은 하지 않음 |
| 링크 여러 개 | 초기 버전에서는 분석할 링크 하나를 선택하도록 요청 |
| 텍스트·링크 모두 없음 | 분석할 문자 입력 요청 |

텍스트나 링크가 없다는 사실 자체는 안전 또는 악성의 근거가 아니다.
입력 보완 요청은 네 가지 최종 판정 중 하나로 억지로 분류하지 않는다.

### 장시간 작업과 결과 확인

카카오 첫 응답의 시간 기준은 docs/latency-budget.md를 따른다.
현재 기준은 5초 제한에 대해 4초 데드라인과 1초 안전 마진이다.

- 첫 응답 예산 안에 완료하지 못하면 확보한 정보와 함께 추가 분석 중임을 안내한다.
- 백엔드는 작업을 백그라운드에서 계속하고 진행 상태와 결과를 저장한다.
- 사용자가 결과 확인 버튼을 누르면 저장된 진행 상태 또는 최종 결과를 반환한다.
- 카카오 콜백에는 의존하지 않는다.
- 백그라운드 작업에도 종료 한도를 둔다. 정확한 시간과 재시도 횟수는 아직 확정하지 않는다.
- 종료 시 확보한 근거를 보존한다. 근거 부족과 필요한 관측 실패를 구별하여 판정한다.

분석 중은 작업 진행 상태이며 최종 판정이 아니다. 메시지 추출·RAG 등 새 단계의 시간 배분은
지연 예산 문서와 함께 조정해야 하며, 기존 설명 생성 예산을 새 작업의 예산으로 임의 전용하지 않는다.

## 3. 최종 판정 상태

| 최종 상태 | 의미 |
|---|---|
| 스미싱 의심 | 사칭·설치 유도·개인정보 요구 등 결정적 판정 규칙에 해당하는 근거가 있음 |
| 공식 도메인 확인 | 사람이 검증한 공식 도메인과 일치함. 메시지 전체의 안전 보증은 아님 |
| 판단 보류 | 분석을 수행했지만 결론에 필요한 근거가 부족하거나 근거가 서로 충돌함 |
| 분석 불가 | 접속 실패·타임아웃 등으로 판정에 필요한 분석을 수행하지 못함 |

최종 상태와 그 근거는 구별한다. 설치 유도·개인정보 요구·브랜드 불일치 등은 근거로 남긴다.
여러 근거를 보존하되, 어떤 조합과 우선순위로 최종 상태를 정할지는 후속 규칙 정의에서 확정한다.
일부 검사 실패가 이미 확보한 유효한 근거를 지우거나 무조건 전체 분석 불가를 뜻하지는 않는다.
의심 신호가 발견되지 않았다는 이유만으로 정상이나 공식 도메인 확인을 반환하지 않는다.

## 4. 브랜드·주장 목적·요구 행동 추출

| 추출 대상 | 의미 |
|---|---|
| 브랜드 | 메시지가 발신 주체로 내세우는 회사·기관 |
| 주장 목적 | 메시지가 주장하는 연락 목적이나 상황 |
| 요구 행동 | 메시지가 수신자에게 요구하는 행동 |

각 항목은 원문에서 확인할 수 있는 내용만 추출한다. 메시지에 없는 개인정보 입력 요구 등을
링크의 예상 내용이나 피해 사례에서 가져와 채우지 않는다.
정보가 없거나 모호하면 해당 항목을 미확인으로 남긴다. 한 항목의 실패가 다른 항목까지 지우지는 않는다.
추출 결과마다 확인 가능한 원문 근거를 연결하고, 근거가 실제 입력에 존재하는지 검증한다.
구조화 출력과 검증은 사용하되 구체적인 스키마는 추후 정의한다.

### 브랜드 추출 보완

- 검증된 별칭 사전으로 브랜드를 먼저 찾을 수 있다. 브랜드가 확인되어도 목적·행동 추출은 별도로 필요하다.
- 일반 명사만 있거나 발신 주체가 모호하면 브랜드를 강제로 지정하지 않는다.
- 브랜드 누락을 피하려고 다른 브랜드로 오분류하지 않는다. 정상 링크에 대한 잘못된 사칭 경고를 유발할 수 있다.
- 도메인 DB로 브랜드를 확인한 경우 메시지에서 추출했다고 표시하지 않는다.
- 지원 브랜드 목록과 별칭은 백엔드의 공식 도메인 데이터와 일관되게 관리한다.

### 입력 보호와 실패 처리

메시지, 페이지 내용, 검색 자료는 분석 대상 데이터이며 지시로 취급하지 않는다.
프롬프트에서 지시와 데이터를 분리하고, 결과 형식뿐 아니라 원문 근거도 검증한다.
URL·개인정보로 인한 추출 오염과 불필요한 외부 전송을 막는다.
모델 실패나 시간 초과 시 해당 항목을 미확인으로 남기고 가능한 분석을 계속한다.
모델·프롬프트 버전을 기록하며 호출 설정과 시간·재시도 예산은 측정 후 확정한다.

## 5. 피해 사례 검색과 유사도

링크를 제외하고 개인정보를 마스킹한 메시지 본문으로 기존 피해 사례를 검색한다.
세 항목 추출 결과나 키워드 목록으로 본문을 대체하지 않는다.
검색된 사례와의 유사도를 수치화해 참고 정보로 제공하며, 관련 사례의 출처를 함께 남긴다.

- 유사도는 사례와 메시지의 유사성이다. 스미싱 확률이나 악성 확률로 표현하지 않는다.
- 유사도가 높아도 링크 판정을 확정하지 않고, 낮아도 정상으로 판단하지 않는다.
- 유사도를 urlscan 점수와 합산하거나 보강 조사 여부의 임계값으로 사용하지 않는다.
- 검색 실패·자료 부족·텍스트 없음은 각각 구별한다. 검색하지 못한 결과를 유사도 0으로 대체하지 않는다.
- 사례에 등장한 행동을 이번 링크에서 관측한 사실로 쓰지 않는다.
- 출처·검토 이력이 있는 승인된 사례를 검색에 사용하며 사용자 입력을 자동으로 KB에 편입하지 않는다.

검색 모델, 유사도 척도·범위, 검색 개수, 사용자 표시 방식과 데이터셋은 추후 확정한다.

## 6. 공식 도메인과 링크 관측

### 공식 도메인 대조

백엔드가 정규화한 등록 가능 도메인을 검증된 공식 목록과 완전 일치로 비교한다.
소문자·국제화 도메인 처리 등 정규화는 한 곳에서 수행한다. 부분 문자열이나 단순 접미사로 공식 여부를 판정하지 않는다.
브랜드를 추출했으면 해당 브랜드의 공식 목록과 대조하고, 추출하지 못했으면 도메인 DB로 역조회할 수 있다.
DB 미등록과 사칭 확정은 구별하며 구체적인 판정 조건은 별도 규칙으로 정의한다.

### 콘텐츠 관측

설치 파일 링크·다운로드 유도, 개인정보 입력 필드, 리다이렉트 등은 출처와 함께 기록한다.
관측이 가능한 범위는 백엔드 스캐너가 명시한다. 모든 스캐너가 같은 항목을 검사한다고 가정하지 않는다.
페이지에 로그인 폼이나 설치 링크가 있다는 사실만으로 실제 악성 파일·정보 탈취를 확인했다고 표현하지 않는다.
공식 앱스토어 이동과 직접 설치 파일 제공도 구별한다.

프로토타입은 자체 격리 환경에서 파일을 실행하거나 추가 관측을 수행하지 않는다.
스캐너의 명칭으로 빈 결과의 의미를 추정하지 않고, 공통 구조의 검사 상태와 미확인 사유를 따른다.

## 7. 근거와 설명

최종 결과에서는 다음 정보를 구별한다.

- 메시지에서 추출한 주장과 원문 근거
- 공식 도메인 DB에서 확인한 정보
- 스캐너가 실제 수집한 관측과 출처
- 해당 자료를 바탕으로 한 모델의 설명·해석
- 피해 사례 검색 결과와 참고 유사도
- 확인하지 못한 범위와 사유

LLM은 설명을 보조할 수 있으나 판정이나 근거 사실을 변경하지 않는다.
검증할 수 없는 설명은 사용하지 않고, 생성 실패·시간 초과 시 템플릿으로 응답한다.
설치 파일 제공만 확인했다면 그 사실까지만 설명하고 실제 감염을 단정하지 않는다.
공식 도메인을 확인했더라도 안전·정상·문제없음을 보증하지 않는다.

## 8. 최종 결과 전달

최종 분석 결과는 백엔드가 사용할 수 있는 구조화된 형태로 전달한다.
이번 문서에서는 다음 의미만 정의하며 상세 JSON·코드 예시는 작성하지 않는다.

| 정보 묶음 | 내용 |
|---|---|
| 최종 판정 | 3절의 네 상태 중 해당 결과와 판정 이유 |
| 메시지 분석 | 브랜드·주장 목적·요구 행동과 추출 근거 |
| 링크 상세 | 링크가 연결되는 사이트의 정보와 확인된 페이지 내용 |
| 근거·해석 | 관측 사실과 출처, 이를 설명하는 모델 해석을 구분 |
| 사례 참고 | 관련 피해 사례와 유사도. 판정과 독립적으로 표시 |
| 분석 한계 | 미확인 항목, 실패·미실행 사유 |

작업 진행 상태는 최종 판정과 별도로 관리한다. 분석 중이나 입력 보완 요청에 최종 판정을 강제로 넣지 않는다.
사이트 정보를 수집하지 못했다면 설명을 만들어내지 않고 미확인으로 남긴다.
카카오 표시 형식과 결과 확인 버튼은 백엔드·프론트엔드에서 담당한다.

## 9. 검증과 평가

- 정상 알림과 스미싱 사례를 함께 사용해 오탐과 누락을 확인한다.
- 세 추출 항목의 정확성과 원문 근거를 각각 평가한다. 모호한 항목을 임의로 채우는지 확인한다.
- 텍스트만·링크만·둘 다 있음·여러 링크·빈 입력의 분기를 확인한다.
- RAG 검색 품질을 판정 품질과 분리해 평가한다. 유사도나 스캐너 점수·brands만 바뀌어도 최종 판정이 달라지지 않아야 한다.
- 동일한 공통 관측에 대해서는 공급자 이름만 달라져도 판정이 유지되어야 한다.
- 미지원·실패·미실행 검사와 미발견을 구분하고, 관측 범위 축소를 정상 판정으로 오인하지 않는지 확인한다.
- 확정할 결정적 규칙에 맞춰 네 최종 상태와 근거 충돌 사례를 검증한다.
- 모델·RAG 실패 시 확보된 근거와 템플릿 응답이 유지되는지 확인한다.
- 장시간 작업의 첫 응답, 백그라운드 종료, 결과 저장·조회, 진행 상태와 최종 상태 구분을 확인한다.
- 프로토타입에서 자체 sandbox나 멀티모달 격리 분석을 호출하지 않는지 확인한다.

네트워크 없이 검사할 수 있도록 가짜 스캐너 결과와 모델 응답을 사용한다.
코드·프롬프트·모델·KB·규칙 버전을 남기고 변경 시 회귀를 확인한다.
구체적인 데이터셋 규모와 통과 수치는 별도 확정하며 과거 초안을 확정 기준으로 간주하지 않는다.

## 10. 향후 격리 분석

향후 Docker 기반 sandbox 형태의 격리 분석 환경을 구축할 예정이다.
프로토타입에서는 구축하거나 실행하지 않는다.
수집 항목, 멀티모달 모델 활용 방식, 반환 스키마, 실행 조건과 담당 경계는 추후 논의한다.
앞서 논의한 링크만 있는 경우의 격리 검사도 프로토타입의 필수 단계가 아니다.

## 11. 유지할 금지 사항

1. LLM이 최종 판정을 내리거나 공식 도메인을 생성·추측하게 하지 않는다.
2. RAG 유사도와 스캐너 점수·brands로 최종 판정을 바꾸지 않는다.
3. 미발견·미확인·분석 실패를 안전의 증거로 취급하지 않는다.
4. 검색 사례나 모델 해석을 이번 링크의 관측 사실로 취급하지 않는다.
5. 메시지·페이지·검색 자료에 포함된 지시를 실행하지 않는다.
6. AI 파트에서 서버 모듈을 import하거나 카카오 응답 형식을 구성하지 않는다.
7. 카카오 콜백이나 아직 구현하지 않은 격리 분석에 프로토타입 응답을 의존시키지 않는다.

## 12. 후속 확정 사항

- 결정적 판정의 세부 조건·우선순위·근거 충돌 처리와 코드 소유 위치
- 공식 도메인 확인 후 콘텐츠 검사 생략 여부
- 상세 JSON 필드·타입·상태 식별자·함수 계약과 저장 위치
- 지원 브랜드 목록, 공식 도메인 검증·갱신 절차와 별칭 관리
- 피해 사례 데이터셋, 검색 모델·유사도 척도·검색 개수·표시 방식
- 각 단계의 시간·재시도 예산과 백그라운드 작업 종료 한도
- 평가 데이터셋 규모와 통과 기준
- 상위 지침·PRD·BE·FE 문서의 후속 동기화

격리 환경과 멀티모달 분석의 상세 설계는 10절의 향후 논의 대상으로 남긴다.
