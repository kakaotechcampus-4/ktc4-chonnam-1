## 1. 이 문서가 정하는 것

결과 카드가 사용자에게 **"무엇을 확인했다"고 말해도 되는지**를 사례로 고정한다.
판정 규칙은 BE·AI가 정하고, 사용자가 읽는 문장은 FE가 정한다.
두 쪽이 같은 사례를 두고 같은 뜻으로 설명할 수 있어야 카드에 연결할 수 있다.

순서는 멘토 요청대로다.

1. 사례마다 기대 결과와 안내 문구를 먼저 적는다 (4절)
2. 현재 구현에 넣었을 때 나오는 결과와 비교한다 (5절)
3. 차이를 누가 정해야 하는지 나눈다 (6절)

## 2. 전제 — 팀 확인 필요

| 전제 | 근거 |
| --- | --- |
| 서비스 범위는 **"검토된 택배사 공식 주소와 비교하고, 공식 경로에서 다시 확인하도록 돕는 서비스"** 다 | 멘토가 제시한 범위안. `CLAUDE.md` 절대 원칙 1(화이트리스트 대조가 판정 근거)과 같다 |

| 카드는 **결론과 다음 행동을 첫 줄에** 쓰고, 확인한 범위는 그 아래 이유로 쓴다 | PR #39 멘토 리뷰. 진행 상태를 먼저 읽게 하면 사용자가 위험 여부를 다시 판단해야 한다 |

| 공식 주소와 같다는 것만으로 정상이라고 하지 않고, 목록에 없다는 것만으로 위험이라고 하지 않는다 | PR #39 멘토 리뷰 |
| 사례는 가상 브랜드 `누리택배`, 공식 도메인 `nuri-delivery.example`로 쓴다 | [`kakao-chatbot-build-guide.md`](./kakao-chatbot-build-guide.md)의 합성 문자 기준 |

`누리택배`는 AI의 브랜드 허용 목록(`ai/src/ai/types.py` `Brand`)에 없다.
코드로 실행해 검증할 때는 목록에 있는 택배사 이름과 팀 소유 모형 도메인으로 바꾼다.

## 3. 결과를 만드는 사실 다섯 가지

멘토 코멘트(`types.py:281`)대로 아래 사실을 **서로 다른 값**으로 둔다.
사용자 안내 상태(⑤)는 앞의 네 사실에서 정해진다.
반대로, 카드 문장이 말하는 사실은 앞의 네 칸에 값으로 있어야 한다.

| 사실 | 가질 수 있는 값 | 결과 필드 (`scheme.md`) |
| --- | --- | --- |
| ① 공식 주소 대조 | 일치 / 문자 속 택배사의 공식 주소 아님 / 택배사를 모르거나 목록에 없어 비교 못 함 / 도메인을 얻지 못함 | `url.official` = `official` / `brand_mismatch` / `not_registered` / `unresolved`. 대조는 `services/official_domain_service.py`, 목록은 `services/official_domains.py` |
| ② 스캐너 악성 신호 | 원본 점수, 조회 시각 | `url.scan.score` `url.scan.scanned_at`. **판정에 쓰지 않는다** (반영 여부는 6절 11) |
| ③ 페이지 확인 범위 | 확인함 / 열어보지 못함 / 일부만 확인 / 확인하지 않음(미실행) | `env.answer` = `no_risk_found`·`risk_found` / `failed` / `partial` / `not_run` |
| ④ 문자 위험 근거 | 검증된 근거 있음 / 없음 / 분석 못 함 | `message.details.signals`(1개 이상이면 근거 있음), `message.answer` |
| ⑤ 사용자 안내 상태 | 4절의 S1~S5 | 카드 R1~R4. 지금 실제 결과는 카드 대신 `simpleText` 디버그 출력이다 |

`answer`가 `partial`이어도 `signals`가 있으면 검증된 근거가 있다는 뜻이다(`scheme.md` 4절).
카드는 `answer`만 보지 말고 `signals`를 함께 본다.

## 4. 사례별 기대 결과와 안내 문구

### 안내 상태 정의

| 상태 | 조건 (결과 필드 기준) | 카드 |
| --- | --- | --- |
| S1 공식 주소 아님 | `url.official = brand_mismatch`. 검증된 위험 근거(문자·페이지 `signals`)가 있으면 **S1-근거**, 없으면 **S1-목록 외**로 문장을 나눈다 | R1 |
| S2 공식 주소와 같음 | `url.official = official`이고 `message`·`env` 모두 `no_risk_found` (= `result: true`) | R2 |
| S3 공식 주소지만 확인 필요 | `url.official = official`이지만 문자·페이지에 검증된 위험 근거가 있다. 공식 주소에서 다른 곳으로 이동한 경우도 여기다(5절 사례 3a 참고) | **신규 카드 필요** |
| S4 비교하지 못함 | `url.official = not_registered` 또는 `unresolved` | **신규 카드 필요** (R3은 "정보 부족"을 말하므로 맞지 않다) |
| S5 확인을 못 마침 | 시스템 오류로 결과 자체를 만들지 못했다 (urlscan 실패, 45초 초과 등) | R4 |

위험 안내다(2절 전제).

### 사례별 안내 문구와 지켜야 할 것

**사례 1 — S2**

- 결론 줄: `정상 안내로 판단했어요. 배송은 누리택배 공식 홈페이지에서 확인하세요.`
- 이유: `문자 속 주소가 누리택배 공식 주소와 같고, 페이지에서도 다른 점을 찾지 못했어요.`
  `보낸 사람은 확인하지 못했어요.`
- 지킬 것: 결론을 먼저 말하되, 확인 못 한 범위(보낸 사람)를 이유에 남긴다.
  "안전해요"라는 보증 문장은 쓰지 않는다. 결론 줄을 쓸 수 있는 조건은 6절 9에서 정한다.

**사례 2 — S1-근거**

- 결론 줄: `위험한 문자로 판단했어요. 링크를 누르지 마세요.`
- 이유: `문자는 누리택배라고 하지만, 주소는 누리택배 공식 주소가 아니에요.`
  `문자가 주소를 다시 입력하라고 해요.`
- 지킬 것: 주소 불일치와 **문자 속 근거**를 함께 말한다. 문자 근거 문장은
  검증된 신호(`message.details.signals`)가 있을 때만 넣는다.

**사례 3a — S3**

- 결론 줄: `위험한 문자로 판단했어요. 링크를 누르지 마세요.`
- 이유: `문자 속 주소는 누리택배 공식 주소에서 시작하지만, 열어 보니 공식 주소가 아닌 곳으로 이동했어요.`
  `확인할 일은 누리택배 공식 앱에서 하세요.`
- 지킬 것: **도메인 일치만으로 나머지 검사를 생략하지 않는다.**
  도착 주소를 모르면(수집 실패) S2라고 말하지 않는다.
  도착한 의심 주소는 카드에 링크나 미리보기로 보여주지 않는다.

**사례 3b — S1**

- 문구: 사례 2(근거 있음) 또는 사례 4(근거 없음)와 같다.
- 지킬 것: 플랫폼이 정상 서비스라는 이유로 공식 주소처럼 말하지 않는다.
  공유 플랫폼 도메인은 화이트리스트에 도메인 단위로 올리지 않는다(6절 6).

**사례 4 — S1-목록 외**

- 결론 줄: `공식 주소가 아니에요. 문자 속 링크 대신 누리택배 공식 앱에서 확인하세요.`
- 이유: `문자는 누리택배를 말하지만, 이 주소는 누리택배 공식 주소 목록에 없어요.`
  `이 주소만으로는 위험한지 알 수 없어요.`
- 지킬 것: **목록에 없다는 이유만으로 "위험"이나 "사칭"을 말하지 않는다.**
  "누르지 마세요" 대신 공식 경로를 권한다. 사례 2와의 차이는 검증된 근거가 있는지뿐이다.

**사례 5 — S2 조건 미충족**

- 결론 줄: 6절 9 합의 결과를 따른다. 후보는 S4 결론 줄이다.
- 이유: `문자 속 주소가 누리택배 공식 주소와 같아요.`
  `페이지를 열어보려 했지만 열지 못해서, 이 주소가 어디로 이어지는지는 확인하지 못했어요.`
- 지킬 것: 확인한 사실(주소 일치)과 실패한 범위(페이지, 이동 경로)를 함께 보여준다.
  실패를 위험 근거처럼 말하지 않는다(`results.py:24` 코멘트).
  **지금은 페이지 수집기가 없어 공식 주소인 문자는 모두 이 사례가 된다(5절).**

## 5. 현재 구현과 비교

### 비교 방법

- 기준: `develop` `654fddc` (2026-09-30, PR #31~#38 병합 후)
- 루트 `main.py`의 `kakao_skill()` → `run_analysis()` → `build_ai_url_analysis()` → `finalize_analysis()` 흐름을 코드로 추적했다.
- AI 결과 조립은 **실제 실행**했다. `url.official` 네 값 각각에 대해 BE와 같은 인자
  (`page=None`, `failure=missing_result`)로 `finalize_analysis()`를 불렀다.
- urlscan과 LLM은 호출하지 않았다. 그래서 문자 분석 결과(`message`)와 실제 도착 도메인은 코드로만 추적했다.

### 현재 흐름 요약

```
링크 없음
  → "URL을 찾을 수 없습니다" 텍스트 (R6 카드 아님)

urlscan 요청 실패·시간 초과 (main.py:264-302)
  → AI 결과 없이 "⚠️ 검사 시간 초과: <입력 URL>" 텍스트
  → 이미 시작한 문자 분석 결과는 버려진다

urlscan 성공
  → url.official = 문자 분석이 찾은 택배사 + urlscan 도착 도메인 대조 (main.py:565)
  → finalize_analysis(page=None, failure=missing_result)
  → env.answer = failed   (수집기를 연결하지 않았는데 '실패'로 기록. scheme.md 4절로는 not_run)
  → result = false        (항상)
  → format_ai_result() 텍스트 (카드 아님)
```

실행 결과:

| `url.official` | `result` | `env.answer` |
| --- | --- | --- |
| `official` | `false` | `failed` |
| `brand_mismatch` | `false` | `failed` |
| `not_registered` | `false` | `failed` |
| `unresolved` | `false` | `failed` |
| (참고) `failure`를 넘기지 않으면 | — | `not_run` |

### 사례별 비교

| # | 기대 | 현재 | 차이 |
| --- | --- | --- | --- |
| 1 | S2 | `official`, `env=failed`, `result=false` | 정상 문자도 S2가 될 수 없다. 수집기가 없어서다 |
| 2 | S1-근거 | `brand_mismatch` + 문자 `signals` (LLM이 근거를 내고 검증을 통과하면) | **값은 다 있다.** 카드에 연결하는 일만 남았다 |
| 3a | S3 | BE가 **도착 도메인**만 대조하므로 `brand_mismatch` | 위험 근거가 없으면 S1-목록 외로 보인다. "공식 주소에서 시작했다"는 사실은 결과에 없다 |
| 3b | S1 | 브랜드가 목록에 있으면 `brand_mismatch` | 기대와 같다 |
| 4 | S1-목록 외 | `brand_mismatch`, 문자 `signals` 없음 | 기대와 같다. 사례 2와는 `signals` 유무로 구분한다 |
| 5 | S2 조건 미충족 | `official`, `env=failed` | 미실행이 "열어보지 못함"으로 기록된다. `not_run`이면 "확인하지 않음"으로 정확히 쓸 수 있다 |

**좋아진 점:** "미확인"과 "불일치"를 이제 다른 값으로 받는다(`url.official` 4값, `answer` 5값).
공식 주소여도 문자 근거가 결과에 남는다.

**남은 차이:** 페이지 미실행이 `failed`로 기록된다 · urlscan이 실패하면 문자 근거를 버린다 ·
결과가 카드가 아니라 텍스트다 · 처음 주소를 대조하지 않아 이동 경로를 알 수 없다.

| 4 | 공식 주소일 때 문자 근거 처리 (`results.py:187`) | AI·FE | **해결**. BE가 `official`과 관계없이 문자 결과를 넘긴다(PR #39). 근거가 있으면 S3 |

## 7. 한계

- 합성 사례는 **조건 분기 검증용**이다. 실제 스미싱의 오탐·누락은 출처와 기대 결과를 사람이 검토한 실제 문자 사례로 따로 평가한다.
- 4절 문구의 글자수는 파이썬 `len()`으로 셌다. 결론 줄과 이유를 합친 본문은 최대 85자(사례 1)다.
  사례 5에 S4 결론 줄을 붙이면 약 110자다. 모두 basicCard 본문 한도(230자) 안이다.
  카카오톡 실기기 표시는 아직 확인하지 않았다.
- 신규 카드(S3, S4)와 R1의 두 변형은 관리자센터·BE 템플릿에 아직 없다.
- 5절 실행은 AI 결과 조립만 돌렸다. urlscan·LLM을 거친 실제 문자 분석 결과는 확인하지 않았다.
