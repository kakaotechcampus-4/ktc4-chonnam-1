## 1. 이 문서가 정하는 것

결과 카드가 사용자에게 **"무엇을 확인했다"고 말해도 되는지**를 사례로 고정한다.
판정 규칙은 BE·AI가 정하고, 사용자가 읽는 문장은 FE가 정한다.
두 쪽이 같은 사례를 두고 같은 뜻으로 설명할 수 있어야 카드에 연결할 수 있다.

순서는 멘토 요청대로다.

1. 사례마다 기대 결과와 안내 문구를 먼저 적는다 (4절)
2. 현재 구현에 넣었을 때 나오는 결과와 비교한다 (5절)
3. 차이를 누가 정해야 하는지 나눈다 (6절)

## 2. 전제 — 팀 확인 필요

| 전제 | 근거 |
| --- | --- |
| 서비스 범위는 **"검토된 택배사 공식 주소와 비교하고, 공식 경로에서 다시 확인하도록 돕는 서비스"** 다 | 멘토가 제시한 범위안. `CLAUDE.md` 절대 원칙 1(화이트리스트 대조가 판정 근거)과 같다 |
| 카드의 "공식 주소와 같아요 / 달라요"는 **화이트리스트 대조 결과에만** 연결한다 | 같은 문장을 스캐너 점수로 만들면 확인하지 않은 사실을 말하게 된다 |
| 사례는 가상 브랜드 `누리택배`, 공식 도메인 `nuri-delivery.example`로 쓴다 | [`kakao-chatbot-build-guide.md`](./kakao-chatbot-build-guide.md)의 합성 문자 기준 |

`누리택배`는 AI의 브랜드 허용 목록(`ai/src/ai/types.py` `Brand`)에 없다.
코드로 실행해 검증할 때는 목록에 있는 택배사 이름과 팀 소유 모형 도메인으로 바꾼다.

## 3. 결과를 만드는 사실 네 가지

멘토 코멘트(`types.py:281`)대로 아래 넷을 **서로 다른 값**으로 둔다.
사용자 안내 상태는 앞의 세 사실에서 정해진다.
반대로, 카드 문장이 말하는 사실은 앞의 세 칸에 값으로 있어야 한다.

| 사실 | 가질 수 있는 값 | 지금 코드의 상태 |
| --- | --- | --- |
| ① 공식 주소 대조 | 일치 / 문자 속 택배사의 공식 주소 아님 / 택배사를 특정 못 해 비교 못 함 | `DomainMatch`(`ai/src/ai/types.py`)가 있으나 현재 BE 흐름에서 쓰지 않는다. `backend/src/server/data/whitelist.yaml`의 도메인 목록은 5개 택배사 모두 비어 있다 |
| ② 스캐너 악성 신호 | 원본 점수, 조회 시각, 조회 실패 | urlscan `score`를 `official` boolean으로 바꾸면서 원본이 결과 계약에서 빠진다 |
| ③ 페이지 확인 범위 | 확인함 / 열어보지 못함 / 일부만 확인 / 확인하지 않음(미실행) | 수집기를 연결하지 않았는데 항상 `COLLECTION_FAILED`(수집 실패)로 넘긴다 |
| ④ 사용자 안내 상태 | 4절의 S1~S5 | 카드 R1~R4. 지금 실제 결과는 카드 대신 `simpleText` 디버그 출력이다 |

## 4. 사례별 기대 결과와 안내 문구

### 안내 상태 정의

| 상태 | 조건 (①·③ 기준) | 카드 |
| --- | --- | --- |
| S1 공식 주소 아님 | 문자가 택배사를 밝혔고, 주소가 그 택배사 공식 목록에 없다 | R1. 검증된 위험 근거가 있으면 **S1-근거**, 없으면 **S1-목록 외**로 문장을 나눈다 |
| S2 공식 주소와 같음 | 처음 주소와 도착 주소가 모두 공식 목록에 있고, 확인한 범위에서 위험 근거가 없다 | R2 |
| S3 공식 주소지만 확인 필요 | 공식 주소에서 출발했지만 다른 곳으로 이동했거나, 페이지·문자에서 검증된 위험 근거가 있다 | **신규 카드 필요** |
| S4 비교하지 못함 | 문자에서 택배사를 특정하지 못했다 | **신규 카드 필요** (R3은 "주소 없음"을 말하므로 맞지 않다) |
| S5 확인을 못 마침 | 시스템 오류로 대조 자체를 못 했다 | R4 |

모든 상태의 카드에 ③ 페이지 확인 범위를 한 줄로 붙인다.
네 값은 서로 다른 문장을 쓴다.

| ③ 값 | 카드 문장 |
| --- | --- |
| 확인함 | `페이지에서도 다른 점을 찾지 못했어요.` (위험 근거가 없을 때) |
| 열어보지 못함 | `페이지를 열어보려 했지만 열지 못했어요.` |
| 일부만 확인 | `페이지는 일부만 확인했어요.` |
| 확인하지 않음 | `페이지 내용은 확인하지 않았어요.` |

### 사례별 안내 문구와 지켜야 할 것

**사례 1 — S2**

- 제목: `🔍 공식 주소와 같아요`
- 본문: `문자 속 주소가 누리택배 공식 주소와 같아요. 페이지에서도 다른 점을 찾지 못했어요.`
  `보낸 사람은 확인하지 못했어요. 안전하다는 뜻은 아니니, 확인할 일은 누리택배 공식 앱에서 하세요.`
- 지킬 것: 확인한 범위(주소, 페이지)와 확인 못 한 범위(보낸 사람)를 같이 말한다.
  "안전해요"로 읽히는 문장을 쓰지 않는다.

**사례 2 — S1-근거**

- 제목: `⚠️ 공식 주소와 달라요`
- 본문: `문자는 누리택배라고 하지만, 주소는 누리택배 공식 주소가 아니에요.`
  `문자가 주소를 다시 입력하라고 해요. 이 링크는 누르지 마세요.`
- 지킬 것: 주소 불일치와 **문자 속 근거**를 함께 말한다. 문자 근거 문장은
  AI가 검증한 인용(`message.details`)이 있을 때만 넣는다.

**사례 3a — S3**

- 제목: `⚠️ 공식 주소에서 다른 곳으로 이어져요`
- 본문: `문자 속 주소는 누리택배 공식 주소에서 시작하지만, 열어 보니 공식 주소가 아닌 곳으로 이동했어요.`
  `이 링크는 누르지 마세요. 확인할 일은 누리택배 공식 앱에서 하세요.`
- 지킬 것: **도메인 일치만으로 나머지 검사를 생략하지 않는다.**
  도착 주소를 모르면(수집 실패) S2라고 말하지 않고 사례 5처럼 "열어보지 못함"을 붙인다.
  도착한 의심 주소는 카드에 링크나 미리보기로 보여주지 않는다.

**사례 3b — S1**

- 문구: 사례 2(근거 있음) 또는 사례 4(근거 없음)와 같다.
- 지킬 것: 플랫폼이 정상 서비스라는 이유로 공식 주소처럼 말하지 않는다.
  공유 플랫폼 도메인은 화이트리스트에 도메인 단위로 올리지 않는다(6절 합의 항목).

**사례 4 — S1-목록 외**

- 제목: `🔎 공식 주소 목록에 없어요`
- 본문: `문자는 누리택배를 말하지만, 이 주소는 누리택배 공식 주소 목록에 없어요.`
  `이 주소만으로는 위험한지 알 수 없어요. 문자 속 링크 말고 누리택배 공식 앱에서 확인하세요.`
- 지킬 것: **목록에 없다는 이유만으로 "위험"이나 "사칭"을 말하지 않는다.**
  "누르지 마세요" 대신 공식 경로를 권한다. 사례 2와의 차이는 검증된 근거가 있는지뿐이다.

**사례 5 — S2 + 열어보지 못함**

- 제목: `🔍 공식 주소와 같아요`
- 본문: `문자 속 주소가 누리택배 공식 주소와 같아요.`
  `페이지를 열어보려 했지만 열지 못해서, 이 주소가 어디로 이어지는지는 확인하지 못했어요. 확인할 일은 누리택배 공식 앱에서 하세요.`
- 지킬 것: 확인한 사실(주소 일치)과 실패한 범위(페이지, 이동 경로)를 함께 보여준다.
  실패를 위험 근거처럼 말하지 않는다(`results.py:24` 코멘트).

## 5. 현재 구현과 비교

### 비교 방법

- 기준: `refactor/scenario-message-test` (`dee85cb`, `develop`과 같음)
- `main.py`의 `run_analysis()` → `build_ai_url_analysis()` → `finalize_analysis()` 흐름을 코드로 추적했다.
- AI 결과 조립은 합성 입력으로 **실제 실행**했다. `score ≤ 0` 가정과 `score > 0` 가정, 각 1건이다.
- urlscan과 Gemini는 호출하지 않았다. 그래서 **각 사례의 실제 urlscan 점수는 모른다.** 표는 점수에 따라 두 갈래로 적었다.

### 현재 흐름 요약

```
urlscan score ≤ 0 (TEST_SCORE_THRESHOLD)
  → official=true → result=true
  → message·env 10개 값 전부 null (문자에서 찾은 근거도 버려짐)

urlscan score > 0
  → official=false → result=false
  → env.reason = "페이지 접속·수집에 실패하여 … 의심으로 처리했습니다."
    (수집기를 연결하지 않아 시도조차 안 했는데 '실패'로 기록됨)

urlscan 요청 실패·시간 초과
  → AI 호출 없이 "⚠️ 검사 시간 초과: <입력 URL>" 텍스트
```

실행 결과(요약) — 문자 근거 `'주소를 다시 입력하세요'`를 넣었을 때:

| 가정 | `result` | `message.details.reason` | `env.details.reason` |
| --- | --- | --- | --- |
| `score ≤ 0` | `true` | `null` | `null` |
| `score > 0` | `false` | `문자에서 '주소를 다시 입력하세요'라고 안내했습니다.` | `페이지 접속·수집에 실패하여 내용을 확인하지 못했으므로 의심으로 처리했습니다. 분석할 자료 또는 결과를 확보하지 못해 의심으로 처리했습니다.` |

### 사례별 비교

`kakao-fe-be-integration.md` 2절대로 `result=true`를 R2에 연결했다고 가정한다.

| # | 기대 | 현재 (`score ≤ 0`) | 현재 (`score > 0`) | 차이 |
| --- | --- | --- | --- | --- |
| 1 | S2 | true → R2 "공식 주소와 같아요" | false, "수집 실패로 의심" | 겉보기 결과는 맞을 수 있다. 하지만 true는 **공식 주소를 대조한 결과가 아니라 스캐너가 악성으로 보지 않았다는 뜻**이다 |
| 2 | S1-근거 | true → R2 "공식 주소와 같아요", **문자 근거 버려짐** | false, 문자 근거 유지 | 새로 만든 사칭 도메인이 점수 0 이하로 나오면 **잘못된 안심**을 준다 |
| 3a | S3 | 도착 페이지 점수에 따라 true → R2 | false | 출발 주소가 공식인지, 이동했는지를 표현할 값이 없다 |
| 3b | S1 | 플랫폼 페이지 점수에 따라 true → R2 | false | 정상 플랫폼 페이지가 "공식 주소와 같아요"로 표시될 수 있다 |
| 4 | S1-목록 외 | true → R2 "공식 주소와 같아요" | false, "수집 실패로 의심" | 공식이 아닌 주소를 공식이라고 말하거나, 반대로 실패를 의심 근거처럼 말한다 |
| 5 | S2 + 열어보지 못함 | true, 수집 결과를 넣을 자리 없음 | false, 미연결을 "실패"로 기록 | "확인함 / 열어보지 못함 / 일부 / 미실행"을 구분할 수 없다 |

**공통 차이:** 지금 계약에서는 "미확인"과 "불일치"가 모두 `false`다.
카드는 두 경우를 다른 문장으로 말해야 하는데, 받는 값으로는 구분할 수 없다.

## 6. 합의가 필요한 것

| # | 항목 | 담당 | FE 요청 |
| --- | --- | --- | --- |
| 1 | `official`의 뜻: 스캐너 점수와 공식 주소 대조를 **다른 필드로 분리** | BE·AI | 카드의 "공식 주소와 같아요 / 달라요"는 대조 결과 필드에만 연결한다 |
| 2 | 화이트리스트 도메인 채우기 | BE | 목록이 빌 동안 S1·S2 문구는 쓸 수 없다 |

| 4 | 공식 주소일 때 문자 근거 처리 (`results.py:187`) | AI·FE | 버리지 말고 S3 판단이나 카드 근거 줄에 쓴다. 판정을 뒤집을지는 AI·BE가 정한다 |
| 5 | 이동 경로(처음 주소 ≠ 도착 주소) 표시 | BE·AI | S3의 조건이다. 처음 주소와 도착 주소를 모두 받아야 한다 |
| 6 | 공유 플랫폼 도메인 등록 규칙 | BE | 여러 사람이 글을 올리는 플랫폼은 도메인 단위로 목록에 올리지 않는다 |
| 7 | 공식 도메인 즉답(`chatbot-copy.md` D2) 재검토 | FE | 즉답은 이동 경로와 페이지를 보기 전이다. 사례 3a·5와 충돌한다. 즉답을 없애거나, 즉답에 "이어지는 주소와 페이지는 확인 중"을 넣고 콜백으로 마무리하는 안 중에서 정한다 |
| 8 | AI `reason` 문장을 카드에 옮길지 | FE | 실패 사유 문장("…의심으로 처리했습니다")은 카드에 옮기지 않는다. 3절 ③의 확인 범위 문장으로 바꾼다 |

## 7. 한계

- 합성 사례는 **조건 분기 검증용**이다. 실제 스미싱의 오탐·누락은 출처와 기대 결과를 사람이 검토한 실제 문자 사례로 따로 평가한다.
- 4절 문구의 글자수는 파이썬 `len()`으로 셌다. 제목은 최대 22자, 본문은 최대 103자로
  basicCard 한도(제목 50자, 본문 230자) 안이다. 카카오톡 실기기 표시는 아직 확인하지 않았다.
- 신규 카드(S3, S4)와 R1의 두 변형은 관리자센터·BE 템플릿에 아직 없다.
