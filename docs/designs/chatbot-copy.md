# 챗봇 화면별 문구

- 작성일: 2026-09-22
- 상태: **작성 완료, 사용자 테스트 미실행**
- 기준 문서: `docs/designs/chatbot-flow.md` (확정 흐름 — 이 문서는 그 흐름을 수정하지 않는다)
- 제약 근거: `docs/designs/kakao-chatbot-build-guide.md` 7절 (글자수), `docs/latency-budget.md`
- 결정 근거: [ADR 0003](../adr/0003-kakao-callback.md) (콜백 채택), [ADR 0005](../adr/0005-no-detail-web.md) (상세 웹 없음)
- 연동 근거: `docs/designs/kakao-fe-be-integration.md` (BE 전달 JSON과 카드의 관계)
- 규칙 근거: `docs/designs/smishing-message-intake-ux.md` 3절 (참고 정보 표시 규칙)

`chatbot-flow.md`는 **왜 이 문구인가**의 결정 기록이고, 이 문서는 **실제로 화면에 나가는 글자**다.
문구는 자주 바뀌므로 분리했다. 흐름을 바꾸는 결정은 이 문서가 아니라 `chatbot-flow.md`에서 한다.

## 1. 이번에 반영한 시나리오 결정

1차 시나리오와 엣지케이스를 확정 흐름에 얹으면서 정한 것들이다.

| # | 결정 | 근거 |
| --- | --- | --- |
| D1 | **대기 안내를 쓴다(R5).** 첫 응답은 5초 안에 나가고 최종 결과는 콜백으로 전달한다 | [ADR 0003](../adr/0003-kakao-callback.md) 채택. urlscan 실측 약 30초라 5초 안에 최종 결과를 낼 수 없다 |
| D2 | **공식 도메인이 일치하면 대기 안내 없이 즉답한다.** R5를 거치지 않고 바로 R2 | `latency-budget.md` "공식 도메인 즉답(<1초)". 느린 경로는 애매한 경우에만 탄다 |
| D3 | **엣지 1(`배고파`)과 엣지 2(아무 말)의 화면을 하나로 합친다(E1)** | `kakao-chatbot-build-guide.md` 2절 — 붙여넣은 문자도 `배고파`도 **둘 다 폴백 블록**으로 간다. 카카오 ML은 이 둘을 가르지 못한다 |
| D4 | 판단 기준을 "스미싱 관련 발화인가"가 아니라 **"문자 본문의 형태인가"**로 둔다 | 길이·줄바꿈·URL/전화번호 유무로 결정적 구분이 된다. ML도 AI 키워드 분류도 필요 없다 |
| D5 | **링크 없는 문자(엣지 3)에 "스미싱 추정"을 말하지 않는다.** R6로 보낸다 | `smishing-message-intake-ux.md` 3절 어휘 차단 규칙. 관측 0건인 상태에서 판정으로 읽히는 문장을 내보내지 않는다 |
| D6 | **링크만 온 경우(엣지 4)는 본문을 더 요구하지 않고 바로 판정한다** | 화이트리스트 대조에 본문이 필요 없다. 결과를 줄 수 있는데 사용자를 한 번 더 돌리지 않는다 |
| D7 | **주소가 여러 개면 R7로 안내한다.** 다중 주소 확인은 1차 범위 밖 | 첫 주소만 검사하면 확인 안 한 주소가 위험할 때 **잘못된 안심**을 준다(테스트 탈락 기준 "안전하다고 오해한 횟수 0"에 직접 걸림) |
| D8 | **대응 매뉴얼은 R1 카드 본문에 넣지 않는다.** 캐러셀 `지금 할 일`과 `신고·상담 받기` 블록에 둔다 | 230자 제약, 그리고 "한 문장에 한 행동" 규칙 |
| D9 | **전화번호는 관측 대상으로 승격하지 않는다** | 택배사 공식 번호는 지점·대리점까지 있어 화이트리스트가 완결되지 않고, 불완전한 화이트리스트는 오탐을 만든다 |

## 2. 구체화한 흐름

```
[웰컴 블록 W1]  ← 채널 최초 1회만
  [동의하고 시작]              → B1
  [내 문자는 어떻게 쓰이나요]     → W2

[개인정보 안내 W2]
  [동의하고 시작]              → B1
  [다음에 할게요]              → W1

[봇 리스트 메뉴]  ← 상시
  [문자 확인하기] → B1   [신고·상담 받기] → B3   [내 문자는 어떻게 쓰이나요] → W2

[문자 확인하기 B1]
  [문자 복사하는 법]           → B2
[복사 안내 B2]
  [돌아가기]                  → B1

[신고·상담 받기 B3]
  [전화 상담] [챗봇 상담] [채팅 상담]

── 사용자가 무언가를 입력 (전부 폴백 블록 → 스킬 서버) ──
                    │
          BE: 문자 본문의 형태인가?  ← D3·D4
                    │
        ┌───────────┴───────────┐
       아니오                    예
        │                        │
       E1                  URL 개수 확인
                                 │
              ┌──────────┬───────┴───────┐
            0개        2개 이상         1개
              │          │              │
             R6         R7       화이트리스트 대조 (<1초)
                                         │
                            ┌────────────┴────────────┐
                        일치 (즉답)                  불일치·미확인
                            │                            │
                           R2                    R5 분석 중 (첫 응답)
                                                         │
                                            urlscan·격리 (~35초, 상한 60초)
                                                         │
                                                    콜백으로 최종 결과
                                                         │
                                        ┌────────┬───────┼────────┐
                                     다름     못 찾음  정보 부족  실패
                                      R1        R2       R3       R4

R1 [신고·상담 받기] [자세히 보기]      R2 [공식 앱 열기] [자세히 보기]
R3 [다시 보내기]   [자세히 보기]      R4 [다시 해보기] [처음으로]
R5 [결과 확인](후속 작업)                R6 [공식 앱 열기] / [주소 추가로 보내기]
R7 [다시 보내기]
E1 [문자 확인하기] / [문자 복사하는 법]

[자세히 보기] — 캐러셀 3장 (R1·R2·R3에서 진입, 상태별 본문 차이)
  C1 확인한 것 → C2 확인 못 한 것 → C3 지금 할 일
  → 3장 모두에 같은 행동 버튼을 단다
```

**링크만 온 경우(엣지 4)는 별도 분기가 아니다.** URL 1개 경로를 그대로 타고 R1~R4로 간다(D6).
결과 카드 아래에 `문자 본문도 보내기`를 선택 버튼으로 둘 수 있으나 필수가 아니다.

**폴백 블록에서도 카드형 응답이 된다(확인 완료).** `kakao-chatbot-build-guide.md` 2절은
공식 문서 기준으로 "확인 못 함"이라고 적고 있으나, 실제 채널에서 되는 것을 확인했다.
따라서 E1·R1~R7 전부를 이미지·버튼이 있는 카드로 낼 수 있고,
폴백을 텍스트로만 받고 다시 블록으로 넘기는 우회 경로는 필요 없다.

## 3. 화면별 문구

글자수는 스크립트로 셌다. 한도는 `kakao-chatbot-build-guide.md` 7절
(제목 50자 / basicCard 본문 230자 / 버튼 14자·가로 2개면 8자).
**이모지는 카드 제목과 본문에만 쓰고 버튼에는 쓰지 않는다.** R1은 `⚠️` 하나만 쓴다.

| 제목 | `📩 클릭 전에 먼저 확인하세요` (16자) |

| 버튼 | `신고·상담 받기`(8) / `자세히 보기`(6) — 가로 |

### R2 다른 점을 못 찾음

| | |
| --- | --- |
| 제목 | `🔍 다른 점을 못 찾았어요` (14자) |
| 본문 | `문자에 있는 주소를 공식 홈페이지 주소와 비교했는데 다른 점을 찾지 못했어요.`<br>`다만 안전하다는 뜻은 아니에요. 확인할 일이 있다면 문자 속 링크 말고 공식 앱에서 직접 확인하세요.` (101자) |
| 버튼 | `공식 앱 열기`(7) / `자세히 보기`(6) — 가로 |

`안전하다는 뜻은 아니에요`는 첫 카드와 캐러셀 C2에 **모두** 넣는다(프로토타입 문서의 확정 사항).

### R3 확인할 정보가 부족함

| | |
| --- | --- |
| 제목 | `🧐 확인할 정보가 부족해요` (14자) |
| 본문 | `보내주신 내용만으로는 주소를 확인하기 어려웠어요.`<br>`문자를 자르지 말고 전체를 그대로 다시 보내주세요.` (57자) |
| 버튼 | `다시 보내기`(6) / `자세히 보기`(6) — 가로 |

### R4 확인을 못 마침

| | |
| --- | --- |
| 제목 | `🙏 지금은 확인을 못 마쳤어요` (16자) |
| 본문 | `확인을 끝내지 못했어요. 위험한지 아닌지 아직 알 수 없어요.`<br>`잠시 뒤에 문자를 그대로 다시 보내주세요.` (59자) |
| 버튼 | `다시 해보기`(6) / `처음으로`(4) — 가로 |

⚠️ **관리자센터 원본의 `보내주신 문자에는 문제가 없어요`를 쓰지 않는다.**
`kakao-fe-be-integration.md` 3절이 지적한 대로, 분석 실패 상황에서 **안전 보증처럼 읽힌다.**
위 문구는 "확인을 못 했다"와 "그래서 아직 모른다"를 함께 말해 그 오독을 막는다.
관리자센터 원본과 BE 전달본을 이 문구로 통일해야 한다.

R3과 R4를 나누는 이유는 **사용자가 할 일이 다르기 때문**이다.
R3은 "보낸 것에 확인할 게 없다"(사용자 조치 필요), R4는 "우리 쪽이 못 했다"(그대로 재시도).
문구에서 내부 상태 이름(`판단 보류` `처리 실패`)은 쓰지 않고 원인만 다르게 쓴다.

### R5 분석 중 (첫 응답)

| | |
| --- | --- |
| 제목 | `⏳ 확인하고 있어요` (10자) |
| 본문 | `문자에 있는 주소를 확인하고 있어요. 최대 1분쯤 걸릴 수 있어요.`<br>`결과가 나오면 바로 알려드릴게요. 그동안 문자 속 링크는 누르지 마세요.` (79자) |
| 버튼 | `결과 확인`(5) — **후속 작업. 구현 전에는 버튼 없이 안내만 낸다** |

공식 도메인이 일치하면 이 화면을 거치지 않고 바로 R2로 간다(D2).
`그동안 문자 속 링크는 누르지 마세요`가 이 화면의 핵심이다 — 대기 시간이 최대 1분이라,
기다리는 동안 사용자가 링크를 눌러버리는 것이 가장 큰 위험이다.

`[결과 확인]` 버튼과 결과 저장·재조회는 [ADR 0005](../adr/0005-no-detail-web.md)에 따라
후속 작업이다. **구현 전에는 콜백이 실패하면 사용자가 결과를 다시 볼 경로가 없다.**

### R6 확인할 주소 없음 (엣지 3)

| | |
| --- | --- |
| 제목 | `📭 확인할 주소가 없어요` (13자) |
| 본문 | `문자에서 확인할 인터넷 주소를 찾지 못했어요.`<br>`지금은 주소가 있어야 확인할 수 있어요. 문자에 주소가 있는데 빠졌다면 그 부분을 더 보내주세요.` (81자) |
| 버튼 | `공식 앱 열기`(7) / `주소 추가로 보내기`(10) — **세로 배치** |

**"스미싱으로 보여요" 같은 문장을 쓰지 않는다(D5).** 관측이 0건이라 방어할 근거가 없다.
AI 유형 참고 칸을 쓸 경우 `smishing-message-intake-ux.md` 3절의 네 가지 제약
(어휘 차단 / 상태 불변 / 없으면 안 그림 / 형식 서술만)을 그대로 적용한다.

### R7 주소가 여러 개

| | |
| --- | --- |
| 제목 | `🔗 주소가 여러 개예요` (12자) |
| 본문 | `지금은 주소가 1개일 때만 확인할 수 있어요.`<br>`확인하고 싶은 주소 1개만 남겨서 다시 보내주세요.` (55자) |
| 버튼 | `다시 보내기`(6) |

범위 제한이 원인이라는 것을 문장에서 드러낸다. "내 문자가 이상한가"로 읽히면 안 된다.
다중 주소를 구현하면 이 화면만 지우면 된다.
카드는 이미 관리자센터에 있으나 `kakao-fe-be-integration.md` 2절 기준으로
**BE 전달 JSON 범위에는 아직 포함되지 않았다.**

### E1 문자 형태가 아닌 입력 (엣지 1 + 엣지 2 통합)

| | |
| --- | --- |
| 제목 | `💬 문자를 붙여넣어 주세요` (14자) |
| 본문 | `저는 택배 문자에 있는 주소가 공식 주소와 같은지 확인해 드려요.`<br>`확인할 문자를 복사해서 그대로 붙여넣어 주세요.` (64자) |
| 버튼 | `문자 확인하기`(7) / `문자 복사하는 법`(9) — **세로 배치** |

`배고파`(엣지 1)와 붙여넣기 실패(엣지 2)가 같은 화면을 받는다(D3).
**"이해하지 못했어요" 같은 실패 문장을 쓰지 않는다** — 뭘 하면 되는지만 말한다.
사용자를 탓하지 않으므로 두 경우 모두에 자연스럽다.

## 4. 자세히 보기 캐러셀 3장

순서는 `확인한 것 → 확인 못 한 것 → 지금 할 일`이다.
**3장 모두에 같은 행동 버튼**을 단다(R1은 `신고·상담 받기`, R2는 `공식 앱 열기`, R3은 `다시 보내기`).
어디서 멈춰도 다음 행동이 보인다.

캐러셀 본문은 **128자 안**으로 맞췄다. `textCard` 캐러셀 한도가 128자이고
`basicCard` 캐러셀이면 230자라, 어느 타입으로 만들어도 통과한다.

### C1 확인한 것

제목 `✅ 확인한 것` (7자)

| 상태 | 본문 | 글자수 |
| --- | --- | --- |
| R1 | `문자에 있던 주소 1개를 공식 홈페이지 주소와 비교했어요. 주소가 공식 주소와 달랐어요.` | 49 |
| R2 | `문자에 있던 주소 1개를 공식 홈페이지 주소와 비교했어요. 다른 점은 찾지 못했어요.` | 47 |
| R3 | `문자에 있던 주소를 공식 홈페이지 주소와 비교하려 했지만, 주소를 확인하지 못했어요.` | 47 |

### C2 확인 못 한 것

제목 `❓ 확인 못 한 것` (10자) — 세 상태 공통

`그래서 '문제없음'이 '안전함'을 뜻하지는 않아요.`

### C3 지금 할 일

제목 `👉 지금 할 일` (8자)

| 상태 | 본문 | 글자수 |
| --- | --- | --- |
| R1 | `이 링크를 누르지 마세요. 확인할 일이 있으면 공식 앱을 직접 열어서 보세요.`<br>`이미 눌렀다면 아래에서 상담받으세요.` | 65 |

## 5. 필요한 이미지

`kakao-fe-be-integration.md` 2절 기준으로 R1~R4·R6·R7 카드는 이미 관리자센터에 있다.
**없는 것은 R5 하나뿐이고, 콜백 채택(D1)으로 R5가 필요해졌다.**

| 화면 | 이미지 | 나타낼 상태 |
| --- | --- | --- |
| R1 | 있음 | 주소가 공식과 다름 |
| R2 | 있음 | 비교했으나 차이 없음 — **안전 표시로 읽히면 안 됨** |
| R3 | 있음 | 확인할 정보 부족 |
| R4 | 있음 | 확인을 마치지 못함 |
| R6 | 있음 | 확인할 주소 없음 |
| R7 | 있음 (BE 전달 범위 밖) | 주소가 여러 개 |
| **R5** | **제작 필요** | **분석 중 — 결과가 아님이 드러나야 함** |

- 규격: 800×400 (2:1), 500KB 이하. 기존 프로토타입과 동일.
- 원본 위치: `kakao-templates/assets/prototype/`
- **R5 이미지는 결과 카드 6장과 시각적으로 구분되어야 한다.** 결과처럼 보이면 사용자가 대기 중인 화면을 결론으로 읽는다.
- 브랜드·URL·동적 문구는 이미지에 넣지 않는다. 상태만 나타낸다.
- 캐러셀 이미지는 **전부 1:1 또는 전부 2:1로 통일**해야 한다(build-guide 7절).

## 6. 이모지 정책

| 규칙 | 이유 |
| --- | --- |
| 카드 제목에 1개, 본문에 최대 1개 | 더 넣으면 안내문이 장식으로 읽힌다 |
| **버튼에는 쓰지 않는다** | 버튼 8자(가로 2개) 한도를 이모지가 잡아먹어 가로 배치가 깨진다 |
| **R1은 `⚠️` 하나만** | 위험 결과에 다른 이모지가 붙으면 심각도가 희석된다 |
| 실패·거절 화면(R3·R4·R6·R7·E1)은 사용자를 탓하지 않는 이모지 | `❌` `🚫`는 사용자 잘못으로 읽힌다 |

글자수는 파이썬 `len()` 기준으로 셌다. 카카오가 이모지를 2자로 세는지는 확인하지 못했다.
가장 긴 제목이 18자(B1)라 50자 한도에는 여유가 충분하다.

## 8. 검토받고 싶은 것

1. D3(엣지 1·2 통합)이 맞는가. 폴백이 핵심 경로인 이상 다른 방법이 있는가
2. E1 문구가 `배고파`를 보낸 사람에게도 어색하지 않은가
3. R4 문구의 `저희 쪽 문제로`가 신뢰를 떨어뜨리지는 않는가. 숨기는 것보다는 낫다고 판단했다
4. R7을 만드는 대신 R3으로 흡수하는 쪽이 나은가
5. B1의 `최대 1분쯤 걸릴 수 있어요`로 대기 체감이 흡수되는가. 1분은 챗봇 대기로는 긴 시간이다 (사용자 테스트 항목)
6. R4의 새 문구가 `kakao-fe-be-integration.md` 3절이 지적한 안전 보증 오독을 실제로 막는가
7. R5 대기 중 사용자가 같은 문자를 다시 보내면 어떻게 할지 (중복 요청 처리)
