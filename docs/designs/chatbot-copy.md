  비었는지로 정한다(v3 §10 B3). 답 처리는 LLM·네트워크 없이 끝나서 콜백 없이 바로 답한다.

`kakao-chatbot-build-guide.md` 2절의 미확인 항목은 이 검증 기록과 구분해 갱신한다.
현재 폴백은 `render` 스킬 응답을 사용하지만, E1·R1~R7의 BE 분기·카드 반환과
콜백 완료 말풍선은 아직 검증되지 않았다.

다르므로 BE·PM 확인이 필요하다.
그래서 “확인이 끝나면 바로 지운다”, “따로 보관하지 않는다”는 문장을 아직

2026-10-15에 실기기에서 읽기 쉽게 고쳤다. 긴 한 문장에 두 가지 전송을 담아 줄을 어디서 나눠도 어색해서,
무엇이 어디로 가는지를 `- 항목: 서비스` 목록으로 나눴다. 옛 문구의 `임시 확인`은 urlscan을 시험 기간에만
쓴다는 뜻이라 `링크 검사 서비스는 시험 운영 기간에만 써요.`로 풀어 썼다(AI 분석은 출시 뒤에도 남는다).
`자세한 처리 방침은`의 `자세한`은 줄 길이 때문에 뺐다. 정식 방침을 쓸 때 다시 고친다.

**2026-10-21 바꾼 이유** (PR #86 멘토 리뷰, 10/17)

> "앱 설치 요구와 사칭 정황을 확인한 경우라면, 스미싱이 의심된다고 안내하면서 설치를 멈추고 공식 경로로
> 확인하도록 하는 편이 적절해 보입니다. 페이지를 확인하지 못했다는 설명은 그 뒤에 덧붙이면 되겠습니다."

- 앱 설치를 요구했다는 것과 실제 악성 앱이라는 것은 다르다. 그래서 `위험한 문자로 판단했어요`(확정처럼 읽힘) 대신
  `스미싱이 의심돼요`로 쓰고, 약하게 들리지 않도록 바로 다음 줄에 멈출 행동을 둔다.
- 순서는 결론(제목) → 멈출 행동 → 확인할 곳 → 확인 범위 → KISA 안내 → 책임 한계다.
- `stop_line`은 3절 "멈출 행동과 대응 문장"의 이어 붙이기 규칙으로 만든다. 재료는 `message.details.signals`와
  `env.details.signals`의 `code`다. 에이전트 모드에서는 `AgentFinal.stop_actions`를 그대로 쓴다.

  | 신호 `code` | 멈출 행동 |
  | --- | --- |
  | (항상, 맨 앞) | `dont_click_link` |
  | `install_prompt` · `remote_control` | `dont_install_app` |
  | `credential_request` | `dont_enter_info` |

  고를 행동이 링크밖에 없으면 지금 문구 `링크를 누르거나 앱을 설치하지 마세요.`를 쓴다.
- `org_label`은 R9와 같다. `message.brand`이고, 없거나 `unknown`이면 `보낸 기관의`다.
- `scope_line`은 페이지를 끝까지 보지 못했을 때만 넣는다. 끝까지 봤으면 줄째 뺀다.

  | `env.answer` | `scope_line` |
  | --- | --- |
  | `risk_found` · `no_risk_found` | (줄 없음) |
  | `partial` | `페이지는 끝까지 확인하지 못했어요.` |
  | `failed` | `페이지는 열지 못해 문자 내용으로만 판단했어요.` |
  | `not_run` | `페이지는 확인하지 않고 문자 내용으로만 판단했어요.` |

- 2026-10-01부터 BE는 검증된 위험 근거(`signals`)가 있을 때 이 카드를 보낸다. 공식 주소와 다른지와 관계없다
  (`result-meaning-cases.md` 4절).
- PR #39 리뷰("결론과 행동을 먼저")에 따라 제목을 결론으로, 첫 줄을 행동으로 바꿨다. R8·R9와 같은 구조다.
  개정본 제목 `⚠️ 스미싱 의심 안내`와 첫 줄 `해당 메시지는 스미싱으로 의심되오니 주의하시기 바랍니다.`는 결론이
  흐려서 뺐고, 둘째 줄과 근거 안내 줄은 다른 카드와 같은 "~요" 말투로 맞췄다.
- 마지막 보증 문장은 팀이 넣은 책임 한계 문장이라 그대로 둔다. 말투가 혼자 "~니다"이고 위험 카드에서
  어색할 수 있어, 유지할지 금요일 회의에서 확인한다.

행동 줄(`문자 속 링크를 누르거나 앱을 설치하지 마세요.`)은 굵게 보이고 싶은 줄이다. basicCard 본문은
서식을 지원하지 않으므로 강조가 필요하면 제목으로 올리거나 줄을 앞에 둔다.
`자세히 보기` 버튼과 `확인한 근거는 [자세히 보기]에서 볼 수 있어요.` 줄은 2026-10-02에 뺐다. BE에
캐러셀을 보내는 경로가 없어 개발 채널에서 문서용 대괄호 칸이 그대로 보였다. 구현되면 버튼(`block_detail`)과

### R4 확인을 못 마침

| | |
| --- | --- |
| 제목 | `🙏 이번에는 확인하지 못했어요` (16자) |
| 본문 | `결과를 드릴 수 없어 확인을 멈췄어요.`<br>`잘못 보내신 게 아니에요.`<br><br>`잠시 뒤 다시 보내 주세요.`<br><br>`※ 확인 전까지 링크·송금·앱 설치는 하지 마세요.` (2026-10-29 문자·녹음 공용으로 바꿈) |
| 버튼 | 없음 |

- 개정본은 `다시 시도` 버튼(서버가 같은 문자를 다시 검사)을 두었다. 재검사는 BE 구현이 필요한데
  이번 연결 범위에 넣지 않아서(2026-10-01), 버튼을 빼고 마지막 줄을 문자를 다시 보내 달라는 안내로 바꿨다.
  재검사를 구현하면 `다시 시도`(5) → `{{ block_retry }}` 버튼을 달고, 본문의 `잠시 뒤 문자를 다시 보내 주세요.`를
  `잠시 뒤에 다시 시도해 주세요.`로 바꾼다. 버튼 없이 문구만 바꾸면 누를 곳이 없으므로 둘을 같이 바꾼다.
- 2026-10-13: 옛 제목 `지금은 확인을 못 마쳤어요`가 분석 중(R5)과 구분되지 않아 끝났다는 말로 바꿨다.
  첫 줄에 결과가 더 오지 않는다는 뜻을 넣었다. 확인을 못 했을 뿐인데 안전하다고 오해해 링크를 누르지
  않도록 경고 줄을 더했다. 이모지는 R1(⚠️)과 겹치지 않게 🙏를 유지한다.
- 개정본의 `보내주신 문자에는 문제가 없어요`는 분석 실패 상황에서 문자가 **안전하다는 뜻으로 읽혀**
  `문자를 잘못 보내신 게 아니에요.`로 바꿨다 (PR #39 멘토 리뷰, `kakao-fe-be-integration.md` 3절).
  문자의 안전이 아니라 사용자의 행동을 말한다. 관리자센터 원본도 같은 문장으로 바꿔야 한다.
- 개정본 첫 줄 `저희 쪽 문제로 확인을 끝내지 못했어요.`는 제목과 같은 말이라 뺐다. 실패 원인을
  모두 우리 쪽으로 단정할 수도 없다(링크가 만료된 경우 등).

R3과 R4를 나누는 이유는 **사용자가 할 일이 다르기 때문**이다.
R3은 "보낸 것에 확인할 게 없다"(사용자 조치 필요), R4는 "우리 쪽이 못 했다"(그대로 재시도).
문구에서 내부 상태 이름(`판단 보류` `처리 실패`)은 쓰지 않고 원인만 다르게 쓴다.

### R5 분석 중 (첫 응답)

**카드가 아니라 글자만 보낸다.** 콜백 대기 응답은 `useCallback: true`와 `data.text`만
담고 `template`을 넣지 않는다([카카오 AI 챗봇 콜백 개발 가이드](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/ai_chatbot_callback_guide)).
바로연결(`quickReplies`)도 `template` 안에 있으므로 제목·버튼·바로연결을 쓸 수 없다.

| | |
| --- | --- |
| `data.text` · 관리자센터 대기 메시지 | `⏳ 보내 주신 내용을 확인하고 있어요.`<br>`확인이 끝나면 이 채팅창으로 결과를 보내드릴게요.`<br>`기다리는 동안 링크·송금·앱 설치는 하지 마세요.`<br>`결과가 오지 않으면 「결과 확인」이라고 보내 주세요.` (2026-10-29 문자·녹음 공용으로 바꿈. 관리자센터 폴백 블록도 같이 바꿔야 한다) |
| 버튼 (개정본) | `스미싱 판정 결과 확인`(12) → K — **이 응답에는 달 수 없다** |

개정본의 버튼과 마지막 줄 `‘결과 확인’ 버튼을 눌러주세요`는 위 제약과 부딪혀서, 마지막 줄을
`결과가 오지 않으면 ‘결과 확인’이라고 보내 주세요.`로 바꿨다(2026-10-01 BE 지적, PR #39 멘토 리뷰).
BE의 결과 확인 로직이 준비돼 실제로 가능한 행동이다. `결과 확인` 버튼은 보통 스킬 응답(K1·K5)의
바로연결로만 달 수 있다. 그래서 처음 한 번만 입력하면 그다음부터는 바로연결을 누르면 된다.
`스미싱 판정 결과 확인`도 K 블록 발화에 넣어 둔다.

**사용자에게 보이는 대기 문구는 관리자센터 폴백 블록의 `Callback 설정` 대기 메시지다(2026-10-06 확인).**
그전에는 콜백만 켜져 있고 대기 메시지 칸이 비어 있어서, BE가 `data.text`를 보내도 아무것도 보이지 않았다.
2026-10-06에 칸을 채워 배포한 뒤 개발 채널(@클릭전확인)에서 대기 문구가 표시됐다.
표시된 마지막 줄이 관리자센터 문구(`「결과 확인」`)였으므로 BE의 `data.text`(당시 `‘결과 확인’`)는 화면에 나오지 않는다.
**문구를 바꿀 때는 관리자센터 대기 메시지를 고친다.** `r5-analyzing.json`의 `data.text`는 같은 문장으로 맞춰 둔다.

개정본이 참고한 보호나라 챗봇은 첫 응답을 **일반 카드 + 버튼**으로 보내고 결과는 사용자가 버튼을
눌러 가져가게 한다(콜백 미사용). 분석이 최대 10분이라 콜백 주소 유효 시간(5분)을 넘기 때문으로 보인다.
우리는 45초 안에 끝나 콜백으로 결과를 보낼 수 있어서 콜백을 유지한다(ADR 0003, 2026-10-02 결정).
버튼 방식으로 바꿀지는 팀 회의에서 다시 볼 수 있다.

공식 도메인이어도 이 화면을 거친다. 공식 주소 즉답(D2)은 구현되지 않았다(2026-10-13 기준).
`기다리는 동안 문자 속 링크는 누르지 마세요`가 이 화면의 핵심이다 — 대기 중 사용자가
링크를 눌러버리는 것이 가장 큰 위험이다. `data.text`의 글자수 한도는 문서에 없다.
실기기에서 줄바꿈과 잘림을 확인한다.

개정본 R5 아래에 붙은 참고 시안("최대 10분 이후 아래 버튼을 클릭해서…")은 참고 자료로 보고 문구에 넣지 않았다.
우리 대기 상한은 45초다(`main.py` `CALLBACK_DEADLINE_SECONDS`). `latency-budget.md`의 60초는 그 전 값이다.

### K 결과 확인

사용자가 `결과 확인`이라고 보내거나 바로연결 `결과 확인`을 누르면 스킬이 답한다.
관리자센터에 `결과 확인` 블록을 만들고 스킬을 연결한다. 2026-10-02 "결과 카드" 시나리오에 만들었고
패턴 발화는 `결과 확인` `스미싱 판정 결과 확인` `결과 알려줘` `결과 어떻게 됐어` `확인 결과` `결과 보여줘` `결과 확인하기` 7개다.
`결과 확인하기`는 2026-10-06에 더했다. 하단 메뉴 `결과 확인`이 채팅창에 이 말을 보낸다. 등록 전에도 비슷한 말로 맞춰져
결과 확인 블록으로 갔지만, 빗나가면 폴백(R6)으로 빠지므로 정식으로 등록했다.
2026-10-02 BE가 기존 `/kakao/skill` 스킬을 연결했다. BE는 발화 글자가 아니라 요청의
`intent.name`(블록 이름)이 `결과 확인`인지로 이 블록을 알아본다. 발화를 더 넣어도 BE는 고치지 않는다.
`결과` 한 단어는 넣지 않았다. 스미싱 문자에 흔한 "검사 결과를 확인하세요" 같은 문장이
폴백(문자 확인) 대신 이 블록으로 갈 수 있어서다. 개발 채널에서 이런 문자가 폴백으로 가는지 확인한다.
BE는 카카오 사용자 ID로 **그 사용자의 가장 최근 작업**을 찾는다. 사용자가 작업 번호를
입력하지 않는다. 작업 상태는 BE PR #40의 `running` `completed` `timeout` `failed`를 따른다.

29자라 두 줄로 넘어갔다. `조금만 기다렸다가`를 `잠시 뒤`로 줄였다(24자). R4의 `잠시 뒤 문자를 다시 보내 주세요.`와 같은 말이다. 다시 누르라는 안내는 그대로다.

"결과가 나오면 바로 알려드릴게요"는 쓰지 않는다. 콜백 주소가 만료됐으면 결과가 알아서
오지 않는다.

**K2 결과 다시 보기** (`completed`)

- 첫 말풍선(`simpleText`): `{HH:MM}에 확인한 결과예요.` — 한국 시간
- 이어서 저장한 결과 카드(R1~R3)를 그대로 보낸다. 말풍선은 한 응답에 최대 3개다.
- 다시 분석하지 않는다. 확인 시각을 붙이는 이유는 이 결과가 **그 시각의 페이지 상태**라서다.

**K3 확인 실패** (`timeout` `failed`)

- R4 카드를 그대로 보낸다. 실패를 위험 근거처럼 말하지 않는다(`result-meaning-cases.md` 4절 사례 5).

**K4 결과 없음** (작업을 찾지 못함)

| | |
| --- | --- |
| 제목 | `📭 확인 결과를 찾지 못했어요` (16자) |
| 본문 | `확인할 문자나 통화 녹음을 다시 보내 주세요.` (2026-10-29 공용) |
| 버튼 | `문자 다시 보내기`(8) → B1 / `녹음 다시 보내기`(8) → V0 — 처음 시작이 아니라 다시 보내는 상황이다. B1 하나로만 보내면 녹음을 보낸 사람이 스미싱 안내를 받는다 |

"보낸 문자가 없어요"라고 쓰지 않는다. 지금 BE 작업 저장소는 메모리에만 있어서 서버가
재시작하면 보낸 문자의 결과도 사라진다. 사용자를 탓하는 문장이 되면 안 된다.

**K5 중복 요청** (`running` 중에 새 문자를 보냄)

| | |
| --- | --- |
| 제목 | `⏳ 앞서 보내 주신 내용을 확인하고 있어요` (2026-10-29 공용) |
| 본문 | `한 번에 하나씩 확인해요.`<br>`결과가 나온 뒤에 다음 것을 보내 주세요.` |
| 바로연결 | `결과 확인`(5) |

새로 보낸 문자는 분석하지 않고 보관하지도 않는다. 지금 BE는 같은 상황에
`simpleText`("이전 요청을 아직 확인하고 있어요…")로 답한다. 이 카드로 바꾼다.
대기 응답(R5)과 달리 보통 스킬 응답이라 바로연결을 달 수 있다.

### R6 확인할 주소 없음 (엣지 3)

| | |
| --- | --- |
| 제목 | `🔗 확인할 링크가 없어요` (13자) |
| 본문 | `그래서 이번에는 검사하지 않았어요.`<br>`링크가 없다고 안전한 건 아니에요.`<br><br>`문자 속 번호로 전화하거나 앱을 설치하지 마세요.`<br>`보낸 기관의 공식 앱·홈페이지·대표번호로 직접 확인하세요.`<br><br>`링크가 있는 문자라면 전체를 복사해 다시 보내 주세요.` (127자) |
| 버튼 | `신고·상담하기`(7) → B2 / `다른 문자 확인하기`(10) → B1 — **세로 배치** |

2026-10-05 멘토 리뷰(PR #39, 10/3)로 바꿨다. 이전 문구는 다시 보내 달라고만 해서,
전화·송금·앱 설치를 요구받은 사용자가 다음에 할 일을 알 수 없었다.

> "링크가 없다는 이유로 안전하다고 볼 수는 없습니다. (…) 링크가 실제로 없는 문자에
> 재입력만 요구하지 않도록 해 주세요."

- 순서: 검사하지 않은 사실 → 안전하다는 뜻이 아님 → 할 일 → 다시 보내는 방법.
- 가짜 고객센터로 전화하게 한 뒤 원격제어 앱을 깔게 하는 수법이 있어서 전화와 앱 설치를 직접 막는다.
- **"스미싱으로 보여요" 같은 문장을 쓰지 않는다(D5).** 관측이 0건이라 방어할 근거가 없다.
- BE는 잡담(`배고파`)과 링크 없는 문자를 아직 구분하지 못해 둘 다 이 카드를 받는다(D4).
  그래서 제목을 `이 문자에는`이 아니라 `확인할 링크가 없어요`로 썼다.
- 이전 본문의 `300자 이상` 줄은 BE 입력 길이 기준이 없어 뺐다(7절).
- 본문의 요구 행동(전화·송금·앱 설치)을 분석하는 기능은 URL 검사와 따로 반환하도록
  BE·AI에 요청한다. 그 전까지 이 카드는 문자 내용을 언급하지 않는다.

**에이전트 모드(`AGENT_MODE=on`)에서는 링크 없는 문자가 R6로 오지 않는다.** 문자 내용을 분석해 R6b로 결론을 준다(D14, 3절 R6b).
R6는 `AGENT_MODE=off`일 때와, 문자가 아닌 입력을 BE가 가려낼 수 없을 때만 남는다.

AI 유형 참고 칸을 쓸 경우 `smishing-message-intake-ux.md` 3절의 네 가지 제약
(어휘 차단 / 상태 불변 / 없으면 안 그림 / 형식 서술만)을 그대로 적용한다.

문자 분석을 끝내지 못한 경우에도 나가서, 검사 후 근거가 없었다고 읽혔다.

> "사용자에게는 문자에서 확인한 사실, 검사하지 못한 부분, 문자에 적힌 링크나 연락처를 쓰지 않고
> 해당 업무를 확인할 방법을 알려주면 됩니다."

> "완료 여부와 함께 실제 확인한 사실을 렌더러에 전달하면 같은 보류 결과에서도 정확한 설명을 만들 수 있습니다."

2026-10-15 멘토 리뷰(PR #86, 10/15)로 첫머리를 두 갈래로 나누고, 결론과 다음 행동을 확인 범위보다 앞에 뒀다.

> "상태를 하나 더 만드는 것보다, 첫 안내를 읽고 어떻게 대응해야 할지 알 수 있는지가 더 중요하다고 생각합니다.
> 현재 문자에서 의심 정황이 확인됐다면 '주의가 필요한 문자예요'라는 판단과 함께, 어떤 행동을 멈추고
> 어디에서 확인하면 되는지를 먼저 안내하면 좋겠습니다."

**의심 정황을 확인했다고 보는 조건**

아래 두 가지를 모두 만족하면 `의심 정황 있음`이다.

1. `message.details.doubts`의 `value`에 아래 **민감한 요구 행동** 중 하나 이상이 있다.
2. `url.official`이 `official`이 아니다.

| 민감한 요구 행동 (`doubts.value`) | 멈출 행동 (이어 붙일 때) |
| --- | --- |
| `정보 입력` | `정보를 입력하` |
| `본인 확인` | `본인 인증을 하` |
| `앱 설치` | `앱을 설치하` |
| `금전 인출` | `돈을 보내` |
| `전화 응대` | `문자 속 번호로 전화하` |
| `주소 입력·수정` | `주소를 입력하` |
| `송금·입금` | `돈을 보내` |
| `상품권 구매` | `상품권 핀번호를 보내` |
| `인증번호 전달` | `인증번호를 알려 주` |
| `전화 걸기` | `문자 속 번호로 전화하` |
| `메신저 이동` | `다른 메신저로 대화를 옮기` |

- 마지막 다섯 줄은 2026-10-21에 더했다. AI가 요구 행동 분류에 이 다섯 값을 더한 뒤에 쓴다(`agent-loop-plan-v2.md` §13 Task 1, §9 B6).
  문장은 3절 "멈출 행동과 대응 문장"과 같다.

- `doubts`는 고정 규칙이 찾은 요구와 원문 검증을 통과한 신호에서 나오고, 항목마다 문자 원문 인용(`evidence`)이 붙어 있다
  (`ai/src/ai/pipeline/results.py` `build_message_part`). 그래서 "문자에 실제로 적힌 요구"로 쓸 수 있다.
  판정에는 쓰지 않고 첫머리를 고르는 데만 쓴다(CLAUDE.md 원칙 1·2).
- `배송 조회`·`링크 접속`·`상세 내용 확인`·`수령·일정 확인`·`사진 확인`·`주문 취소·환불`은 민감한 요구로 보지 않는다.
  진짜 택배 문자에도 흔해서, 넣으면 대부분의 R9가 `주의가 필요한 문자예요`가 된다.
- 기관·지역을 모른다는 것, 알려진 사례와 닮았다는 것만으로는 `의심 정황 있음`으로 보지 않는다
  (PR #86 멘토 리뷰 처음 문장, `ai/tests/test_revision_results.py` "유사도만으로 위험 근거를 만들지 않는다").
- **공식 주소와 같으면 제외한다 (2026-10-15 결정, A안).** 진짜 택배사가 공식 주소로 "주소를 확인·수정해 주세요"라고
  보내는 경우가 흔해서, 넣으면 진짜 문자에 경고가 나가고 아래 `확인한 것`의 `주소가 {brand} 공식 주소와 같아요`와
  말이 엇갈린다. 공식 주소를 악용한 사기에서는 제목이 약해지는 단점이 있지만, 이 카드는 어느 갈래든
  "링크 대신 공식 앱·홈페이지에서 확인하라"고 안내하므로 행동 안내는 빠지지 않는다. 실제 문자에서 이 조합이
  얼마나 나오는지는 AI와 확인한다. `redirected_from_official`(공식 주소에서 다른 곳으로 이동)은 `official`이 아니므로
  제외하지 않는다.

**빈칸 채우는 규칙**

`headline`은 위 갈래 표의 제목이다.

`action_guide`

- `org_label`은 `message.brand`다. 없거나 `unknown`이면 `보낸 기관의`를 넣는다. 문자가 내세운 기관 이름(`청소행정과` 등)은
  넣지 않는다. 주장한 이름을 우리 안내 문장에서 되풀이하지 않기 위해서다. 구체적인 확인 경로는 자세히 보기의
  공식 확인 방법 카드(C4)가 보충한다.
- `의심 정황 있음`일 때 `{멈출 행동}`은 `링크를 누르`로 시작하고, `doubts`에서 민감한 요구 행동을 **원문 순서대로 최대 2개**
  골라 `거나 `로 이은 뒤 `지 마세요.`로 끝낸다. R9는 링크가 있는 문자만 오므로 `링크를 누르`는 늘 들어간다.
  - 1개: `링크를 누르거나 정보를 입력하지 마세요.`
  - 2개: `링크를 누르거나 정보를 입력하거나 앱을 설치하지 마세요.`
  - 3개 이상 이으면 첫 줄이 길어져 먼저 안내하는 효과가 약해진다. 나머지는 아래 `요구한 것` 줄에 다 나온다.
- `전화 응대`가 "전화를 걸라"는 요구인지 "걸려 올 전화를 받으라"는 요구인지는 AI와 확인한다.
  받으라는 뜻이면 `모르는 번호의 전화에 응하`로 바꾼다.

`message_claims`

문자가 **주장한** 내용을 모은 칸이다. 확인한 사실이 아니므로 `확인한 것`과 나눈다.
줄이 하나도 없으면 칸 전체(제목과 뒤 빈 줄 포함)를 빈 문자열로 둔다. 줄이 있으면 아래 모양이다.

```
{칸 제목}
- 내세운 기관: …
- 내세운 명분: '…'
- 요구한 것: …
(빈 줄)
```

| 줄 | 값 | 넣는 규칙 |
| --- | --- | --- |
| 내세운 기관 | `message.brand`가 있음 | `- 내세운 기관: {brand}` (따옴표 없이) |
| | 없거나 `unknown`, `reason.text`에 `문자가 내세운 기관: '…'`이 있음 | `- 내세운 기관: '…'` (원문 인용) |
| 내세운 명분 | `reason.text`에 `문자가 내세운 명분: '…'`이 있음 | `- 내세운 명분: '…'` |
| 요구한 것 | `doubts`가 있음 | `- 요구한 것: {value, value, value}` (원문 순서, 최대 3개, `unknown` 제외) |

- `reason.text`는 한 문자열이다(`ai/src/ai/pipeline/results.py` `build_message_part`). 렌더러가 문장 앞머리
  (`문자가 내세운 기관:`, `문자가 내세운 명분:`)로 골라 따옴표 안만 쓴다. AI 필드는 늘리지 않는다.
- `reason.text`의 그 밖의 문장은 쓰지 않는다. 요구 인용(`문자에서 '…'라고 안내했습니다.`)은 `요구한 것` 줄이,
  분석 실패 문장은 `확인하지 못한 것`의 `문자 내용 ({실패 이유})`가 이미 알린다(이슈 #76 겹침 정리).
  `제공된 문자에서 명시적인 행동 요구를 확인하지 못했습니다.`도 넣지 않는다. `요구한 것` 줄이 없는 것으로 충분하다.
- 인용은 30자를 넘으면 끝을 `…`로 줄인다. 본문 전체가 400자를 넘으면 `내세운 명분` 줄부터 뺀다.
  첫머리와 확인 범위가 먼저다.
- 이전 `문자에 적힌 내용` 칸(`{{ message_reason }}`, 이슈 #68)과 `확인한 것`의 `문자에 적힌 보낸 곳`·`문자에서 요구한 것`
  줄을 이 칸으로 합쳤다. 같은 말이 두 번 나오던 문제(이슈 #76)가 없어진다.
- 칸 제목은 `의심 정황 있음`이면 `주의할 점`, 없으면 `문자에 적힌 내용`이다. 진짜일 수 있는 문자의 주장을
  "주의할 점"이라고 부르지 않기 위해서다.

`checked`·`unchecked`는 아래 표의 문장을 `- `로 시작하는 줄로 만들어 위에서부터 이어 붙인다.
넣을 문장이 하나도 없으면 `- 없음`을 넣는다.

| 무엇 | 값 | `checked`(확인한 것) | `unchecked`(확인하지 못한 것) |
| --- | --- | --- | --- |
| 보낸 곳 | 항상 | — | `실제로 보낸 곳` |
| 주소 | `url.official` = `official` | `주소가 {brand} 공식 주소와 같아요` (택배사를 모르면 `주소가 공식 주소 목록에 있어요`) | — |
| | `not_registered`, 택배사를 모름 (`message.brand`가 없거나 `unknown`) | — | `주소가 공식 주소인지 (보낸 기관을 몰라 대조하지 못했어요)` |
| | `not_registered`, 택배사를 앎 | — | `주소가 공식 주소인지 (공식 주소 목록에 없는 기관이라 대조하지 못했어요)` |
| | `brand_mismatch` | `공식 주소 목록에 없는 주소예요` | — |
| | `shortener_unresolved` | — | `주소가 공식 주소인지 (단축 주소라 실제 주소를 확인하지 못했어요)` |
| | `redirected_from_official` | `문자 속 주소는 {brand} 공식 주소와 같아요` | `이동한 주소가 안전한지 (공식 주소에서 다른 주소로 이동했어요)` |
| | `unresolved` | — | `주소가 공식 주소인지` |
| 문자 | `message.answer` = `no_risk_found` | `문자 내용 (확실한 위험 근거는 찾지 못했어요)` | — |
| | `partial` 또는 `failed` | — | `문자 내용 ({실패 이유})` — 아래 실패 이유 표 |
| | `not_run` | — | `문자 내용` |
| 페이지 | `env.answer` = `no_risk_found` | `페이지 내용 (확실한 위험 근거는 찾지 못했어요)` | — |
| | `partial` | — | `페이지 내용 (끝까지 확인하지 못했어요)` |
| | `failed` | — | `페이지 내용 (열지 못했어요)` |
| | `not_run` | — | `페이지 내용` |

- **보낸 곳은 항상 `확인하지 못한 것`에 넣는다.** "검찰청이라고 주장한다"와 "검찰청이 보냈다"를
  구분하라는 멘토 리뷰(PR #39, `ai/src/ai/pipeline/results.py` 153줄 의견)를 따른다.
  문자가 내세운 기관은 `message_claims`의 `내세운 기관` 줄에만 둔다.
- 요구 행동은 사실 목록(`doubts`)이다. 위험 근거(`signals`)가 아니므로 "위험한 요구"라고 쓰지 않는다
  (`docs/scheme.md` 3절).
- **분석을 마쳤지만 검증된 위험 근거가 없을 때는 `{문자/페이지} 내용 (확실한 위험 근거는 찾지 못했어요)`로 쓴다**
  (2026-10-16). 이전 문장 `문자에서 위험 신호를 찾지 못했어요`는 주의 갈래 제목(`주의가 필요한 문자예요`)과 함께 나오면
  앞뒤가 맞지 않게 읽혔다. 문자 분석을 마치고 요구 행동은 있지만 검증된 신호가 없으면 `message.answer`가
  `no_risk_found`라서 주의 갈래에서도 이 줄이 나온다. `확실한`은 검증된 근거(`signals`)를 뜻하고(PR #86 멘토 리뷰
  "확실한 위험 근거를 확보했다면 그 경고는 유지"), `찾지 못했어요`는 없다고 단정하지 않는다.
  `확인하지 못한 것`의 `{대상} ({이유})` 모양과도 맞춘다.
- **`확인한 것`에는 끝까지 검사한 결과만 넣는다.** 검사를 안 했거나, 실패했거나, 끝내지 못한 것은
  `확인하지 못한 것`에 넣고 괄호로 이유를 구분한다(2026-10-08 멘토 리뷰, PR #54 10/7:
  "검사를 하지 않은 경우, 검사에 실패한 경우, 검사는 끝났지만 목록에서 찾지 못한 경우를 같은 값으로 처리하면 안 됩니다").
- `not_registered`는 주소가 목록에 없다는 뜻이 아니라 **대조를 하지 못했다**는 뜻이다. 택배사를 몰랐거나,
  택배사가 공식 주소 목록에 없을 때 나온다(`services/official_domain_service.py`). 이전 규칙은 이것을
  `공식 주소 목록에 없는 주소예요`로 안내해, 목록에 있는 naver.com 주소에도 그렇게 나갔다(멘토 리뷰).
  실제로 대조해서 다른 `brand_mismatch`만 이 문장을 쓴다.
- **단축 주소·이동 보류 문장 (이슈 #66).** `shortener_unresolved`·`redirected_from_official`은 `unresolved`의 세부 사유로,
  판정상으로는 `unresolved`와 같고 카드 문구 선택에만 쓴다(`ai/src/ai/types.py` `DomainMatch`, `feature/rag-fix-final-ai` 8faa17d).
  아직 develop에는 없다.
  - 일반 문장 `주소가 공식 주소인지`만으로는 사용자가 왜 확인하지 못했는지 알 수 없어 이유를 붙였다.
  - 이동한 경우는 `확인한 것`에 공식 주소와 같다는 줄만 나가면 공식인데 왜 보류인지 읽히지 않아서, 이동한 주소를
    확인하지 못했다는 줄을 함께 넣는다.
- `partial`은 일부를 검사해 근거가 없었다는 뜻이 아니라 **분석을 끝내지 못하고 자료만 남은 상태**다
  (시간 초과 등, `ai/src/ai/pipeline/results.py` `_answer`). 이전 규칙의 `문자 일부에서 위험 신호를 찾지 못했어요`는
  분석을 마친 것처럼 읽혀서 뺐다. 어느 부분까지 끝났는지 결과에 담기면 그때 `확인한 것`에 넣을지 다시 정한다.
- 문자 분석을 못 끝낸 이유는 `message.details.reason.failures`의 **첫 번째** 값으로 고른다(#59).
  내부 코드는 카드에 보이지 않고 아래 문장으로만 바꾼다. 원본은 `services/chatbot_copy_data.py` `MESSAGE_FAILURE_COPY`.

  | `failures[0]` | 실패 이유 |
  | --- | --- |
  | `timeout` | `분석 시간이 초과되어 끝까지 확인하지 못했어요` |
  | `refused` | `분석 요청이 거절되어 확인하지 못했어요` |
  | `invalid_output` | `분석 결과를 올바르게 받지 못했어요` |
  | `llm_error` | `분석 중 오류가 발생해 확인하지 못했어요` |
  | `empty_input` | `링크만 있어서 확인할 글이 없었어요` |
  | `input_too_large` | `문자가 너무 길어 끝까지 확인하지 못했어요` |
  | 없음 또는 그 밖의 값 | `문자 분석을 완료하지 못했어요` |

  `empty_input`은 분석에 실패한 것이 아니라 **링크를 빼고 나니 읽을 글이 없었다**는 뜻이다(사용자가 링크만
  붙여넣은 경우). 기본 문구로 보내면 실패처럼 읽혀서 따로 둔다(멘토 리뷰 PR #54 10/7: 검사하지 않은 경우와
  실패한 경우를 같은 값으로 처리하지 않는다). `input_too_large`는 링크를 뺀 본문이 8,192자를 넘을 때다
  (`ai/src/ai/pipeline/analysis.py` `MAX_MESSAGE_CHARS`).
- R9에 오는 결과는 검증된 위험 근거가 없으므로 문자·페이지가 `risk_found`인 경우는 없다.
- 기한 줄은 의심 문자 링크를 피하라는 안내 때문에 실제 제출·납부 기한을 놓치지 않게 하려는 것이다
  (멘토 리뷰: "문자가 진짜인지와 실제 처분이 있는지는 별개입니다"). 다음 행동이므로 첫머리 바로 아래에 둔다.
- 소제목(`주의할 점`, `확인한 것` 등)에는 이모지를 쓰지 않는다(6절). `✅ 확인한 것`은 "안전이 확인됐다"로 읽힐 수 있다.
  본문이 회색이라 소제목이 눈에 덜 띄는 문제는 실기기 확인 때 `[주의할 점]` 같은 대괄호를 시험해 본다.
- **빈칸을 BE가 채우기 전에 이 카드가 배포되면 `{{ headline }}`이 글자 그대로 보인다.**
  렌더러는 값이 없는 빈칸을 남겨 두기 때문이다. BE 렌더러 변경과 함께 합친다.

- 페이지 수집기가 없는 지금은 공식 주소인 문자도 여기로 온다. 공식 주소와 같다는 것만으로
  정상이라고 하지 않는다(PR #39 멘토 리뷰, `result-meaning-cases.md` 6절 9).
- 2026-10-02 결정: 격리 환경이 붙기 전까지는 공식 주소여도 R9로 둔다. 격리 환경이 붙으면
  공식 주소인 경우를 R2로 보낼지 다시 정한다(`result-meaning-cases.md` 6절 9).

### Q1 이미 하신 게 있나요? (리스트 카드)

결과 카드 바로 아래에 붙는다(D11·D12). 붙이는 곳은 R1 · R8 · V1 · R6b 의심, R9·R6b·V1의
`주의가 필요한 …예요` 갈래, 그리고 **링크가 있는 R9 `판단하기 어려워요`**다(2026-10-27 D16, v3 §7.6).
R2(공식 주소 일치)와 링크 없는 `판단하기 어려워요`(R6b·V1)에는 붙이지 않는다.

- 링크가 있는 `판단하기 어려워요`에 붙이는 이유: 위험 신호를 못 찾았어도 이미 그 링크에 정보를 넣은 사람이 대응을 찾을 길이 있어야 한다.
  결과 카드에 신고 버튼이 없으므로(D15) 이 사람에게는 Q1이 상담 입구다.
- 대신 이때는 `돈이나 상품권을 보냈어요`를 넣지 않는다. 돈 요구가 없었던 결과에 "돈 보냈나요?"를 물으면 정상 문자를 받은 사람을 놀라게 한다.

예시 (A2, 멈출 행동이 `dont_click_link` · `dont_install_app`, 129자):


- 카드 파일은 `a2-not-yet.json`(문자)와 `a3-clicked-link.json`이다(2026-10-29). 문자 A2의 빈칸은 녹음 A2처럼 `stop_line` 하나다.
  3절 "멈출 행동과 대응 문장"의 `stop_line` 규칙 그대로 만들면 `지금처럼 ` 뒤에 그대로 붙는다(`링크를 누르지 마세요.`, `링크를 누르거나 앱을 설치하지 마세요.`).
  `paste_text`는 넣지 않는다. Q1이 붙는 결과(의심, 주의, 링크 있는 판단 어려움)에는 멈출 행동이 하나 이상 있다고 보고, 비는 경우가 있는지 BE, AI와 확인한다.
- `잘하셨어요`는 사용자의 행동을 말한다. 문자가 안전하다는 뜻이 아니다. `다행이에요`·`안전해요`는 쓰지 않는다(§7.6 금지어).
- A2의 KISA 두 줄은 B2a(문자만 받음)와 같은 문장이다. 상황이 같으므로 같은 말로 안내한다. 한쪽을 고치면 다른 쪽도 고친다.
  삭제·차단을 신고 뒤에 두는 이유도 B2a와 같다(지우면 신고할 문자가 남지 않는다).
- 삭제 줄은 B2a의 `다 끝나면`을 `신고·상담을 마쳤다면`으로 바꿔 썼다(2026-10-27). B2a는 "확인 → 신고·상담" 다음이라
  `다 끝나면`이 분명하지만, A2는 확인이 이미 끝난 상태라 무엇이 끝난 뒤인지 흐려진다.
- V1 녹음 결과의 A2 문구와 버튼은 보이스피싱 흐름을 정리할 때 다시 본다. `그 번호`가 어느 번호인지 흐리고,
  보이스피싱 신고 창구(112·1332)와 KISA 중 무엇을 버튼으로 둘지 정하지 않았다.
  → 2026-10-27 녹음 결과의 상담 버튼은 `1394 상담`으로 정했다(D17, `voice-phishing-flow.md`). 문구는 그 문서에서 다시 쓴다.
  → 2026-10-29 문구를 바꿨다(위 표). `그 번호`를 `번호를 차단하세요`로 앞에 두고, 녹음 A2는 `잘하셨어요`로 시작하지 않는다.
- A3의 118 문장은 R1a의 `이미 눌렀거나 설치했다면 118에 문의하세요.`를 옮긴 것이다. 링크만 누른 상황이라 급한 말투(B2b `🚨 지금 바로 상담받으세요`)는 쓰지 않는다.
  B2b는 하단 메뉴에서 `링크를 눌렀어요`를 고른 사람이 보는 카드라 정보 입력·앱 설치까지 포함한다.
- `phone` 버튼은 PC 카카오톡에서 보이지 않아 A3 본문에 번호를 적는다(대응 표 아래 규칙과 같다).
- A3은 `링크만 눌렀어요`에 대응이 없을 때(받은 파일이 없을 때)다. 파일을 받게 하는 페이지였다면 K6(`delete_downloaded_file`)로 간다.
- 그래도 A3에 `받은 파일이 있다면 열지 말고 지우세요.`를 넣는다(2026-10-27). 페이지를 끝까지 보지 못했으면 코드가 파일을 놓칠 수 있고,
  사용자도 무언가 받아졌는지 모를 수 있다. 해가 없는 안전 쪽 안내라 조건 없이 둔다. 대응 표 `delete_downloaded_file`과 같은 뜻이다.

Q1에서 대응할 일이 있는 답을 골랐을 때 보낸다. 값은 `response_actions`다(§7.5, 코드가 고름).

| 버튼 | 문자 결과: 대응 표의 `K6 버튼`을 대응 순서대로, 최대 3개, 세로. 하나도 없으면 `KISA 상담하기`(9) — `webLink` `https://www.kisa.or.kr/118` (2026-10-27 `신고·상담하기` → B2에서 바꿈. B2는 상황을 다시 묻는다, D15). 녹음 결과: "녹음 결과 버튼 (D17)" 표. **고른 답이 `앱을 설치했어요`뿐이면 버튼을 달지 않는다**(D17) |

예시 (금융감독원 사칭, 송금 요구):

```
⚠️ 보이스피싱이 의심돼요
통화를 끊고, 돈을 보내거나 상대가 알려 준 번호로 전화하지 마세요.
금융감독원 대표번호(1332)로 직접 전화해 확인하세요.

주의할 점
- 상대가 내세운 기관: '금융감독원 수사관 김○○입니다'
- 상대가 한 말: '안전계좌로 옮기셔야 합니다'
- 내세운 사정: '고객님 명의 계좌가 범죄에 연루됐습니다'
- 요구한 것: 송금·입금, 전화 걸기

확인한 것
- 통화 내용 (받아 적은 글)
- 상대가 말한 전화번호

확인하지 못한 것
- 실제로 건 곳
- 받아 적은 글이 정확한지 (말을 글로 옮겨 틀릴 수 있어요)
[자세히 보기]
[다른 녹음 확인하기]
```

- `stop_line`은 공통 규칙대로다. 녹음이면 `hang_up`이 늘 들어간다(§7.4).
- `verify_line`은 `official_contact`(`org`, `number`, `source_url`)로 만든다(2026-10-29 AI 칸).
  - `org`·`number`가 있으면 `{org} 대표번호({number})로 직접 전화해 확인하세요.`
    번호는 **대표번호 KB(`official_numbers.yaml`)에서만** 온다. 녹음에 나온 번호는 쓰지 않는다(사기범 번호일 수 있다).
  - 값이 `null`이면 `상대가 말한 기관의 대표번호를 직접 찾아 전화해 확인하세요.`
  - `source_url`은 카드에 쓰지 않는다. KB 검토용이다.
  - R9는 문자가 내세운 기관 이름을 안내 문장에 넣지 않는다. 여기서는 공식 자료와 맞춘 기관 이름과 번호라서 넣는다.
- `call_claims`는 `claims`(v3 `ClaimView`)로 채운다. R9의 `message_claims`와 같은 모양이다. 칸 제목은 `suspected`·`caution`이면 `주의할 점`, 아니면 `통화에서 들은 내용`이다.
  - `- 상대가 내세운 기관: '…'` — `identity[].quote`
  - `- 상대가 한 말: '…'` — 첫 `demands[].quote` (v2 `basis_quote` 대신)
  - `- 내세운 사정: '…'` — `blockers` 먼저, 이어서 `pretexts`
  - `- 요구한 것: …` — `demands[].kind` 라벨, 원문 순서, 최대 3개
  - 값이 없는 줄은 뺀다. **통화 상대가 한 말만 쓴다.** 사용자 쪽 말은 근거로 쓰지 않는다(보이스피싱 분석 MVP 설계 "상대 화자 근거 원칙").
  - 인용은 30자를 넘으면 `…`로 줄인다.
  - **누가 한 말인지 모를 때**(`unchecked`에 `speaker`가 있을 때)는 말머리를 아래처럼 바꾼다. 누가 말했는지 모르는데 `상대가`라고 단정하지 않기 위해서다(2026-10-29, PR #114 멘토 리뷰 2번).

    | 평소 | 누가 한 말인지 모를 때 |
    | --- | --- |
    | `- 상대가 내세운 기관: '…'` | `- 통화에 나온 기관: '…'` |
    | `- 상대가 한 말: '…'` | `- 통화에 나온 말: '…'` |
    | `- 내세운 사정: '…'` | `- 통화에 나온 사정: '…'` |
    | `- 요구한 것: …` | `- 통화에 나온 요구: …` |

    제목, `stop_line`, Q1은 그대로 둔다. 송금을 멈추고 공식 번호로 확인하라는 안내는 누가 말했는지와 상관없이 필요하다.
    `verify_line`의 기관 번호가 `null`일 때만 `통화에 나온 기관의 대표번호를 직접 찾아 전화해 확인하세요.`로 바꾼다.
- `checked`·`unchecked`는 아래 "확인한 것·확인하지 못한 것 (에이전트 결과)" 표로 만든다. `similar_cases`(비슷한 사례)는 녹음 캐러셀 2번째 장에 보여 준다(2026-10-30, 4절 "녹음 캐러셀의 비슷한 사례").
- V1에는 신고 버튼도 1332 안내도 넣지 않는다(D15·D17). 신고·지급정지·상담은 Q1 → K6·A2에서 안내하고, 버튼은 "녹음 결과 버튼 (D17)" 표를 따른다.

### R6b 링크 없는 문자 결과

링크 없는 문자(가족·지인 사칭, 기관 사칭) 분석 결과다. 에이전트 모드에서는 링크 없는 문자를 R6 즉답으로 보내지 않는다(D14).
결론이 `suspected`면 `r6b-warning`, `inconclusive`면 `r6b-uncertain`이다(§9 B5).

| 카드 | 결론 | 제목 (`{{ headline }}`) |
| --- | --- | --- |
| `r6b-warning` | `suspected` | `⚠️ 사칭 문자로 의심돼요` (14자) |
| `r6b-uncertain` | `inconclusive`, `caution=true` | `🔎 주의가 필요한 문자예요` (14자) |
| | `inconclusive`, `caution=false` | `🤔 판단하기 어려워요` (11자) |

| | |
| --- | --- |
| 본문 | `{{ stop_line }}`<br>`{{ verify_line }}`<br>`{{ basis_note }}`<br><br>`{{ message_claims }}``확인한 것`<br>`{{ checked }}`<br><br>`확인하지 못한 것`<br>`{{ unchecked }}` |
| 버튼 | `다른 문자 확인하기`(10) → B1 (2026-10-27 `신고·상담하기` 뺌, D15) |

예시 (가족 사칭, 통화해 보니 본인이 아님):

```
⚠️ 사칭 문자로 의심돼요
돈을 보내거나 인증번호를 알려 주지 마세요.
원래 알던 번호로 직접 전화해 확인하세요.
답해 주신 내용 기준으로 안내했어요.

주의할 점
- 내세운 관계: '엄마'
- 내세운 사정: '폰이 고장나서 통화가 안돼'
- 요구한 것: 송금·입금, 인증번호 전달

확인한 것
- 문자 내용
- 원래 번호로 통화한 결과 (본인이 아니라고 답해 주셨어요)

확인하지 못한 것
- 실제로 보낸 사람
```

- **"스미싱"이라고 쓰지 않는다.** 링크가 없는 문자라서 `사칭`으로 쓴다(D14).
- 버튼은 세 제목 모두 같다. 의심·주의 갈래는 Q1이 신고·상담으로 잇고(D15), `판단하기 어려워요` 갈래는 R9처럼 신고 버튼 없이 둔다.
  한 카드 안에서 갈래마다 버튼을 바꾸면 렌더러가 버튼까지 골라야 해서 하나로 맞췄다. 신고하려는 사람은 하단 메뉴 `신고 상담`을 쓴다.
- `stop_line`은 공통 규칙대로다. 링크가 없으므로 `dont_click_link`는 나오지 않는다.
- `verify_line`
  - 가족·지인이라고 한 문자(받아들인 관계 인용이 있음): `원래 알던 번호로 직접 전화해 확인하세요.`
  - 기관이라고 한 문자: `{{ org_label }} 공식 앱·홈페이지나 대표번호로 직접 확인하세요.` (`org_label`은 R9와 같음)
  - `caution=false`이고 멈출 행동이 없으면 이 줄이 첫 줄이 된다. 앞에 `문자 속 번호 대신 `을 붙인다(R9의 의심 정황 없음 갈래와 같은 모양).
- `basis_note`는 결론의 근거에 사용자 답(`user_answer`)이 있을 때만 `답해 주신 내용 기준으로 안내했어요.`를 넣는다(§10 FE2). 없으면 줄째 뺀다.
- `message_claims`는 R9 규칙에 `- 내세운 관계: '…'`(받아들인 `acquaintance_claim` 인용) 줄을 맨 앞에 더한다.
  `내세운 명분`은 가족·지인 문자에서는 `내세운 사정`으로 쓴다(폰 고장, 급한 일 등).
- 카드 파일은 `r6b-warning.json`, `r6b-uncertain.json`이다(2026-10-30). 두 카드는 모양이 같고 `headline`만 다르다. 버튼 블록은 B1(`6aa6a4436d537a3eabb81ad5`)이다.
- 가족·지인 문자이고 아직 통화로 확인하지 않았으면(`follow_up` = `called_known_number`) 결과 아래에 Q2의 리스트 카드를 붙인다.
  Q1과 함께 나가면 Q1을 먼저 둔다. 이미 돈을 보낸 사람은 대응이 먼저다.

### Q2 원래 알던 번호로 통화해 보셨나요?

가족·지인이라고 하는 문자에서 보낸다(§6.2 `called_known_number`). 이 답은 Q1과 달리 **결론을 바꿀 수 있다**
(본인이 아니라고 하면 사칭 근거가 된다, §7.3 L-4). 답으로 결론을 고치는 일은 게이트(코드)가 한다.

> **v3 기준 (2026-10-27, D16).** 분석 중 질문이 없어져 Q2도 결과 카드(R6b) 아래에 Q1 다음으로 붙는다. 그래서 늘 아래 말풍선 2(리스트 카드)만 쓴다.
> 말풍선 1의 멈출 행동·확인 안내는 결과 카드에 이미 있다. 답이 오면 게이트만 다시 돌아 새 결과 카드가 나간다(v3 §8).
> 아래 말풍선 1 문구는 분석 중 질문이던 때(v2)의 기록으로 남긴다.

말풍선 두 개로 보낸다. 사용자가 답하지 않아도 멈출 행동은 먼저 받은 상태가 되게 하려는 것이다(§6.2).

| | |
| --- | --- |
| 말풍선 1 제목 | `{{ stop_title }}` — 멈출 행동의 첫 번째를 `한 문장으로 쓸 때` 문장에서 마침표를 빼고 쓴다(예: `돈을 보내지 마세요`). 없으면 `보내기 전에 확인해 주세요` |
| 말풍선 1 본문 | `문자만으로는 누가 보냈는지 알 수 없어요.`<br>`원래 알던 번호로 직접 전화해 확인해 보세요.` (48자) |
| 말풍선 2 | 리스트 카드. 머리글 `📞 원래 알던 번호로 통화해 보셨나요?` (21자. 2026-10-30 Q1 `🙋`과 맞춰 이모지를 넣음), 항목은 아래 표 |

| `option_id` | 항목 |
| --- | --- |
| `not_person` | `본인이 아니래요` |
| `is_person` | `본인이 맞대요` |
| `no_answer` | `전화를 안 받아요` |
| `not_yet` | `아직 안 해 봤어요` |
| `unknown` | `잘 모르겠어요` |

- 항목의 `extra`는 Q1과 같은 모양이다(`question_id: "called_known_number"`).
- 문자에 적힌 번호로 걸어 보라고 하지 않는다. 사기범 번호일 수 있다(§6.2).
- 결과 카드에 후속 질문으로 붙일 때(`follow_up`)는 말풍선 2만 붙인다. 멈출 행동은 결과 카드에 이미 있다.
- 카드 파일은 `q2-called-known-number.json`이다(2026-10-30). 말풍선 2만 만들었다. 항목은 Q1처럼 `{{ items }}` 통째 빈칸이고, 답변 블록도 Q1과 같은 `block_answer`를 쓴다. 항목이 5개라 리스트 카드 한도(5개) 안이다.

### 확인한 것·확인하지 못한 것 (에이전트 결과)

V1·R6b, 그리고 에이전트 모드의 R9가 쓴다. 값은 `AgentFinal.checked`·`unchecked`다(§7.6).
줄 모양은 R9와 같다. `checked`는 `- {무엇}`, `unchecked`는 `- {무엇} ({이유})`이고, 하나도 없으면 `- 없음`.

| `item` | 무엇 |
| --- | --- |
| `message_text` | `문자 내용` |
| `screenshot_text` | `캡처 속 글자` |
| `transcript` | `통화 내용 (받아 적은 글)` |
| `link_address` | `문자 속 주소` |
| `official_domain` | `주소가 공식 주소인지` (확인했으면 R9 주소 줄 문장을 그대로 쓴다) |
| `domain_age` | `주소가 만들어진 때` |
| `page_static` | `페이지 내용` |
| `page_rendered` | `페이지 화면 (직접 열어 본 화면)` |

| `reason` | 괄호 안 이유 |

| `skipped_enough_evidence` | `근거가 충분해 더 보지 않았어요` |

| `not_allowed` | `페이지를 열지 않기로 하셨어요` |
| `no_link` | `링크가 없는 문자예요` |

- `actual_sender`는 항상 `cannot_verify`로 온다(§7.6). R9의 "보낸 곳은 항상 `확인하지 못한 것`에 넣는다"와 같다.
- V1의 받아 적기는 틀릴 수 있어서 `받아 적은 글이 정확한지 (말을 글로 옮겨 틀릴 수 있어요)`를 늘 넣는다. 이 줄은 `transcript_accuracy` 칸에서 온다(2026-10-29).
- V1도 `similar_cases` 줄을 위 표대로 넣는다(2026-10-30, 비슷한 사례를 다시 넣음). 녹음 캐러셀의 사례 장과 어긋나지 않게 두 경우는 따로 쓴다.
  - 검색은 끝났지만 `matches`가 비었으면 AI가 `checked`로 보내도 `확인하지 못한 것`에 `- 비슷한 사례 (비교할 사례를 찾지 못했어요)`로 넣는다. 사례 장이 빠지는데 `확인한 것`에 있으면 무엇을 확인했는지 알 수 없다.
  - 이유가 `failed`면 `열지 못했어요` 대신 `- 비슷한 사례 (사례를 찾다가 문제가 생겼어요)`로 쓴다. `열지 못했어요`는 페이지용 문구다.
- V1은 `number_checks`(상대가 말한 번호를 대표번호 KB와 대조한 결과)가 있으면 `phone_number` 줄 대신 아래 줄을 쓴다(2026-10-29). 번호가 여러 개면 최대 2줄.

  | `number_checks[].result` | 넣는 곳 | 줄 |
  | --- | --- | --- |
  | `not_official` | 확인한 것 | `- 상대가 말한 번호({number}): {org} 대표번호가 아니에요` |
  | `official` | 확인한 것 | `- 상대가 말한 번호({number}): {org} 대표번호와 같아요 (번호가 같아도 본인이라는 뜻은 아니에요)` |
  | `org_not_listed` | 확인하지 못한 것 | `- 상대가 말한 번호가 {org} 번호인지 (대표번호 자료에 없는 기관이에요)` — "공식이 아니다"로 쓰지 않는다 |
- V1에서 말한 사람을 나누지 못하면(2026-10-29, PR #114 멘토 리뷰 2번) `확인하지 못한 것`에 아래 두 줄을 넣는다.
  누가 말한 번호인지 몰라 번호 대조도 하지 않기 때문이다. `call_claims` 말머리도 바뀐다(3절 V1).
  - `- 누가 한 말인지 (말한 사람을 나누지 못했어요)` (`speaker`, `speaker_unknown`)
  - `- 통화에 나온 전화번호 (말한 사람을 나누지 못했어요)` (`phone_number`, `speaker_unknown`. 통화에 번호가 나왔을 때만)
- 한 사람만 말한 녹음(음성메시지 등)은 나누지 못한 것으로 보지 않는다. 그 사람을 상대로 보고 평소 문구를 쓴다.
  지금 AI는 녹음에서 두 사람의 말이 모두 나오지 않으면 실패로 보는 것 같다(`transcript.py` `_split_untrustworthy`). `speaker`, `speaker_unknown`과 함께 AI에 요청했다(#116).
- 결론을 '안전' 쪽으로 옮기는 말은 쓰지 않는다. `user_answer`가 `is_person`이어도 `확인한 것`에 답을 적을 뿐이다(§6.2).

## 4. 자세히 보기 캐러셀 3장

R1에서 진입한다. 순서는 `의심 근거 → 확인 범위 → 행동 안내`이고,
**버튼은 C3에만 단다**(`chatbot-flow.md` 3절).
이슈 #69로 C3 뒤에 공식 확인 방법(C4)을 0~3장 붙이고, R9에서도 진입하게 한다(아래 C4).
캐러셀 본문은 **128자 안**으로 맞춘다. `textCard` 캐러셀 한도가 128자다.

C1·C2의 대괄호 칸은 BE가 채운다. **결과의 `details.signals`(검증을 통과한 근거)만 쓴다**
(`docs/scheme.md` 1절). 근거가 입력에 없는 LLM 문장은 넣지 않는다(CLAUDE.md 절대 원칙 2).
`reason.text`는 카드에 옮기지 않는다(`result-meaning-cases.md` 6절 8).

### 빈칸 채우는 규칙

| 칸 | 값 |
| --- | --- |
| `signal_title` | 아래 표에서 `signals[].code`에 맞는 제목 |

| `account_recruitment` | `통장 모집` | `일자리나 대가를 내세워 통장이나 체크카드를 빌려 달라고 하는 수법이에요.` | 113 |
| `other_impersonation` | `그 밖의 사칭` | `택배사나 출입국사무소 같은 곳인 척하며 돈이나 개인정보를 요구하는 수법이에요.` | 118 |
| `other` | `보이스피싱` | (빈 문자열. 남는 빈 줄은 BE가 정리한다) | 73 |

- 가장 닮은 사례 하나(`similar_cases.matches[0]`)의 유형만 쓴다.
- `matches`가 비었거나 `similar_cases`가 `null`이면 **이 장을 통째로 뺀다.**
- 대본은 보여 주지 않는다. 저장소의 사례 127건은 모두 합성 대본이고, 실제 대본은 재배포 허락이 없다(`ai/src/ai/kb/voice_cases/README.md`). 그래서 `실제 사례`가 아니라 `예시 통화`라고 쓴다.
- 닮은 정도(`similarity`)는 숫자로 쓰지 않는다. 보이스피싱일 확률이 아니고 판정에도 쓰지 않는다. 마지막 두 줄이 이 점을 알린다.
- 지금 AI 결과의 `matches[]`에는 `case_id`, `similarity`만 있고 `type`이 없다. `type`을 함께 실어 달라고 AI에 요청한다.

같은 캐러셀 1번째 장(의심되는 말)의 마지막 줄은 `{{ claim_note }}`로 바꿨다(2026-10-30). 예전 고정 문장 `상대 화자의 말만 근거로 썼어요.`는 말투가 어색하고, 말한 사람을 가리지 못한 경우(#116)에는 맞지 않는다.

| 경우 | `claim_note` |
| --- | --- |
| 평소 | `통화 상대가 한 말만 근거로 썼어요.` |
| `unchecked`에 `speaker`가 있을 때 | `누가 한 말인지 가리지 못해 통화에 나온 말을 옮겼어요.` |

## 5. 이미지 현황과 후속 검토

`kakao-fe-be-integration.md` 2절 기준으로 R1~R4·R6·R7 카드는 이미 관리자센터에 있다.

응답이라 글자만 보낼 수 있다(3절 R5). 관리자센터 카드와 이미지가 필요 없다.

### 실기기 확인 항목

카드 길이와 핵심 버튼 위치는 FE가 조정할 수 있다. 카카오의 하단 메뉴와 입력창 위치는

| --- | --- |
| 첫 화면에서 핵심 버튼이 보이는가 | 카드가 도착한 직후 스크롤 없이 제목과 첫 버튼이 보인다 |

## 6. 이모지 정책

| 규칙 | 이유 |
| --- | --- |
| 카드 제목에 최대 1개, 본문에 최대 1개 | 더 넣으면 안내문이 장식으로 읽힌다 |
| **버튼에는 쓰지 않는다** | 버튼 8자(가로 2개) 한도를 이모지가 잡아먹어 가로 배치가 깨진다 |
| **R1은 `⚠️` 하나만** | 위험 결과에 다른 이모지가 붙으면 심각도가 희석된다 |
| 실패·거절 화면(R3·R4·R6·R7·E1)은 사용자를 탓하지 않는 이모지 | `❌` `🚫`는 사용자 잘못으로 읽힌다 |
| **의심 결과는 시나리오와 상관없이 `⚠️`** (R1·V1·R6b 주의), 주의 갈래는 `🔎`, 판단 보류는 `🤔` (2026-10-21) | 같은 무게의 결론은 같은 표시로 읽히게 한다. 시나리오마다 다른 이모지를 쓰면 심각도가 달라 보인다 |
| 급한 행동 안내는 `🚨` (B2b·K6) | 결론이 아니라 지금 할 일이라는 표시다 |

W1 `🛡️`(문자·전화 둘 다 지키는 첫 화면), R2 `🔗`(주소 대조 결과. `✅`는 "안전 확인"으로 읽혀 쓰지 않는다), Q1 `🙋`, C2 `❔`, C3 `📵`(B2a·녹음 C3과 같은 "하지 마세요" 표시) (2026-10-29), 녹음 캐러셀 비슷한 사례 `📚`, Q2 `📞` (2026-10-30). C1 제목은 BE가 채운다.
글자수는 파이썬 `len()` 기준으로 셌다. 카카오가 이모지를 2자로 세는지는 확인하지 못했다.
