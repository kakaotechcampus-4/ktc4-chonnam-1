## 3. 화면별 문구

글자수는 스크립트로 셌다(줄바꿈 제외). 한도는 `kakao-chatbot-build-guide.md` 7절
(제목 50자 / basicCard 본문 230자 / textCard 본문 400자 / 버튼 14자·가로 2개면 8자).
**이모지는 카드 제목과 본문에만 쓰고 버튼에는 쓰지 않는다.** R1은 `⚠️` 하나만 쓴다.
본문의 `[ ]`는 나중에 채울 자리다. 버튼과 헷갈리지 않도록 버튼은 따로 적는다.

### W1 웰컴

| | |
| --- | --- |
| 제목 | `문자 속 링크, 누르기 전에 확인해요` (20자) |
| 본문 | `반가워요, 문자 확인을 도와주는 화기니예요.`<br>`의심스러운 문자를 보내주시면,`<br>`링크를 확인해 결과와 이유를 알려드려요.` (62자) |
| 버튼 | `스미싱 확인하기`(8) → B1 / `개인정보 처리 안내`(10) → W2 — **세로 배치** |

`동의` 버튼은 두지 않는다. 동의는 W3에서만 받는다(`chatbot-flow.md` 9절 (1)).
이미지는 2026-10-13에 확정 자산(`assets/cards/w1-welcome.png`)을 넣었다.

2026-10-15에 본문을 실기기 폭에 맞춰 줄을 나눴다. 옛 문구는 27자·33자 줄이 단어 중간에서 끊겼고,
`확인하고, 확인한 내용을`처럼 `확인`이 겹쳤다. 무엇을 알려 주는지 드러나게 `결과와 이유`로 쓴다.
`근거와 함께 알려드려요`는 알려 줄 대상이 빠져 어색하고 말이 딱딱해 쓰지 않았다.
이전 초안에 있던 한계 문장(`안전하다고 보장해 드리는 건 아니에요`)은 개정본에서 빠졌다(8절 검토 항목).

### W2 개인정보 처리 안내

| | |
| --- | --- |
| 제목 | `🔒 개인정보 처리 안내` (12자) |
| 본문 | `문자 내용과 링크를 확인에 사용해요.`<br>`이때 일부 정보를 외부 분석 서비스로 보내요.`<br><br>`자세한 내용은 아래 버튼에서 확인해 주세요.` (69자) |
| 버튼 | `처리 내용 자세히 보기`(12) → W2a / `스미싱 확인하기`(8) → B1 — **세로 배치** |

정보를 보는 화면이다. 동의는 W3에서만 받는다.

2026-10-15에 실기기 폭에 맞춰 고쳤다. 31자였던 둘째 문장이 단어 중간에서 끊겼고, 줄만 나누니
긴 줄 뒤에 짧은 줄 둘이 와서 문장이 끊겨 보였다. 문장마다 한 줄에 들어가게 다듬었다.
- `보내주신`은 뺐다. 사용자가 보낸 문자라는 것은 말하지 않아도 알 수 있다.
- `전송돼요`를 W2a의 `아래 서비스로 보내요`와 맞춰 `보내요`로 바꿨다.
- 알리는 내용(사용하는 정보, 외부 전송 사실, 상세는 버튼)은 그대로다. `확인에만` 같은 새 약속은 넣지 않았다.
- 안내와 버튼 유도 문장 사이에 빈 줄을 넣었다.

마지막 줄은 W2a에 보관 기간(`retention`)이 들어가면 `전송 정보와 보관 기간은 아래 버튼에서 확인해 주세요.`(24자)로 바꾼다.
버튼을 누를 이유가 분명해진다. 지금 W2a는 보관 기간을 "정식 출시 전에 안내"로 미뤄 두어,
지금 바꾸면 안내한 내용이 버튼 뒤에 없다. 그래서 2026-10-15에는 `자세한 내용은 …`을 유지했다.

현재 BE 코드는 원문 발화를 로그에 출력하고 URL을 외부 urlscan에
`visibility=public`으로 전송한다. 이는 `docs/PRD.md`의 비공개 분석 전제와도
다르므로 BE·PM 확인이 필요하다.
그래서 “확인이 끝나면 바로 지운다”, “따로 보관하지 않는다”는 문장을 아직
사용자에게 약속할 수 없다. W2·W2a는 정책·구현 확인 전까지 배포 대상이 아니다.

### W2a 개인정보 처리 상세 (신규)

| | |
| --- | --- |
| 제목 | `🔒 개인정보 처리 상세 안내` (15자) |
| 본문 | `지금은 시험 운영 중이에요.`<br>`확인을 위해 아래 서비스로 보내요.`<br><br>`- 링크: 외부 검사 서비스(urlscan.io)`<br>`- 문자 내용: AI 분석 서비스`<br><br>`링크 검사 서비스는 시험 운영 기간에만 써요.`<br>`처리 방침은 정식 출시 전에 안내해 드릴게요.` (129자) |
| 버튼 | `스미싱 확인하기`(8) → B1 |

**2026-10-14 시험 운영 문구로 바꿨다.** urlscan은 시험 기간에만 쓰고 출시 때는 자체 격리 서버로 바뀌므로,
정식 처리 방침(사용 항목, 전송 항목·공개 범위, 보관 기간·삭제 요청 방법)은 출시 전에 쓴다. 그때까지는 사용자 테스트
참가자가 지금 무엇이 어디로 가는지만 알 수 있게 한다. 문자 내용을 AI 분석 서비스로 보내는 것은 출시 뒤에도 남는다.
이전 안의 빈칸(`used_info` `sent_info` `retention`)은 쓰지 않는다. 정식 방침을 쓸 때 다시 정한다.
개정본에는 이미지 자리가 있으나 자산이 정해지지 않았다. 이미지가 없으면 텍스트 카드로 보낸다(5절).
2026-10-15에 실기기에서 읽기 쉽게 고쳤다. 긴 한 문장에 두 가지 전송을 담아 줄을 어디서 나눠도 어색해서,
무엇이 어디로 가는지를 `- 항목: 서비스` 목록으로 나눴다. 옛 문구의 `임시 확인`은 urlscan을 시험 기간에만
쓴다는 뜻이라 `링크 검사 서비스는 시험 운영 기간에만 써요.`로 풀어 썼다(AI 분석은 출시 뒤에도 남는다).
`자세한 처리 방침은`의 `자세한`은 줄 길이 때문에 뺐다. 정식 방침을 쓸 때 다시 고친다.

  개정본 R2에는 이 문장이 없고 `자세히 보기`도 없다. 마지막 두 줄이 같은 역할을 하는지
  사용자 테스트로 확인한다(8절).
- 개정본에는 이미지 시안이 있다. 이미지가 안전 표시로 읽히지 않는지 함께 본다(5절).

### R3 확인할 정보가 부족함

버튼은 `chatbot-flow.md` 3절대로 둔다. 본문 첫 줄은 개정본 원문(`스미싱 여부`)을 따른다.
사용자가 궁금한 것은 주소가 아니라 스미싱인지 여부다.

| | |
| --- | --- |
| 제목 | `🧐 확인할 정보가 부족해요` (14자) — 이전 초안 |
| 본문 | `보내주신 내용만으로는 스미싱 여부 확인이 어려웠어요.`<br>`문자를 자르지 말고 전체를 그대로 다시 보내주세요.` (57자) — 개정본 |
| 버튼 | `다시 보내기`(6) |

`자세히 보기` 버튼은 R1과 같은 이유로 2026-10-02에 뺐다. 되살릴 때는 캐러셀이 R1 기준(의심 근거)이라
R3에서 열 때 C1·C2에 무엇을 보여줄지 먼저 정해야 한다(7절).

### R4 확인을 못 마침

| | |
| --- | --- |
| 제목 | `🙏 이번에는 확인하지 못했어요` (16자) |
| 본문 | `결과를 드릴 수 없어 확인을 멈췄어요.`<br>`문자를 잘못 보내신 게 아니에요.`<br><br>`잠시 뒤 문자를 다시 보내 주세요.`<br><br>`※ 확인 전까지 링크는 누르지 마세요.` (79자) |
| 버튼 | 없음 |

- 개정본은 `다시 시도` 버튼(서버가 같은 문자를 다시 검사)을 두었다. 재검사는 BE 구현이 필요한데
  이번 연결 범위에 넣지 않아서(2026-10-01), 버튼을 빼고 마지막 줄을 문자를 다시 보내 달라는 안내로 바꿨다.
  재검사를 구현하면 `다시 시도`(5) → `{{ block_retry }}` 버튼을 달고, 본문의 `잠시 뒤 문자를 다시 보내 주세요.`를
  `잠시 뒤에 다시 시도해 주세요.`로 바꾼다. 버튼 없이 문구만 바꾸면 누를 곳이 없으므로 둘을 같이 바꾼다.
- 2026-10-13: 옛 제목 `지금은 확인을 못 마쳤어요`가 분석 중(R5)과 구분되지 않아 끝났다는 말로 바꿨다.
  첫 줄에 결과가 더 오지 않는다는 뜻을 넣었다. 확인을 못 했을 뿐인데 안전하다고 오해해 링크를 누르지
  않도록 경고 줄을 더했다. 이모지는 R1(⚠️)과 겹치지 않게 🙏를 유지한다.
- 개정본의 `보내주신 문자에는 문제가 없어요`는 분석 실패 상황에서 문자가 **안전하다는 뜻으로 읽혀**
  `문자를 잘못 보내신 게 아니에요.`로 바꿨다 (PR #39 멘토 리뷰, `kakao-fe-be-integration.md` 3절).
  문자의 안전이 아니라 사용자의 행동을 말한다. 관리자센터 원본도 같은 문장으로 바꿔야 한다.
- 개정본 첫 줄 `저희 쪽 문제로 확인을 끝내지 못했어요.`는 제목과 같은 말이라 뺐다. 실패 원인을
  모두 우리 쪽으로 단정할 수도 없다(링크가 만료된 경우 등).

R3과 R4를 나누는 이유는 **사용자가 할 일이 다르기 때문**이다.
R3은 "보낸 것에 확인할 게 없다"(사용자 조치 필요), R4는 "우리 쪽이 못 했다"(그대로 재시도).
문구에서 내부 상태 이름(`판단 보류` `처리 실패`)은 쓰지 않고 원인만 다르게 쓴다.

### R5 분석 중 (첫 응답)

**카드가 아니라 글자만 보낸다.** 콜백 대기 응답은 `useCallback: true`와 `data.text`만
담고 `template`을 넣지 않는다([카카오 AI 챗봇 콜백 개발 가이드](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/ai_chatbot_callback_guide)).
바로연결(`quickReplies`)도 `template` 안에 있으므로 제목·버튼·바로연결을 쓸 수 없다.

| | |
| --- | --- |
| `data.text` · 관리자센터 대기 메시지 | `⏳ 문자 속 링크를 확인하고 있어요.`<br>`확인이 끝나면 이 채팅창으로 결과를 보내드릴게요.`<br>`기다리는 동안 문자 속 링크는 누르지 마세요.`<br>`결과가 오지 않으면 「결과 확인」이라고 보내 주세요.` (101자) |
| 버튼 (개정본) | `스미싱 판정 결과 확인`(12) → K — **이 응답에는 달 수 없다** |

개정본의 버튼과 마지막 줄 `‘결과 확인’ 버튼을 눌러주세요`는 위 제약과 부딪혀서, 마지막 줄을
`결과가 오지 않으면 ‘결과 확인’이라고 보내 주세요.`로 바꿨다(2026-10-01 BE 지적, PR #39 멘토 리뷰).
BE의 결과 확인 로직이 준비돼 실제로 가능한 행동이다. `결과 확인` 버튼은 보통 스킬 응답(K1·K5)의
바로연결로만 달 수 있다. 그래서 처음 한 번만 입력하면 그다음부터는 바로연결을 누르면 된다.
`스미싱 판정 결과 확인`도 K 블록 발화에 넣어 둔다.

**사용자에게 보이는 대기 문구는 관리자센터 폴백 블록의 `Callback 설정` 대기 메시지다(2026-10-06 확인).**
그전에는 콜백만 켜져 있고 대기 메시지 칸이 비어 있어서, BE가 `data.text`를 보내도 아무것도 보이지 않았다.
2026-10-06에 칸을 채워 배포한 뒤 개발 채널(@클릭전확인)에서 대기 문구가 표시됐다.
표시된 마지막 줄이 관리자센터 문구(`「결과 확인」`)였으므로 BE의 `data.text`(당시 `‘결과 확인’`)는 화면에 나오지 않는다.
**문구를 바꿀 때는 관리자센터 대기 메시지를 고친다.** `r5-analyzing.json`의 `data.text`는 같은 문장으로 맞춰 둔다.

개정본이 참고한 보호나라 챗봇은 첫 응답을 **일반 카드 + 버튼**으로 보내고 결과는 사용자가 버튼을
눌러 가져가게 한다(콜백 미사용). 분석이 최대 10분이라 콜백 주소 유효 시간(5분)을 넘기 때문으로 보인다.
우리는 45초 안에 끝나 콜백으로 결과를 보낼 수 있어서 콜백을 유지한다(ADR 0003, 2026-10-02 결정).
버튼 방식으로 바꿀지는 팀 회의에서 다시 볼 수 있다.

공식 도메인이어도 이 화면을 거친다. 공식 주소 즉답(D2)은 구현되지 않았다(2026-10-13 기준).
`기다리는 동안 문자 속 링크는 누르지 마세요`가 이 화면의 핵심이다 — 대기 중 사용자가
링크를 눌러버리는 것이 가장 큰 위험이다. `data.text`의 글자수 한도는 문서에 없다.
실기기에서 줄바꿈과 잘림을 확인한다.

개정본 R5 아래에 붙은 참고 시안("최대 10분 이후 아래 버튼을 클릭해서…")은 참고 자료로 보고 문구에 넣지 않았다.
우리 대기 상한은 45초다(`main.py` `CALLBACK_DEADLINE_SECONDS`). `latency-budget.md`의 60초는 그 전 값이다.

### K 결과 확인

사용자가 `결과 확인`이라고 보내거나 바로연결 `결과 확인`을 누르면 스킬이 답한다.
관리자센터에 `결과 확인` 블록을 만들고 스킬을 연결한다. 2026-10-02 "결과 카드" 시나리오에 만들었고
패턴 발화는 `결과 확인` `스미싱 판정 결과 확인` `결과 알려줘` `결과 어떻게 됐어` `확인 결과` `결과 보여줘` `결과 확인하기` 7개다.
`결과 확인하기`는 2026-10-06에 더했다. 하단 메뉴 `결과 확인`이 채팅창에 이 말을 보낸다. 등록 전에도 비슷한 말로 맞춰져
결과 확인 블록으로 갔지만, 빗나가면 폴백(R6)으로 빠지므로 정식으로 등록했다.
2026-10-02 BE가 기존 `/kakao/skill` 스킬을 연결했다. BE는 발화 글자가 아니라 요청의
`intent.name`(블록 이름)이 `결과 확인`인지로 이 블록을 알아본다. 발화를 더 넣어도 BE는 고치지 않는다.
`결과` 한 단어는 넣지 않았다. 스미싱 문자에 흔한 "검사 결과를 확인하세요" 같은 문장이
폴백(문자 확인) 대신 이 블록으로 갈 수 있어서다. 개발 채널에서 이런 문자가 폴백으로 가는지 확인한다.
BE는 카카오 사용자 ID로 **그 사용자의 가장 최근 작업**을 찾는다. 사용자가 작업 번호를
입력하지 않는다. 작업 상태는 BE PR #40의 `running` `completed` `timeout` `failed`를 따른다.

**K1 아직 확인 중** (`running`)

| | |
| --- | --- |
| 제목 | `⏳ 아직 확인하고 있어요` (13자) |
| 본문 | `잠시 뒤 '결과 확인'을 다시 눌러 주세요.`<br>`그동안 문자 속 링크는 누르지 마세요.` (46자) |
| 바로연결 | `결과 확인`(5) |

2026-10-15에 실기기 폭에 맞춰 첫 줄을 줄였다. 옛 문구 `조금만 기다렸다가 다시 '결과 확인'을 눌러 주세요.`는
29자라 두 줄로 넘어갔다. `조금만 기다렸다가`를 `잠시 뒤`로 줄였다(24자). R4의 `잠시 뒤 문자를 다시 보내 주세요.`와 같은 말이다. 다시 누르라는 안내는 그대로다.

"결과가 나오면 바로 알려드릴게요"는 쓰지 않는다. 콜백 주소가 만료됐으면 결과가 알아서
오지 않는다.

**K2 결과 다시 보기** (`completed`)

- 첫 말풍선(`simpleText`): `{HH:MM}에 확인한 결과예요.` — 한국 시간
- 이어서 저장한 결과 카드(R1~R3)를 그대로 보낸다. 말풍선은 한 응답에 최대 3개다.
- 다시 분석하지 않는다. 확인 시각을 붙이는 이유는 이 결과가 **그 시각의 페이지 상태**라서다.

**K3 확인 실패** (`timeout` `failed`)

- R4 카드를 그대로 보낸다. 실패를 위험 근거처럼 말하지 않는다(`result-meaning-cases.md` 4절 사례 5).

**K4 결과 없음** (작업을 찾지 못함)

| | |
| --- | --- |
| 제목 | `📭 확인 결과를 찾지 못했어요` (16자) |
| 본문 | `확인할 문자를 다시 붙여넣어 보내주세요.` (22자) |
| 버튼 | `다시 보내기`(6) → B1 — R3과 같은 이름. 처음 시작이 아니라 다시 보내는 상황이다 |

"보낸 문자가 없어요"라고 쓰지 않는다. 지금 BE 작업 저장소는 메모리에만 있어서 서버가
재시작하면 보낸 문자의 결과도 사라진다. 사용자를 탓하는 문장이 되면 안 된다.

**K5 중복 요청** (`running` 중에 새 문자를 보냄)

| | |
| --- | --- |
| 제목 | `⏳ 앞서 보낸 문자를 확인하고 있어요` (20자) |
| 본문 | `한 번에 문자 1개씩 확인해요.`<br>`결과가 나온 뒤에 새 문자를 보내주세요.` (40자) |
| 바로연결 | `결과 확인`(5) |

새로 보낸 문자는 분석하지 않고 보관하지도 않는다. 지금 BE는 같은 상황에
`simpleText`("이전 요청을 아직 확인하고 있어요…")로 답한다. 이 카드로 바꾼다.
대기 응답(R5)과 달리 보통 스킬 응답이라 바로연결을 달 수 있다.

### R6 확인할 주소 없음 (엣지 3)

| | |
| --- | --- |
| 제목 | `🔗 확인할 링크가 없어요` (13자) |
| 본문 | `그래서 이번에는 검사하지 않았어요.`<br>`링크가 없다고 안전한 건 아니에요.`<br><br>`문자 속 번호로 전화하거나 앱을 설치하지 마세요.`<br>`보낸 기관의 공식 앱·홈페이지·대표번호로 직접 확인하세요.`<br><br>`링크가 있는 문자라면 전체를 복사해 다시 보내 주세요.` (127자) |
| 버튼 | `신고·상담하기`(7) → B2 / `다른 문자 확인하기`(10) → B1 — **세로 배치** |

2026-10-05 멘토 리뷰(PR #39, 10/3)로 바꿨다. 이전 문구는 다시 보내 달라고만 해서,
전화·송금·앱 설치를 요구받은 사용자가 다음에 할 일을 알 수 없었다.

> "링크가 없다는 이유로 안전하다고 볼 수는 없습니다. (…) 링크가 실제로 없는 문자에
> 재입력만 요구하지 않도록 해 주세요."

- 순서: 검사하지 않은 사실 → 안전하다는 뜻이 아님 → 할 일 → 다시 보내는 방법.
- 가짜 고객센터로 전화하게 한 뒤 원격제어 앱을 깔게 하는 수법이 있어서 전화와 앱 설치를 직접 막는다.
- **"스미싱으로 보여요" 같은 문장을 쓰지 않는다(D5).** 관측이 0건이라 방어할 근거가 없다.
- BE는 잡담(`배고파`)과 링크 없는 문자를 아직 구분하지 못해 둘 다 이 카드를 받는다(D4).
  그래서 제목을 `이 문자에는`이 아니라 `확인할 링크가 없어요`로 썼다.
- 이전 본문의 `300자 이상` 줄은 BE 입력 길이 기준이 없어 뺐다(7절).
- 본문의 요구 행동(전화·송금·앱 설치)을 분석하는 기능은 URL 검사와 따로 반환하도록
  BE·AI에 요청한다. 그 전까지 이 카드는 문자 내용을 언급하지 않는다.

AI 유형 참고 칸을 쓸 경우 `smishing-message-intake-ux.md` 3절의 네 가지 제약
(어휘 차단 / 상태 불변 / 없으면 안 그림 / 형식 서술만)을 그대로 적용한다.

### R7 주소가 여러 개

| --- | --- |
| 제목 | `🔗 주소가 여러 개예요` (12자) |
| 본문 | `주소가 1개일 때만 확인할 수 있어요.`<br>`확인하고 싶은 주소 1개만 남겨서 다시 보내주세요.` (49자) |
| 버튼 | 없음 |

범위 제한이 원인이라는 것을 문장에서 드러낸다. "내 문자가 이상한가"로 읽히면 안 된다.
다중 주소를 구현하면 이 화면만 지우면 된다.
카드는 이미 관리자센터에 있으나 `kakao-fe-be-integration.md` 2절 기준으로
**BE 전달 JSON 범위에는 아직 포함되지 않았다.**

### R8 공식 주소 아님 (신규, 임시)

조건: 검증된 위험 근거(`signals`)가 없고 `url.official == "brand_mismatch"`
(`result-meaning-cases.md` 4절의 S1-목록 외). 2026-10-01 BE 연결용으로 추가했다.

| | |
| --- | --- |
| 제목 | `🔎 공식 주소가 아니에요` (13자) |
| 본문 | `문자 속 링크 대신 공식 앱이나 홈페이지에서 직접 확인하세요.`<br>`문자 속 택배사({{ org_name }})의 공식 주소 목록에 이 주소가 없어요.`<br>`주소만으로는 위험한지 알 수 없어요.` (`org_name` 6자 기준 92자) |

- `message.brand`가 `unknown`이면 R8을 쓰지 않는다(R9로 보낸다). `org_name`에 `unknown`을 넣지 않는다.
  `brand_mismatch`는 택배사를 알아냈을 때만 나오므로, 조건대로 고르면 이 경우는 생기지 않는다.
- **목록에 없다는 이유만으로 "위험"이나 "사칭"이라고 말하지 않는다**(PR #39 멘토 리뷰). 제휴사 주소일 수 있다.
- 첫 줄은 결론 다음의 행동이다. 제목이 결론("공식 주소가 아니에요")이다.

### R9 판단 보류 (신규, 임시)

조건: 검증된 위험 근거가 없고 R8이 아닌 나머지
(`url.official`이 `official` · `not_registered` · `unresolved`(세부 사유 `shortener_unresolved` · `redirected_from_official` 포함), 또는 `brand_mismatch`인데 택배사를 모를 때).
2026-10-01 BE 연결용으로 추가했다.

카드는 하나이고, 첫머리만 **문자에서 의심 정황을 확인했는지**에 따라 두 갈래로 나뉜다(2026-10-15, PR #86 멘토 리뷰 5번).

예시 (의심 정황 있음, 택배사가 아닌 기관):

```
링크를 누르거나 정보를 입력하지 마세요.

- 내세운 명분: '쓰레기 무단투기 신고가 접수되었습니다'

- 없음

```

2026-10-05 멘토 리뷰(PR #39, 10/3)로 빈칸 방식으로 바꿨다. 이전 본문의 `이번 확인에서 위험 근거는 찾지 못했지만`은
문자 분석을 끝내지 못한 경우에도 나가서, 검사 후 근거가 없었다고 읽혔다.

> "사용자에게는 문자에서 확인한 사실, 검사하지 못한 부분, 문자에 적힌 링크나 연락처를 쓰지 않고
> 해당 업무를 확인할 방법을 알려주면 됩니다."

> "완료 여부와 함께 실제 확인한 사실을 렌더러에 전달하면 같은 보류 결과에서도 정확한 설명을 만들 수 있습니다."

2026-10-15 멘토 리뷰(PR #86, 10/15)로 첫머리를 두 갈래로 나누고, 결론과 다음 행동을 확인 범위보다 앞에 뒀다.

> "상태를 하나 더 만드는 것보다, 첫 안내를 읽고 어떻게 대응해야 할지 알 수 있는지가 더 중요하다고 생각합니다.
> 현재 문자에서 의심 정황이 확인됐다면 '주의가 필요한 문자예요'라는 판단과 함께, 어떤 행동을 멈추고
> 어디에서 확인하면 되는지를 먼저 안내하면 좋겠습니다."

**의심 정황을 확인했다고 보는 조건**

아래 두 가지를 모두 만족하면 `의심 정황 있음`이다.

1. `message.details.doubts`의 `value`에 아래 **민감한 요구 행동** 중 하나 이상이 있다.
2. `url.official`이 `official`이 아니다.

| 민감한 요구 행동 (`doubts.value`) | 멈출 행동 (이어 붙일 때) |
| --- | --- |
| `정보 입력` | `정보를 입력하` |
| `본인 확인` | `본인 인증을 하` |
| `앱 설치` | `앱을 설치하` |
| `금전 인출` | `돈을 보내` |
| `전화 응대` | `문자 속 번호로 전화하` |
| `주소 입력·수정` | `주소를 입력하` |

- `doubts`는 고정 규칙이 찾은 요구와 원문 검증을 통과한 신호에서 나오고, 항목마다 문자 원문 인용(`evidence`)이 붙어 있다
  (`ai/src/ai/pipeline/results.py` `build_message_part`). 그래서 "문자에 실제로 적힌 요구"로 쓸 수 있다.
  판정에는 쓰지 않고 첫머리를 고르는 데만 쓴다(CLAUDE.md 원칙 1·2).
- `배송 조회`·`링크 접속`·`상세 내용 확인`·`수령·일정 확인`·`사진 확인`·`주문 취소·환불`은 민감한 요구로 보지 않는다.
  진짜 택배 문자에도 흔해서, 넣으면 대부분의 R9가 `주의가 필요한 문자예요`가 된다.
- 기관·지역을 모른다는 것, 알려진 사례와 닮았다는 것만으로는 `의심 정황 있음`으로 보지 않는다
  (PR #86 멘토 리뷰 처음 문장, `ai/tests/test_revision_results.py` "유사도만으로 위험 근거를 만들지 않는다").
- **공식 주소와 같으면 제외한다 (2026-10-15 결정, A안).** 진짜 택배사가 공식 주소로 "주소를 확인·수정해 주세요"라고
  보내는 경우가 흔해서, 넣으면 진짜 문자에 경고가 나가고 아래 `확인한 것`의 `주소가 {brand} 공식 주소와 같아요`와
  말이 엇갈린다. 공식 주소를 악용한 사기에서는 제목이 약해지는 단점이 있지만, 이 카드는 어느 갈래든
  "링크 대신 공식 앱·홈페이지에서 확인하라"고 안내하므로 행동 안내는 빠지지 않는다. 실제 문자에서 이 조합이
  얼마나 나오는지는 AI와 확인한다. `redirected_from_official`(공식 주소에서 다른 곳으로 이동)은 `official`이 아니므로
  제외하지 않는다.

**빈칸 채우는 규칙**

`headline`은 위 갈래 표의 제목이다.

`action_guide`

- `org_label`은 `message.brand`다. 없거나 `unknown`이면 `보낸 기관의`를 넣는다. 문자가 내세운 기관 이름(`청소행정과` 등)은
  넣지 않는다. 주장한 이름을 우리 안내 문장에서 되풀이하지 않기 위해서다. 구체적인 확인 경로는 자세히 보기의
  공식 확인 방법 카드(C4)가 보충한다.
- `의심 정황 있음`일 때 `{멈출 행동}`은 `링크를 누르`로 시작하고, `doubts`에서 민감한 요구 행동을 **원문 순서대로 최대 2개**
  골라 `거나 `로 이은 뒤 `지 마세요.`로 끝낸다. R9는 링크가 있는 문자만 오므로 `링크를 누르`는 늘 들어간다.
  - 1개: `링크를 누르거나 정보를 입력하지 마세요.`
  - 2개: `링크를 누르거나 정보를 입력하거나 앱을 설치하지 마세요.`
  - 3개 이상 이으면 첫 줄이 길어져 먼저 안내하는 효과가 약해진다. 나머지는 아래 `요구한 것` 줄에 다 나온다.
- `전화 응대`가 "전화를 걸라"는 요구인지 "걸려 올 전화를 받으라"는 요구인지는 AI와 확인한다.
  받으라는 뜻이면 `모르는 번호의 전화에 응하`로 바꾼다.

`message_claims`

문자가 **주장한** 내용을 모은 칸이다. 확인한 사실이 아니므로 `확인한 것`과 나눈다.
줄이 하나도 없으면 칸 전체(제목과 뒤 빈 줄 포함)를 빈 문자열로 둔다. 줄이 있으면 아래 모양이다.

```
{칸 제목}
- 내세운 기관: …
- 내세운 명분: '…'
- 요구한 것: …
(빈 줄)
```

| 줄 | 값 | 넣는 규칙 |
| --- | --- | --- |
| 내세운 기관 | `message.brand`가 있음 | `- 내세운 기관: {brand}` (따옴표 없이) |
| | 없거나 `unknown`, `reason.text`에 `문자가 내세운 기관: '…'`이 있음 | `- 내세운 기관: '…'` (원문 인용) |
| 내세운 명분 | `reason.text`에 `문자가 내세운 명분: '…'`이 있음 | `- 내세운 명분: '…'` |
| 요구한 것 | `doubts`가 있음 | `- 요구한 것: {value, value, value}` (원문 순서, 최대 3개, `unknown` 제외) |

- `reason.text`는 한 문자열이다(`ai/src/ai/pipeline/results.py` `build_message_part`). 렌더러가 문장 앞머리
  (`문자가 내세운 기관:`, `문자가 내세운 명분:`)로 골라 따옴표 안만 쓴다. AI 필드는 늘리지 않는다.
- `reason.text`의 요구 인용(`문자에서 '…'라고 안내했습니다.`)과 분석 실패 문장은 쓰지 않는다. 요구는 `요구한 것` 줄이,
  실패는 `확인하지 못한 것`의 `문자 내용 ({실패 이유})`가 이미 알린다(이슈 #76 겹침 정리).
- 인용은 30자를 넘으면 끝을 `…`로 줄인다. 본문 전체가 400자를 넘으면 `내세운 명분` 줄부터 뺀다.
  첫머리와 확인 범위가 먼저다.
- 이전 `문자에 적힌 내용` 칸(`{{ message_reason }}`, 이슈 #68)과 `확인한 것`의 `문자에 적힌 보낸 곳`·`문자에서 요구한 것`
  줄을 이 칸으로 합쳤다. 같은 말이 두 번 나오던 문제(이슈 #76)가 없어진다.
- 칸 제목은 `의심 정황 있음`이면 `주의할 점`, 없으면 `문자에 적힌 내용`이다. 진짜일 수 있는 문자의 주장을
  "주의할 점"이라고 부르지 않기 위해서다.

`checked`·`unchecked`는 아래 표의 문장을 `- `로 시작하는 줄로 만들어 위에서부터 이어 붙인다.
넣을 문장이 하나도 없으면 `- 없음`을 넣는다.

| 무엇 | 값 | `checked`(확인한 것) | `unchecked`(확인하지 못한 것) |
| --- | --- | --- | --- |
| 보낸 곳 | 항상 | — | `실제로 보낸 곳` |
| 주소 | `url.official` = `official` | `주소가 {brand} 공식 주소와 같아요` (택배사를 모르면 `주소가 공식 주소 목록에 있어요`) | — |
| | `not_registered`, 택배사를 모름 (`message.brand`가 없거나 `unknown`) | — | `주소가 공식 주소인지 (보낸 기관을 몰라 대조하지 못했어요)` |
| | `not_registered`, 택배사를 앎 | — | `주소가 공식 주소인지 (공식 주소 목록에 없는 기관이라 대조하지 못했어요)` |
| | `brand_mismatch` | `공식 주소 목록에 없는 주소예요` | — |
| | `shortener_unresolved` | — | `주소가 공식 주소인지 (단축 주소라 실제 주소를 확인하지 못했어요)` |
| | `redirected_from_official` | `문자 속 주소는 {brand} 공식 주소와 같아요` | `이동한 주소가 안전한지 (공식 주소에서 다른 주소로 이동했어요)` |
| | `unresolved` | — | `주소가 공식 주소인지` |
| 문자 | `message.answer` = `no_risk_found` | `문자에서 위험 신호를 찾지 못했어요` | — |
| | `partial` 또는 `failed` | — | `문자 내용 ({실패 이유})` — 아래 실패 이유 표 |
| | `not_run` | — | `문자 내용` |
| 페이지 | `env.answer` = `no_risk_found` | `페이지에서 위험 신호를 찾지 못했어요` | — |
| | `partial` | — | `페이지 내용 (끝까지 확인하지 못했어요)` |
| | `failed` | — | `페이지 내용 (열지 못했어요)` |
| | `not_run` | — | `페이지 내용` |

- **보낸 곳은 항상 `확인하지 못한 것`에 넣는다.** "검찰청이라고 주장한다"와 "검찰청이 보냈다"를
  구분하라는 멘토 리뷰(PR #39, `ai/src/ai/pipeline/results.py` 153줄 의견)를 따른다.
  문자가 내세운 기관은 `message_claims`의 `내세운 기관` 줄에만 둔다.
- 요구 행동은 사실 목록(`doubts`)이다. 위험 근거(`signals`)가 아니므로 "위험한 요구"라고 쓰지 않는다
  (`docs/scheme.md` 3절).
- **`확인한 것`에는 끝까지 검사한 결과만 넣는다.** 검사를 안 했거나, 실패했거나, 끝내지 못한 것은
  `확인하지 못한 것`에 넣고 괄호로 이유를 구분한다(2026-10-08 멘토 리뷰, PR #54 10/7:
  "검사를 하지 않은 경우, 검사에 실패한 경우, 검사는 끝났지만 목록에서 찾지 못한 경우를 같은 값으로 처리하면 안 됩니다").
- `not_registered`는 주소가 목록에 없다는 뜻이 아니라 **대조를 하지 못했다**는 뜻이다. 택배사를 몰랐거나,
  택배사가 공식 주소 목록에 없을 때 나온다(`services/official_domain_service.py`). 이전 규칙은 이것을
  `공식 주소 목록에 없는 주소예요`로 안내해, 목록에 있는 naver.com 주소에도 그렇게 나갔다(멘토 리뷰).
  실제로 대조해서 다른 `brand_mismatch`만 이 문장을 쓴다.
- **단축 주소·이동 보류 문장 (이슈 #66).** `shortener_unresolved`·`redirected_from_official`은 `unresolved`의 세부 사유로,
  판정상으로는 `unresolved`와 같고 카드 문구 선택에만 쓴다(`ai/src/ai/types.py` `DomainMatch`, `feature/rag-fix-final-ai` 8faa17d).
  아직 develop에는 없다.
  - 일반 문장 `주소가 공식 주소인지`만으로는 사용자가 왜 확인하지 못했는지 알 수 없어 이유를 붙였다.
  - 이동한 경우는 `확인한 것`에 공식 주소와 같다는 줄만 나가면 공식인데 왜 보류인지 읽히지 않아서, 이동한 주소를
    확인하지 못했다는 줄을 함께 넣는다.
- `partial`은 일부를 검사해 근거가 없었다는 뜻이 아니라 **분석을 끝내지 못하고 자료만 남은 상태**다
  (시간 초과 등, `ai/src/ai/pipeline/results.py` `_answer`). 이전 규칙의 `문자 일부에서 위험 신호를 찾지 못했어요`는
  분석을 마친 것처럼 읽혀서 뺐다. 어느 부분까지 끝났는지 결과에 담기면 그때 `확인한 것`에 넣을지 다시 정한다.
- 문자 분석을 못 끝낸 이유는 `message.details.reason.failures`의 **첫 번째** 값으로 고른다(#59).
  내부 코드는 카드에 보이지 않고 아래 문장으로만 바꾼다. 원본은 `services/chatbot_copy_data.py` `MESSAGE_FAILURE_COPY`.

  | `failures[0]` | 실패 이유 |
  | --- | --- |
  | `timeout` | `분석 시간이 초과되어 끝까지 확인하지 못했어요` |
  | `refused` | `분석 요청이 거절되어 확인하지 못했어요` |
  | `invalid_output` | `분석 결과를 올바르게 받지 못했어요` |
  | `llm_error` | `분석 중 오류가 발생해 확인하지 못했어요` |
  | `empty_input` | `링크만 있어서 확인할 글이 없었어요` |
  | `input_too_large` | `문자가 너무 길어 끝까지 확인하지 못했어요` |
  | 없음 또는 그 밖의 값 | `문자 분석을 완료하지 못했어요` |

  `empty_input`은 분석에 실패한 것이 아니라 **링크를 빼고 나니 읽을 글이 없었다**는 뜻이다(사용자가 링크만
  붙여넣은 경우). 기본 문구로 보내면 실패처럼 읽혀서 따로 둔다(멘토 리뷰 PR #54 10/7: 검사하지 않은 경우와
  실패한 경우를 같은 값으로 처리하지 않는다). `input_too_large`는 링크를 뺀 본문이 8,192자를 넘을 때다
  (`ai/src/ai/pipeline/analysis.py` `MAX_MESSAGE_CHARS`).
- R9에 오는 결과는 검증된 위험 근거가 없으므로 문자·페이지가 `risk_found`인 경우는 없다.
- 기한 줄은 의심 문자 링크를 피하라는 안내 때문에 실제 제출·납부 기한을 놓치지 않게 하려는 것이다
  (멘토 리뷰: "문자가 진짜인지와 실제 처분이 있는지는 별개입니다"). 다음 행동이므로 첫머리 바로 아래에 둔다.
- 소제목(`주의할 점`, `확인한 것` 등)에는 이모지를 쓰지 않는다(6절). `✅ 확인한 것`은 "안전이 확인됐다"로 읽힐 수 있다.
  본문이 회색이라 소제목이 눈에 덜 띄는 문제는 실기기 확인 때 `[주의할 점]` 같은 대괄호를 시험해 본다.
- **빈칸을 BE가 채우기 전에 이 카드가 배포되면 `{{ headline }}`이 글자 그대로 보인다.**
  렌더러는 값이 없는 빈칸을 남겨 두기 때문이다. BE 렌더러 변경과 함께 합친다.

- 페이지 수집기가 없는 지금은 공식 주소인 문자도 여기로 온다. 공식 주소와 같다는 것만으로
  정상이라고 하지 않는다(PR #39 멘토 리뷰, `result-meaning-cases.md` 6절 9).
- 2026-10-02 결정: 격리 환경이 붙기 전까지는 공식 주소여도 R9로 둔다. 격리 환경이 붙으면
  공식 주소인 경우를 R2로 보낼지 다시 정한다(`result-meaning-cases.md` 6절 9).

## 4. 자세히 보기 캐러셀 3장

R1에서 진입한다. 순서는 `의심 근거 → 확인 범위 → 행동 안내`이고,
**버튼은 C3에만 단다**(`chatbot-flow.md` 3절).
이슈 #69로 C3 뒤에 공식 확인 방법(C4)을 0~3장 붙이고, R9에서도 진입하게 한다(아래 C4).
캐러셀 본문은 **128자 안**으로 맞춘다. `textCard` 캐러셀 한도가 128자다.

C1·C2의 대괄호 칸은 BE가 채운다. **결과의 `details.signals`(검증을 통과한 근거)만 쓴다**
(`docs/scheme.md` 1절). 근거가 입력에 없는 LLM 문장은 넣지 않는다(CLAUDE.md 절대 원칙 2).
`reason.text`는 카드에 옮기지 않는다(`result-meaning-cases.md` 6절 8).

### C4 공식 확인 방법 (신규, 이슈 #69)

공식 기관이 안내한 확인 경로와 절차를 보여 준다. 값은 `ai.kb.guidance.find_guidance()`가 고른
`Guidance`다(검토를 마친 `norm_rules`만, 최대 3개, `verification`이 먼저). 판정 결과에 쓰지 않는 참고 정보다
(`ai/src/ai/kb/guidance.py`). 그래서 **결론을 붙이지 않는다.** "그러니 이 문자는 가짜예요" 같은 문장은 쓰지 않는다.

| | |
| --- | --- |
| 제목 | `📋 공식 확인 방법` (BE `c4-guidance.json`) |
| 본문 | `{{ guidance_text }}` |
| 버튼 | 없음 |

**`guidance_text` 채우는 규칙**

| `kind` | 값 | 예 |
| --- | --- | --- |
| `verification` | `text` 그대로 | `과태료·범칙금 문자 속 인터넷주소(URL)나 전화번호 대신, …직접 확인한다.` |
| `procedure` | 첫 줄 `{source}({연도})`, 둘째 줄 `text` 그대로. 연도는 `published_at` 앞 4자리, 없으면 괄호째 뺀다 | `로젠택배 공지 「택배 스미싱 문자 주의 안내」(2019)`<br>`로젠택배는 고객이 콜센터로 전화했을 때만 URL이 담긴 문자를 보낸다.` |

- 이슈 #69에서 정한 `{source}는 ~라고 안내했어요({연도})`는 쓰지 않는다. 2026-10-14 검토 완료 자료로 만들어 보니
  `text`가 `~않는다.`로 끝나 `…보내지 않는다.라고 안내했어요`가 됐다. `source`도 기관 이름이 아니라
  공지 제목(`인터넷우체국 공지 「…」`)이라 `~는`이 어색했다. 원문은 고치지 않고 출처만 앞에 둔다.
  지금 BE 코드(`services/result_card_renderer.py` `_guidance_description()`)는 옛 형식이라 바꿔야 한다.
- 새 형식이면 `procedure` 4개는 모두 128자 안(가장 긴 것 123자)이다.

**128자를 넘을 때** (이슈 #77)

- **자르지 않는다.** 지금 BE는 128자에서 `…`로 자른다. 그러면 고객센터 번호가 중간에 끊겨
  틀린 번호(`로젠택배 1588-99…`)가 보인다. 번호는 한 자리라도 틀리면 안 된다.
- 2026-10-14 기준 넘는 자료는 `verification` 2개다. 택배 고객센터 NR-0015 148자, 카드사 고객센터 NR-0019 205자.
- 제안: 128자를 넘으면 쉼표나 문장 끝에서 나눠 C4를 여러 장으로 만든다. 번호 하나(`우체국 1588-1300`)는
  나누지 않는다. 제목은 `📋 공식 확인 방법 (1/2)`처럼 장 번호를 붙인다. 캐러셀 10장 상한은 지금 BE 규칙대로
  신호 카드와 나눠 쓴다.
- BE와 합의 전이다. 합의되면 이 절을 확정한다.

**카드 모양 확인 필요** (`feature/edit-card-final` 기준)

`c4-guidance.json`은 `textCard` 항목인데, BE는 이것을 C1~C3 캐러셀 뒤에 붙인다. 그런데 C1~C3는
이미지가 들어간 `basicCard` 캐러셀로 바뀌었다. 카카오 스킬 응답 형식 문서에 따르면 `basicCard`는
`thumbnail`이 필수이고, 캐러셀 안의 `description`은 최대 2줄이다. 같은 캐러셀에 넣으면 응답이 거절되거나
글이 잘릴 수 있다. C4에 이미지를 넣어 `basicCard`로 맞출지, 별도 `textCard` 캐러셀로 따로 보낼지
BE·팀장과 정한다.

## 5. 이미지 현황과 후속 검토

| R4 | 현재 관리자센터 카드에 이미지 없음 | 확인을 마치지 못함 |
| R6 | 현재 관리자센터 카드에 이미지 없음 | 확인할 주소 없음 |
| R7 | 저장소 자산 없음. 관리자센터 이미지 여부 확인 필요 (BE 전달 범위 밖) | 주소가 여러 개 |
| R5 | 이미지 불가 — 콜백 대기 응답은 글자만 보낸다 | 분석 중 — 결과가 아님이 드러나야 함 |
| W2a | 개정본에 이미지 자리만 있음 | 미정 |

- 규격: 800×400 (2:1), 500KB 이하. 기존 프로토타입과 동일.
- 원본 위치: `frontend/kakao-templates/assets/prototype/`
- 브랜드·URL·동적 문구는 이미지에 넣지 않는다. 상태만 나타낸다.
- 캐러셀 이미지는 **전부 1:1 또는 전부 2:1로 통일**해야 한다(build-guide 7절).
- **이미지 주소가 없으면 썸네일을 넣지 않고 텍스트 카드로 보낸다**(`chatbot-flow.md` 9절 (3)).
  빈 썸네일은 카드 상단에 큰 흰 공백을 만든다. BE 템플릿(`r1`~`r3`)의
  `{{ image_url }}`는 지금 렌더러가 채우지 않는다. BE에 전달할 사항이다.

### 실기기 확인 항목

카드 길이와 핵심 버튼 위치는 FE가 조정할 수 있다. 카카오의 하단 메뉴와 입력창 위치는
바꿀 수 없다. 아래는 안드로이드 카카오톡에서 화면마다 확인한다. 기기·OS·카카오톡 버전과
캡처를 함께 기록한다.

| 확인할 것 | 통과 기준 |
| --- | --- |
| 첫 화면에서 핵심 버튼이 보이는가 | 카드가 도착한 직후 스크롤 없이 제목과 첫 버튼이 보인다 |
| 카드 상단 공백 | 썸네일이 없거나, 있으면 이미지가 실제로 표시된다 |
| 회색 본문 가독성 | 핵심 행동이 본문이 아니라 **제목**이나 버튼에 있다. 본문 색은 관리자센터에서 바꿀 설정을 찾지 못했다 (확인 필요) |
| 큰 글씨 설정 | 기기 글꼴과 카카오톡 글자 크기를 가장 크게 했을 때 제목·버튼 글자가 잘리지 않는다 |
| 가로 버튼 2개 | 8자 버튼이 한 줄에 들어가고 잘리지 않는다 |
| 긴 본문 (B2b·R1a) | 200자 안팎 본문에서 버튼이 화면 밖으로 밀려나지 않는다 |
| 다크 모드 | 이미지 배경이 어두운 화면에서 튀지 않는다 |

**결과 조회 세 상황** (멘토 리뷰 PR #39, 10/3: "실제 카카오에서 분석 중, 콜백 전달 실패,
서버 재시작 후 결과 없음이 각각 어떻게 표시되는지 확인하면 좋겠습니다")

링크가 든 문자로 시작한다. 공식 주소여도 R5 대기를 거친다(D2 미구현, 2026-10-13 기준).
하단 메뉴의 `결과 확인`도 같이 확인한다.

| 상황 | 재현 방법 | 기대 화면 | 필요한 도움 |
| --- | --- | --- | --- |
| 분석 중 | 문자를 보내고 결과가 오기 전에 `결과 확인` 입력 | R5 대기 문구(표시되는지 기록) → K1 `아직 확인하고 있어요` | 없음 |
| 콜백 전달 실패 | BE가 결과 전송을 막거나 콜백 유효 시간보다 늦춘 상태에서 문자 전송 → `결과 확인` 입력 | 결과 카드가 오지 않음 → K2 확인 시각 + 저장된 결과 카드 | BE |
| 서버 재시작 후 결과 없음 | 결과를 받은 뒤 서버 재시작 → `결과 확인` 입력 | K4 `확인 결과를 찾지 못했어요` | BE (재시작) |

## 6. 이모지 정책

| 규칙 | 이유 |
| --- | --- |
| 카드 제목에 최대 1개, 본문에 최대 1개 | 더 넣으면 안내문이 장식으로 읽힌다 |
| **버튼에는 쓰지 않는다** | 버튼 8자(가로 2개) 한도를 이모지가 잡아먹어 가로 배치가 깨진다 |
| **R1은 `⚠️` 하나만** | 위험 결과에 다른 이모지가 붙으면 심각도가 희석된다 |
| 실패·거절 화면(R3·R4·R6·R7·E1)은 사용자를 탓하지 않는 이모지 | `❌` `🚫`는 사용자 잘못으로 읽힌다 |

개정본의 W1·R1a·R2·C1~C3 제목에는 이모지가 없다. 넣지 않아도 규칙에 어긋나지 않는다.
글자수는 파이썬 `len()` 기준으로 셌다. 카카오가 이모지를 2자로 세는지는 확인하지 못했다.
