## 1. 원본 초안

팀원과 잡은 구조다. 아래 2절 이후의 변경은 모두 이 초안을 기준으로 한다.

```
[웰컴 블록]
  - 서비스 설명
  - [동의하고 시작 하기]
  - [약관 전체 보기] → 약관 내용
      - [동의하고 시작]
      - [동의 안 함] → [웰컴 블록]

[상시노출 메뉴] - 1단. 3개 메뉴
  - [스미싱 의심 문자 보내기]
  - [ ]  ← 미정
  - [약관 다시보기]

[스미싱 의심 문자 보내기]
  - 간단 설명
  - [복사 붙여넣기 방법 보기] → 방법 내용

[약관 다시보기]
  - 약관 내용

결과
  - 간단 설명 + 확인된 범위
  결과1 - 위험 징후            : [신고하기] [자세히 보기]
  결과2 - 이상 징후 미발견/판단 보류 : [공식 웹 바로가기] [자세히 보기]
  결과3 - 처리 실패            : [다시 시도] → [스미싱 의심 문자 보내기], [자세히 보기]
  결과4 - 관련 없는 발화        : 재요청 → [스미싱 의심 문자 보내기]
  결과5 - 링크만 전달          : [문자 본문도 보내기] → [스미싱 의심 문자 보내기], [자세히 보기]

[자세히 보기] - 근거
  - 케러셀 형식
  - 다음 행동 지시 → 관측 결과 → 공식 주소 대조 → 확인 못한 것
```

## 2. 용어를 바꾼 이유

초안에는 세 종류의 말이 섞여 있었다.

| 종류 | 예 | 문제 |
| --- | --- | --- |
| 오픈빌더 내부 용어 | 웰컴 블록, 발화, 상시노출 메뉴 | 팀 문서에는 필요하다. 사용자 화면에 나가면 안 된다 |
| 보안 보고서 말투 | 위험 징후, 이상 징후 미발견, 판단 보류, 관측 결과 | 뜻은 정확하지만 읽는 사람이 멈춘다 |
| 법무 말투 | 약관 전체 보기, 동의 안 함 | 딱딱해서 그냥 닫는다 |

버튼 이름은 "무엇"이 아니라 **"내가 뭘 하게 되는지"**로 쓴다.

주 타겟은 20~40대이고 개발자가 아니다.

### 바꾼 문구

| 초안 | 확정 | 이유 |
| --- | --- | --- |
| 스미싱 의심 문자 보내기 | **문자 확인하기** | `스미싱`은 아는 단어지만 자기 상황에 붙이기 어렵다. "이게 스미싱인가?"를 이미 판단해야 누를 수 있는 버튼이다 |
| 동의하고 시작 하기 | **동의하고 시작** | 띄어쓰기 오류. `하기`는 군더더기 |
| 약관 전체 보기 / 약관 다시보기 | **내 문자는 어떻게 쓰이나요** | 실제 내용은 개인정보 안내다. `약관`은 안 읽고 넘기는 단어 |
| 동의 안 함 | **다음에 할게요** | 거부도 정상 선택으로 보이게 |
| 복사 붙여넣기 방법 보기 | **문자 복사하는 법** | |
| 신고하기 | **신고·상담 받기** | `신고`만 있으면 절차가 복잡할 것 같아 안 누른다. 상담도 된다는 걸 알린다 |
| 공식 웹 바로가기 | **공식 앱 열기** | 검증된 공식 경로만 열고 문자에서 받은 URL은 재사용하지 않는다 |
| 다시 시도 | **다시 해보기** | |
| 자세히 보기 | **자세히 보기** (유지) | 이미 흔한 말 |
| 케러셀 | **캐러셀** | 오타. 카카오 공식 표기 |

**내부 라벨로만** 쓴다. 말풍선에는
`kakao-result-card-prototype.md`의 검증 문구를 기준으로 쓴다.

## 3. 확정한 흐름

> 2026-09-26: 웰컴·개인정보 안내·신고·상담 블록과 R5 `[결과 확인]`은 9절의 결정으로 바뀌었다.

```
[웰컴 블록]
  서비스 설명 + 확인 범위와 한계
  [동의하고 시작]              → 문자 확인하기
  [내 문자는 어떻게 쓰이나요]     → 개인정보 안내

[개인정보 안내]
  약관·개인정보 처리 내용
  [동의하고 시작]              → 문자 확인하기
  [다음에 할게요]              → 웰컴 블록

[봇 리스트 메뉴] 3개
  [문자 확인하기]
  [신고·상담 받기]
  [내 문자는 어떻게 쓰이나요]

[문자 확인하기]
  붙여넣기 안내
  [문자 복사하는 법]           → 복사 안내

[복사 안내]
  복사 방법
  [돌아가기]                  → 문자 확인하기

[신고·상담 받기]
  KISA 안내 + 연결
  [전화 상담]
  [챗봇 상담]
  [채팅 상담]

── 결과 (상태별) ──────────────────
R1 공식 주소와 다름   [신고·상담 받기] [자세히 보기]
R2 다른 점 못 찾음    [공식 앱 열기] [자세히 보기]
R3 판단 보류         [다시 보내기] [자세히 보기]
R4 확인 못 마침       [다시 해보기] [처음으로]
R5 확인 중           [결과 확인]
R6 확인할 주소 없음    [공식 앱 열기] [주소 추가로 보내기]
그 외 관련 없는 대화   재요청 안내 → [문자 확인하기]

[자세히 보기] — 캐러셀 3장
  1장  확인한 것 — 공식 주소와 비교한 결과
  2장  확인 못 한 것 — 안전하다는 뜻은 아님
  3장  지금 할 일
  → 3장 모두에 같은 행동 버튼을 단다
```

## 4. 바꾼 결정 3가지

### (1) 빈 메뉴 자리 → `신고·상담 받기`

상시 메뉴는 "언제든 필요한 것"이 들어가는 자리다.
이미 링크를 눌러버린 사람은 문자 확인이 필요 없고 곧바로 상담이 필요하다.
지금 구조에서는 문자를 보내고 위험 결과가 나와야만 KISA로 갈 수 있는데,
그 사람은 그 경로를 지날 이유가 없다.

차선책은 `뭘 확인해 주나요`(서비스 범위와 한계)였다.
"안전하다고 말해주는 서비스"라는 오해를 막는 것이 `docs/PRD.md`의 핵심 위험이라 근거는 충분하지만,
대부분 궁금할 때만 열어보므로 3자리 중 하나를 쓰기엔 아깝다고 판단했다.

### (2) 자세히 보기 = 캐러셀. 상세 웹은 보류

초안대로 캐러셀로 간다. 상세 웹은 만들지 않는다.
`ux-options-3.md`의 웹 필요성 판정 기준에 해당하는 정보가 쌓이면 그때 다시 본다.

따라오는 변경: `smishing-message-intake-ux.md`의 **상세 진입 토큰**, **상세 링크 무효** 상태,
**FE 상세 웹** 역할이 필요 없어진다. 해당 문서는 아직 웹 전제로 적혀 있어 정리가 필요하다.

### (3) 캐러셀 순서는 아직 정하지 않았다

두 주장이 부딪힌다.

| 주장 | 근거 |
| --- | --- |
| `할 일`을 1장에 | 사람들은 옆으로 잘 안 넘긴다. 제일 중요한 것을 첫 장에 |
| `확인한 것`을 1장에 | `자세히 보기`를 누른 사람은 "왜?"가 궁금한 것이다. `할 일`은 직전 결과 카드에서 이미 봤다 |

`확인 못 한 것`이 맨 뒤로 가는 것이 더 큰 위험이다.
오해를 막는 문장("안전하다는 뜻은 아니에요")이 거기 들어 있고,
사용자 테스트의 탈락 기준이 "안전하다고 오해한 횟수 0"이기 때문이다.

**행동 버튼을 3장 모두에 달면** 어디서 멈추든 다음 행동은 항상 보인다.
그래서 순서는 사용자 테스트로 가른다. 볼 지표 두 개:

- 기대 행동 일치 수 (할 일이 앞이면 올라갈 것)
- 안전하다고 오해한 횟수 (확인 못 한 것이 뒤로 가면 올라갈 것)

둘이 반대로 움직이면 그때 정한다.

## 5. 자세히 보기 칸 이름

| 초안 | 확정 |
| --- | --- |
| 다음 행동 지시 | 지금 할 일 |
| 관측 결과 | 확인한 것 |
| 공식 주소 대조 | 공식 주소와 비교 |
| 확인 못한 것 | 확인 못 한 것 |

`공식 주소와 비교`는 `확인한 것`에 합쳐 한 장에 담는다. 그래서 4칸이 아니라 3장이다.

## 6. 개발 채널 프로토타입 확인 결과

카카오 개발 채널 `클릭 전 확인`의 `시나리오 02`에 R1~R3 결과 카드와 공통
`자세히 보기` 캐러셀을 만들었다. 스마트폰 카카오톡에서 2:1 이미지, 제목·본문,
가로 버튼 2개, 캐러셀 3장 연결을 확인했다.

- R1: `공식 주소와 달라요` / `신고·상담 받기` / `자세히 보기`
- R2: `다른 점을 못 찾았어요` / `공식 앱 열기` / `자세히 보기`
- R3: `확인할 정보가 부족해요` / `다시 보내기` / `자세히 보기`
- 캐러셀: `확인한 것` → `확인 못 한 것` → `지금 할 일`

확인한 것은 카카오 렌더링과 연결 동작뿐이다. 사용자 이해도와 안전 오해 여부는 아직
검증하지 않았으므로 최종 UX 선택은 보류한다.

## 7. 아직 정하지 않은 것

| 항목 | 상태 |
| --- | --- |
| 캐러셀 3장의 순서 | 사용자 테스트로 결정 (4절 (3)) |
| 봇 리스트 메뉴 1단/2단 계층 | 카카오 공식 문서에 없음. 직접 켜서 확인 |
| 봇 리스트 메뉴 최대 개수 | 카카오 공식 문서에 없음 |
| R5 `결과 확인` 동작 | 9절 (4)에서 정함 (2026-09-26). 구현은 BE |
| 관련 없는 대화를 어디서 가릴지 | 카카오 블록 / 백엔드 / AI 중 미정 |
| `신고·상담 받기` 블록의 실제 연결 방식 | KISA 챗봇 인계 방법 미확인 |

## 8. 검토받고 싶은 것

1. 버튼 이름이 20~40대 비개발자에게 실제로 자연스러운가. 더 흔한 말이 있는가
2. `내 문자는 어떻게 쓰이나요`가 약관·개인정보 안내라는 것이 전달되는가.
   법적으로 `약관`이라는 말을 빼도 되는가
3. 캐러셀 3장 순서에 대한 4절 (3)의 판단이 타당한가
4. `신고·상담 받기`를 상시 메뉴에 넣은 선택이 맞는가. 차선책이 더 나은가
5. R3(판단 보류)와 R4(처리 실패)를 사용자에게 굳이 나눠 보여줄 필요가 있는가
6. 흐름에서 빠진 화면이 있는가

## 9. PR #24 리뷰 반영 (2026-09-26)

멘토 리뷰의 직관성 코멘트와 `main.py:92` 인라인 코멘트를 반영한 결정이다.
문구는 [`chatbot-copy.md`](./chatbot-copy.md)에 적는다.

### (1) 동의는 문자를 외부로 보내기 직전, 한 곳에서만 받는다

지금은 웰컴·개인정보 안내 화면마다 `동의하고 시작`이 있다. 그런데 이 버튼은 화면만
넘긴다. 서버의 전송 조건과 연결돼 있지 않다. 사용자는 이미 시작했는지, 다시 동의해야
하는지 헷갈린다. 게다가 버튼을 거치지 않고 문자를 바로 붙여넣으면 동의 없이 분석이 시작된다.

| 바꾼 것 | 이유 |
| --- | --- |
| 웰컴·개인정보 안내에서 `동의하고 시작`을 뺀다 | 동의를 받지 않는 버튼에 `동의`라는 이름을 붙이지 않는다 |
| 동의 기록이 없는 사용자가 문자를 보내면 **그때** 전송 동의 카드(W3)를 보낸다 | 바로 붙여넣는 사용자도 반드시 이 자리를 지난다. 그러니 동의를 받을 곳은 여기 한 곳이면 충분하다 |
| 동의한 사용자는 다시 묻지 않는다 | 재방문 때 반복을 없앤다. 문자를 바로 붙여넣는 편한 흐름은 그대로 둔다 |
| 외부로 보내지 않는 응답(R6·R7·E1)은 동의 없이 답한다 | 동의가 필요한 것은 외부 전송이지 대화 자체가 아니다 |

멘토가 예시로 든 순서는 "첫 이용 안내 → 전송 동의 → 문자 입력"이다.
이 결정은 동의를 입력 **뒤**, 전송 **앞**에 둔다. 버튼을 거치지 않는 사용자도 막으려면
전송 직전 확인은 어차피 필요하다. 그래서 앞 단계에 동의를 한 번 더 두지 않는다.

**BE가 필요한 것:** 사용자별 동의 기록, 동의 전에 받은 문자를 동의할 때까지 잠시
들고 있기. 들고 있을 수 없으면 동의 후 "문자를 한 번 더 보내주세요"로 대신한다.
BE 구현 전에는 W3를 배포하지 않는다. 화면 어디에도 `동의`라는 버튼을 두지 않는다.

### (2) 신고·상담은 상황부터 고르게 한다

지금 B3는 긴 설명 뒤에 상담 버튼 3개가 나온다. 급한 사용자가 운영 시간을 읽고
상담 채널까지 직접 골라야 한다.

- 첫 화면에서는 "문자만 받았어요 / 링크를 눌렀어요" 둘 중 하나만 고른다.
- 문자만 받은 사람에게는 할 일(누르지 말고 지우기, 신고)만 보여준다.
- 링크를 누른 사람에게만 상담 채널 3개를 보여준다. 시간 정보는 버튼 바로 위에 한 줄로 둔다.

### (3) 이미지가 준비되지 않은 카드는 텍스트 카드로 보낸다

카드 상단의 큰 흰 공백은 사용자가 "덜 로딩됐다"고 느끼게 하고, 핵심 문구와 버튼을
아래로 밀어낸다. 원인 후보는 두 가지다.

- BE 템플릿 렌더러(`backend/src/server/templates/renderer.py`)가 `thumbnail.imageUrl`의
  `{{ image_url }}`를 채우지 않고 그대로 보낸다.
- 웰컴 이미지 원본 자산을 아직 전달받지 못했다.

스크린샷만으로 원인을 단정할 수는 없다. 그래서 규칙을 정한다. **이미지 주소가 없으면
썸네일을 넣지 않고 텍스트 카드로 보낸다.** 안내 화면(W·B)은 이미지 없이 간다.
결과 카드(R1~R3)는 상태를 알리는 이미지가 준비된 경우에만 쓴다.

### (4) 결과 확인은 대기 메시지가 아니라 별도 블록에서 한다

`[결과 확인]`이 필요한 순간은 콜백이 실패했을 때다. 그래서 콜백으로 오는 카드에
버튼을 달면 소용이 없다. 콜백 대기 메시지(R5)에는 `template`을 넣을 수 없어 버튼과
바로연결도 달 수 없다([카카오 AI 챗봇 콜백 개발 가이드](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/ai_chatbot_callback_guide)).

| 결정 | 이유 |
| --- | --- |
| R5 대기 글자에 "`결과 확인`이라고 보내주세요"를 쓴다 | 콜백 없이도 닿는 유일한 경로가 사용자의 입력이다 |
| 관리자센터에 `결과 확인` 블록을 만들고 스킬로 사용자의 가장 최근 작업을 조회한다 | 작업 번호를 사용자에게 보이거나 입력받지 않는다 |
| 보통 스킬 응답(K1·K5)에는 바로연결 `결과 확인`을 단다 | 두 번째부터는 입력 없이 누를 수 있다 |
| 봇 리스트 메뉴에는 넣지 않는다 | 3자리가 찼다. 결과 확인은 문자를 보낸 직후에만 필요하다 |

화면 문구는 `chatbot-copy.md` 3절 R5와 K1~K5다.
