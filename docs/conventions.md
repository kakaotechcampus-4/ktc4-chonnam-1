# 컨벤션

[코드리뷰 가이드](https://www.notion.so/3dcfc7a167ea80d6b828c4600c4f5f25)에 따른 브랜치 운영, PR 작성, 코드 리뷰 규칙을 정리한다.

## 브랜치 전략

| 브랜치 | 용도와 규칙 |
|---|---|
| `main` | Rulesets로 보호. 직접 push 금지, PR merge만 허용. 멘토 승인 후 팀장이 merge |
| `develop` | 기본 개발·통합 브랜치. 보호하지 않으며 팀에서 관리. 핫픽스·간단한 리팩토링은 직접 push 허용 |
| `feature/<이슈명>` | 기능 단위 작업 브랜치. `develop`을 기준으로 작업하고 팀 내 리뷰 후 `develop`으로 merge |
| `refactor/<내용>` | 멘토 피드백 반영 브랜치. `develop`에서 생성하고 팀 내 리뷰 후 `develop`으로 merge |

## PR과 리뷰 흐름

### 팀원 간 리뷰

- 기능·버그 수정·리팩토링 변경사항은 PR로 공유하고 팀원 리뷰를 받는다. 핫픽스·간단한 리팩토링은 위의 직접 push 예외를 따른다.
- PR은 기능 단위로 작게 나누어 자주 올리고, 대상(base) 브랜치는 `develop`으로 지정한다.
- 같은 도메인을 담당하는 팀원 최소 1명 이상의 리뷰를 받는다.
- 리뷰어는 구체적인 리뷰 댓글과 승인·반려 의견을 남기고, 필요한 경우 함께 코드를 검토한다.
- 리뷰 기한 등 세부 운영 규칙은 팀에서 합의한다. 원문의 '24시간 이내 리뷰', '구체적 코멘트 1개 이상'은 팀별로 조정할 수 있는 예시다.

### 멘토 리뷰

- 팀장(PM)이 `develop` → `main` PR을 작성하고 리뷰를 요청한다.
- 통합된 작업의 진척과 변경 맥락을 설명하고, 검토받고 싶은 코드·설계 포인트를 강조한다.
- 멘토 승인 후 팀장이 merge한다. 미반영 피드백은 수용 가능 여부를 멘토와 조율하고, 승인을 막는 항목은 우선 처리한다.

### 피드백 반영과 재리뷰

1. 피드백을 팀 내에서 논의하고 반영 방향을 정한다. 모든 의견을 무조건 수용하기보다 선택의 근거를 조율한다.
2. `develop`에서 `refactor/<내용>` 브랜치를 만들어 개선사항을 반영한다.
3. `refactor/*` → `develop` PR을 팀 내 리뷰 후 merge한다.
4. 멘토의 해당 리뷰 댓글에 반영 PR 링크를 답글로 남긴다.
5. 기존 멘토 리뷰 PR에 재리뷰를 요청하며, `develop`에 merge된 수정 내용과 PR 링크를 명시한다. 신규 기능 작업과 피드백 반영 내역을 구분한다.

피드백 반영과 `feature/*`의 신규 기능 개발을 병행할 때는 `develop`에 merge하면서 발생할 수 있는 충돌에 유의한다.

## PR 작성 기준

정해진 템플릿은 없지만, 리뷰어가 무엇을 검토해야 하는지 알 수 있도록 다음 세 가지를 포함한다.

1. **변경 요약** — 무엇을 왜 바꿨는지 2~3문장으로 설명한다. 커밋 목록만 나열하지 않는다.
2. **리뷰 포인트** — 검토받고 싶은 파일·함수·설계 결정을 구체적으로 지정한다. '전체 검토 부탁드립니다'처럼 범위가 불분명한 요청은 피한다.
3. **설계·예외** — 검토한 대안과 현재 방식을 선택한 이유, 처리하지 않은 예외나 알려진 한계를 적는다.

| 구분 | 팀 내 리뷰 (`feature/*`·`refactor/*` → `develop`) | 멘토 리뷰 (`develop` → `main`) |
|---|---|---|
| 범위 | 기능 하나 | 통합된 작업 전체 |
| 요약 | 기능이 하는 일 | 전체 작업의 진척과 변경 맥락 |
| 리뷰 초점 | 네이밍, 예외 처리, 테스트 등 구현 세부사항 | 레이어 분리, 확장성, 기술 선택 등 설계·구조 |
| 설명 분량 | 핵심을 짧게 설명 | 판단에 필요한 맥락을 충분히 설명 |

- 제목만으로 작업 내용을 알 수 있게 작성한다.
- 본문이 비어 있거나 '리뷰 부탁드립니다' 한 줄뿐인 PR은 피한다.
- 많은 커밋을 한꺼번에 올리기보다 기능 단위로 나눈다.
- 완료한 부분과 작업 중인 부분을 명확히 구분한다.

## 리뷰 커뮤니케이션

- 코드 리뷰는 상호 피드백으로 코드 품질을 높이고 기술적 통찰을 얻는 협업 활동이다.
- 피드백의 이유를 묻고 기술적 근거를 토론한다.
- 의견이 다르더라도 감정을 배제하고 기술적으로 응답한다.
- 정답을 가리는 것보다 더 나은 방향을 함께 찾는 데 집중한다.

## PR 제출 전 확인

- [ ] base 브랜치가 맞는가? (팀원 리뷰: `develop`, 멘토 리뷰: `main`)
- [ ] 제목만 보고 작업 내용을 알 수 있는가?
- [ ] 구체적인 리뷰 포인트를 최소 1개 적었는가?
- [ ] 빌드·실행이 되는 상태인가?
