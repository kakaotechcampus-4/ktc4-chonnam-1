# ADR 0006 — 상세 결과는 1회용 웹페이지로 보여 주고, 카드는 결론과 행동을 지킨다

상태: 제안 (2026-10-16). 채택하면 [ADR 0005](0005-no-detail-web.md)를 대체한다.

## 맥락

ADR 0005(2026-09-21)는 상세 웹을 만들지 않고 카드와 `자세히 보기` 캐러셀로 결과를 보여 주기로 했다.
이유는 두 가지였다. 프로토타입에서 카드와 캐러셀로 현재 범위를 표현할 수 있었고, 웹을 붙이면
토큰 발급·조회 API·배포 대상이 늘어난다는 것이다. 다시 여는 조건은 "사용자 테스트에서 근거를
이해하지 못한 원인이 카드 분량 부족으로 나오면"이었다.

그 뒤로 사정이 바뀌었다.

- **카드 글자 수 제한에 계속 걸린다.** 사용자 테스트 전이지만 문구를 쓰는 단계에서 이미 아래 문제가 쌓였다.
  - 캐러셀을 이미지 카드(`basicCard`)로 바꾸자 본문이 2줄까지만 보인다(카카오 스킬 응답 형식 문서, `3d8673f`).
  - 공식 확인 방법 카드(C4)는 128자에서 잘려 고객센터 번호가 끊긴다(#77, NR-0015 148자·NR-0019 205자).
  - 판단 보류 카드(R9)의 인용도 30자로 줄여야 400자 안에 든다(#89).
- **#74에서 웹의 기반이 어차피 생긴다.** 보이스피싱 녹음은 카카오 챗봇으로 받을 수 없어서 업로드 웹페이지를 만든다.
  사용자별 1회용 입장권(토큰)과 BE가 페이지를 내보내는 방식이 그때 생긴다. ADR 0005가 걱정한 비용 중
  토큰과 배포 대상은 이미 치르는 셈이고, 결과 페이지에 더 드는 것은 입장권으로 결과를 읽는 조회 API 정도다.
- **원문과 근거를 나란히 보여 줄 수 있다.** 카드는 근거를 요약 문장으로만 전한다. 웹에서는 문자 원문에서
  근거가 된 문구를 강조하고 설명을 붙일 수 있다. 녹음은 글로 바꾼 내용을 원문처럼 보여 줄 수 있다(#74 팀장 제안, 2026-10-15).
- **멘토 리뷰(PR #86, 2026-10-15)는 두 방향을 함께 말했다.**
  > 상태를 하나 더 만드는 것보다, 첫 안내를 읽고 어떻게 대응해야 할지 알 수 있는지가 더 중요하다고 생각합니다.

  > 자료나 화면 구조를 크게 늘리지 않고도 줄일 수 있는 문제들입니다.

  첫 안내만으로 대응할 수 있어야 한다는 점은 카드가 지켜야 한다. 화면을 늘리는 이유는 분명히 남겨야 한다.

## 결정

상세 결과는 **1회용 결과 웹페이지**로 보여 준다. 카드의 역할은 줄이지 않는다.

| | 카드 (챗봇 안) | 결과 웹 (1회용) |
| --- | --- | --- |
| 원칙 | **카드만 읽어도 대응할 수 있게** | 더 알고 싶은 사람을 위한 상세 |
| 담는 것 | 결론(`주의가 필요한 문자예요` 등), 멈출 행동, 확인할 곳, 신고·KISA 버튼 | 원문과 근거 강조, 확인한 것·확인하지 못한 것과 이유, 공식 확인 방법 전문 |
| 바뀌는 것 | `자세히 보기` 버튼이 블록 버튼에서 웹 링크 버튼으로 바뀐다 | `자세히 보기` 캐러셀(C1~C4)을 대신한다 |

- 결과 웹은 #74 업로드 페이지와 같은 구조를 쓴다. 서버가 카드 버튼 주소에 사용자별 입장권을 붙이고,
  BE 서버(메인 서버)가 페이지를 내보낸다. 페이지는 Vite + React + TypeScript로 만들고(`frontend/chatbot-web/`),
  빌드 결과 `dist/`를 함께 커밋한다. 처음에는 화면이 한 장이라 React 없이 TypeScript만 쓰기로 했으나,
  결과 웹이 더해져 화면이 두 장이 되고 공통 부품이 생겨 2026-10-16에 React로 바꿨다.
  도구별 비교와 고른 이유는 `frontend/chatbot-web/README.md` "기술 스택과 고른 이유"에 둔다.
  격리 서버에는 두지 않는다. 사용자 브라우저가 격리 서버에 닿으면 격리한 의미가 없어진다.
- **결과는 빈 페이지가 따로 받아 온다.** 입장권은 주소의 `#` 뒤에 둔다(`…/result#t=…`).
  `#` 뒤는 브라우저가 서버로 보내지 않아 서버 기록과 다른 사이트로 넘어가는 주소(Referer)에 남지 않는다.
  서버는 결과가 없는 빈 페이지만 내보내고, 페이지의 스크립트가 입장권을 읽어 조회 API로 결과를 받아 그린다.
  - 링크가 카톡방에 전달되면 카카오톡 미리보기 봇이 먼저 주소를 연다. 봇은 스크립트를 실행하지 않으므로
    빈 페이지만 보고, 문자 원문이 새거나 입장권이 소모되지 않는다. 서버가 결과를 채운 페이지를 바로 내보내는 방식과
    입장권을 쿠키로 바꾸는 방식은 이 경우에 원문이 봇에게 넘어가거나 입장권이 먼저 소모돼서 고르지 않았다.
  - 조회 API는 입장권을 주소가 아니라 요청 헤더로 받는다(예: `GET /api/result` + `Authorization: Bearer <입장권>`).
  - 응답에는 `Cache-Control: no-store`를 붙여 브라우저와 중간 서버가 결과를 저장하지 않게 한다.
  - 입장권은 "한 번만 열기"가 아니라 **짧은 유효 시간**으로 막는다. 새로고침이나 뒤로 가기에 결과가 사라지지 않게 하기 위해서다.
    시간은 BE·팀이 정한다.
- **원문은 무해화해서 보여 준다.** 휴대폰 브라우저는 글 속 URL과 전화번호를 눌리는 링크로 바꿀 수 있다.
  이것은 격리 환경과 같은 원칙(사용자 브라우저가 의심 페이지에 닿지 않는다, `docs/isolation-security.md`)을
  결과 웹까지 잇는 장치다.
  - URL은 `hxxps://example[.]com`처럼 바꿔 표시한다. `<a>`로 만들지 않는다.
  - 전화번호 자동 링크를 끈다(`<meta name="format-detection" content="telephone=no">`).
  - 미리보기·썸네일·og:image를 불러오지 않는다. 대상 페이지에 사용자 브라우저가 닿지 않게 한다(`frontend/README.md`).
- 근거 강조는 결과에 실제로 있는 인용만 쓴다. `signals`·`doubts`의 `evidence`를 원문에서 찾아 칠하고,
  원문에 없는 문구는 강조하지 않는다. 판정은 하지 않는다(CLAUDE.md 원칙 1·2).
- 결과 웹이 동작하기 전까지는 지금 캐러셀을 그대로 둔다. 버튼을 바꾸는 시점은 결과 웹 배포와 같이한다.

## 이유

- 글자 수 제한을 문구로 버티는 대신 구조로 없앤다. 캐러셀 장 수를 늘리는 방법(ADR 0005 결과 절)은 2줄 제한을 풀지 못한다.
- 원문과 근거를 맞대는 화면은 "왜 이렇게 판단했는지"를 가장 직접 보여 준다. 근거와 함께 알려 준다는 제품 목표와 맞는다.
- #74가 만드는 입장권·페이지 구조를 그대로 쓰므로 추가 비용이 작다.
- 카드에 결론과 행동을 남기므로, 사용자가 웹을 열지 않아도 대응할 수 있다. 멘토 리뷰 5번을 지킨다.

## 결과

- `자세히 보기` 블록에 스킬을 연결하는 일(#77), 캐러셀 2줄 문제, C4를 카드용으로 줄이는 일은 결과 웹이
  생기면 필요 없어진다. 결과 웹이 늦어지면 다시 살핀다.
- BE에 입장권으로 결과를 조회하는 API가 필요하다. 지금의 `/api/analyses/{job_id}`는 분석 번호로 조회하고
  스킬 인증(`X-Skill-Secret`)이 걸려 있어 사용자 브라우저에서 부를 수 없다. 새 API는 분석 번호를 드러내지 않고
  짧은 입장권으로만 조회한다.
- FE 결과 웹은 결과를 받아 오는 동안의 화면과 입장권 없음·만료·실패 화면을 갖는다. 업로드 페이지와 같은 입장권 읽기를 쓴다.
- **알려진 한계**: 지금 분석 결과는 서버 메모리(`ANALYSIS_JOBS`)에만 있어서 서버가 재시작하면 사라진다.
  조회 방식과 상관없이 그때는 결과 웹 링크가 깨지므로 "결과를 찾을 수 없어요" 화면으로 안내한다.
  보관 방식(파일·DB 등)은 BE와 따로 정한다.
- 나중에 격리 서버가 모은 자료(페이지 화면 캡처 등)를 결과 웹에 보여 준다면, 우리 서버를 거쳐서만 보여 준다.
  원래 페이지에서 바로 불러오지 않는다. 수집 결과를 분석에 연결하는 일(#73)은 지금 보류 중이다.
- 입장권 유효 시간, 다시 볼 수 있는 횟수, 원문을 지우는 시점은 업로드 페이지와 같은 기준으로 BE·팀이 정한다.
  정해지면 W2a 개인정보 안내에 반영한다.
- 사용자가 챗봇 밖으로 한 단계 나간다. 그래서 바로 할 행동(신고·KISA 인계)은 카드에 남긴다.
- `frontend/README.md`의 Next.js 상세 웹 설명은 이 결정에 맞게 고친다. 라우트·폴링 설계는 쓰지 않는다.
- 업로드 페이지와 결과 페이지 중 무엇을 먼저 만들지는 팀이 정한다(#74).
