# 실험: 문자 AI 분석 · urlscan 병렬화 전후 소요 시간 비교

- 날짜 / 담당: 2026-09-25 / BE (봄)
- 배경: 멘토 리뷰(PR #24, MJbae)에서 "통합 코드는 문자 분석 뒤에 URL 검사를 시작하므로, 단계별 제한을 늘리는 것만으로 전체 성공률이 좋아지지는 않는다"는 지적을 받았다. `run_analysis()`가 `analyze_message_part()`를 완전히 기다린 뒤에야 urlscan 루프를 시작하는 순차 구조였다.

## 질문

문자 AI 분석과 urlscan은 서로의 결과를 입력으로 쓰지 않는 독립적인 작업이다. 이 둘을 `asyncio.create_task`로 동시에 시작하면 `run_analysis()`의 전체 소요 시간이 얼마나 줄어드는가?

## 방법

- `main.py`의 `run_analysis()`를 수정: `analyze_message_part()`를 즉시 `await`하는 대신 `asyncio.create_task()`로 시작만 해두고, urlscan 루프를 바로 진행한다. 문자 분석 결과가 실제로 필요한 시점(각 링크의 urlscan 완료 직후, `finalize_analysis()` 호출 직전)에서만 그 task를 `await`한다.
- `run_analysis()`의 반환 형식(`kakao_response`가 만드는 `version`/`template` 구조)은 변경하지 않았다 — `run_analysis_and_callback()`과 Job 저장소 작업(BE 다른 담당자)과의 충돌을 피하기 위해서다.
- 실제 urlscan·LLM 호출은 외부 의존이라 값을 통제할 수 없으므로, 문서 근거 지연시간으로 대체(mock)해서 "병렬화 자체의 순수 효과"만 측정했다.
  - 문자 분석 지연: 2.0초 (`docs/ai-be-python-integration.md`가 언급하는 추출·검색·신호 제안 예산 기준)
  - urlscan 지연: 30.0초 (멘토 피드백이 인용한 urlscan 공식 가이드: "첫 결과 조회까지 최소 30초 대기")
- 병렬화 이전(before) 로직과 이후(after) 로직을 각각 재현해 같은 mock으로 총 소요 시간을 쟀다. 이후 실제로 수정한 `main.py`의 `run_analysis()`를 직접 호출해(짧은 mock 지연으로) 반환 형식과 여러 시나리오(링크 1개/2개/0개)에서 오류 없이 동작하는지도 별도로 검증했다.

## 결과 (숫자)

| 구분 | 총 소요 시간 |
| --- | --- |
| BEFORE (순차: 문자 분석 → urlscan) | 32.09s |
| AFTER (병렬: 문자 분석 ∥ urlscan) | 30.06s |
| 절감 | 2.03s (6.3%) |

이론값과 일치했다: BEFORE ≈ 문자분석 + urlscan(32.0s), AFTER ≈ max(문자분석, urlscan)(30.0s).

`run_analysis()`를 실제 mock으로 직접 호출한 검증에서는:
- 링크 1개: 문자 분석(1.08s)이 urlscan(1.08s)과 겹쳐 진행되고, urlscan 완료 시점에 문자 분석 결과가 이미 준비돼 있어 대기 시간 0.00s로 즉시 사용됨.
- 링크 2개: 문자 분석 task를 한 번만 생성하고 두 번째 링크에서는 이미 끝난 task를 재사용(캐시된 결과 즉시 반환), 로그도 중복 출력되지 않음.
- 링크 0개: for 루프를 전혀 안 돌아도 함수 끝에서 문자 분석 task를 정리(취소)해 백그라운드에 방치되지 않음.
- 세 시나리오 모두 반환값이 기존과 동일한 `{"version": "2.0", "template": {...}}` 형식을 유지함.

## 결론

- 병렬화로 얻는 절감은 **문자 분석 소요 시간만큼(수 초)**이다. urlscan이 전체 소요 시간을 압도적으로 지배하므로(30초 vs 2초), 이번 변경만으로 "전체 성공률"이 크게 좋아지지는 않는다 — 멘토 피드백이 지적한 것과 같은 결론이다.
- 그래도 공짜로 얻을 수 있는 개선이라(같은 정확도, 코드 몇 줄로 구현) 적용할 가치는 있다. 다만 이것이 5초/45초 타임아웃 문제의 근본 해결책은 아니다.
- **진짜 병목은 urlscan의 30초 자체다.** 이건 asyncio 병렬화로 줄일 수 있는 종류의 문제가 아니라, urlscan을 자체 시스템으로 교체하거나(팀이 이미 계획 중), 전체 타임아웃·콜백 설계를 이 30초 기준으로 재조정하는 방향의 문제다.

## 한계

- 문자 분석 2.0초, urlscan 30.0초는 문서에 근거한 추정치이지 실측값이 아니다. 실제 LLM 응답 속도나 urlscan 실제 완료 시간은 요청마다 달라질 수 있다.
- 링크가 여러 개일 때 urlscan 자체는 여전히 링크마다 순차 처리된다(이번 변경 범위 밖). 이 부분의 병렬화는 별도 검토가 필요하다.
