# 실험: 동시 요청 시 첫 응답 시간·메모리 변화

- 날짜 / 담당: 2026-09-17 / BE
- 배경: 멘토 피드백 3번 — "요청이 겹쳤을 때 첫 응답 시간과 메모리 사용이 어떻게 달라지는지 가볍게 확인해보라"는 요청에 대한 실험. 관련 계획: [backend/be_pr.md](../../backend/be_pr.md)

## 질문

`feature/smishing-message-intake-be`의 프로토타입(`main.py`)에 동시 요청이 몰리면 첫 응답 시간과 서버 메모리가 얼마나 나빠지는가? 이 결과로 콜백 방식 전환(`useCallback: true` + 큐 워커)을 이번 주에 착수할지, 우선 동시 처리량 제한만 걸지 판단한다.

## 방법

- `urlscan_service.submit_url_scan`/`wait_for_url_scan_result`를 실제 urlscan.io 대신, 지정한 시간만큼 `asyncio.sleep`하는 가짜 함수로 치환해 별도 프로세스로 서버를 띄웠다.
  - 이유: 실제 API를 쓰면 API 키·쿼터가 필요하고 외부 응답 속도 편차가 섞여서, "우리 서버 자체의 동시 처리 능력"만 순수하게 재기 어렵다.
- 카카오 웹훅과 동일한 형식의 요청(링크 1개 포함)을 `httpx.AsyncClient`로 N개 동시에 보내고, `psutil`로 서버 프로세스의 RSS 메모리를 요청 전/도중/후로 측정했다.
- urlscan 대기 시간은 두 가지로 시험: 평시로 가정한 5초, 코드상 최악치인 약 50초(`wait_for_url_scan_result`의 기본 재시도 10회 × 5초).
- 동시 요청 수는 멘토가 요청한 5/10/20건에 더해, 한계점을 보려고 50/100/200건도 추가로 시험했다.

## 결론

- **동시성 자체는 지금 병목이 아니다.** `main.py`가 urlscan 호출을 `await`로 비동기 처리하고 있어서, 5~100건이 동시에 들어와도 서로 대기시키거나 메모리를 눈에 띄게 늘리지 않는다. 배치 전체 소요 시간이 거의 개별 요청 하나의 소요 시간과 같다는 것은 요청들이 직렬로 밀리지 않고 잘 겹쳐서 처리된다는 뜻이다.
- 200건에서 연결 오류가 발생했지만, 이는 개발용 uvicorn(워커 1개, 기본 설정)의 한계로 보인다. 지금 예상 트래픽 규모에서 당장 문제될 수치는 아니며, 실제 배포 시 워커 수·백로그 설정 점검 항목으로 남긴다.
- **그럼에도 콜백 전환은 예정대로 진행한다.** 콜백이 필요한 이유는 동시 요청 부하가 아니라, 요청이 단 1건이어도 urlscan 대기가 최대 ~50초까지 걸려 카카오 5초(우리 예산 4초) 응답 시한을 넘기기 때문이다. 이번 실험은 "그 전환의 기반이 될 비동기 구조 자체는 이미 건전하다"는 것을 확인해준 것이지, 전환의 필요성을 낮추는 근거는 아니다.

## 한계

- 로컬 단일 머신, urlscan 호출을 가짜로 대체한 값이라 실제 외부 API의 네트워크 편차·연결 재사용 비용은 반영되지 않았다.
- 200건 실패는 원인을 깊게 파지 않았다(테스트 클라이언트 연결 풀 한도 확장 후에도 재현됨 — 서버 쪽 uvicorn 기본 설정 가능성이 높지만 확정하지 않음).
