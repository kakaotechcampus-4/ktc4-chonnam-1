# EC2 실제 브라우저·방화벽 검증

검증일: 2026-10-17 KST. PR #100의 `ae641b4` 제품 코드와 별도 런타임 검사 스크립트를 사용했다.
대상: 기존 격리 EC2 `i-0ddf82de2ba56da70`.
Render·카카오 설정, 운영 수집기 버전, 호스트 방화벽 및 AWS 보안 그룹을 변경하지 않았다.

## 브라우저 검사 방법

[`browser_runtime.py`](../../infra/isolation/checks/browser_runtime.py)는 수집 이미지 안에서 실행한다.
운영 이미지 ID `sha256:850a1712d1e569bc84b0e40c01e5d0cd32fe27ad7fb67cf93548a8968c071e03`를
런타임 기반으로 재사용하고, 현재 `collector/`, `scanner/`와 검사 코드를 읽기 전용으로 마운트했다.
새 출시 이미지를 빌드·교체한 검사는 아니다.

별도 `ktc-runtime-check-ae641b4` 컨테이너는 기존 수집 브리지에 연결하되 포트를 게시하지 않았다.
UID/GID 10001, 권한 전체 제거, no-new-privileges, 기존과 동일한 seccomp,
읽기 전용 루트, 임시 `/tmp`, 1536MiB·1.5CPU·256PID 제한과 IPv6 비활성화를 적용했다.
실제 비밀값을 복사하지 않고 합성 토큰만 넣었다. 기존 컨테이너를 재시작하지 않았다.

자체 서명 인증서는 **루프백 가짜 페이지 시험에만** 사용하고 그 렌더러에서만 인증서 예외를 뒀다.
공개 HTTPS 시험은 운영 팩토리의 기본 인증서 검증과 샌드박스를 그대로 사용했다.
팀 페이지의 실제 수집은 HTTPX와 브라우저 합계 약 689ms였으며, 앞선 같은 검사에서는 1218ms였다.
이는 LLM·카카오 전체 응답 지연 측정이 아니다.

공개 접속은 기존 허용 IP `185.199.108.153`으로 고정한 팀 GitHub Pages만 사용했다.
운영 SG와 방화벽이 그 밖의 주소 및 DNS를 차단하므로, 임의 인터넷 사이트를 EC2에서
동적으로 DNS 조회·수집한 검사는 아니다.

## 숨겨진 리다이렉트 재현

외부 인터넷의 해당 기관이나 단축 서비스로 요청을 보내지 않고, 세 호스트 이름을
검사 컨테이너 안의 같은 TLS 가짜 서버로만 연결했다.

```text
bit.ly → JS → attacker.example.test → HTTP 302 → www.cjlogistics.com
```

실제 Chromium의 `navigation_chain`에는 `bit.ly`와 `www.cjlogistics.com`만 남았고
중간 공격자 호스트가 빠지는 것을 확인했다. 실제 브라우저 결과를 수집 응답 형태로
구성해 현재 `parse_collect_response` → `build_ai_url_analysis` → `to_isolated_page`에 전달했다.
`official=unresolved`, 표시 도메인 `bit.ly`, 실제 최종 URL 및 브라우저 HTML 유지가 통과했다.
따라서 브라우저가 실행되면 공식 확정을 보류하는 현재 제한은 그대로 필요하다.

## 방화벽 검사 방법

[`firewall_runtime.py`](../../infra/isolation/checks/firewall_runtime.py)는
`sudo python3 <검사 디렉터리>/checks/firewall_runtime.py`로 EC2에서 실행했다.
현재 `network_config.firewall_rules()`가 생성한 명령을 새 라우터 네임스페이스에만 적용한다.
운영 `KTC-*` 체인에 규칙을 추가하거나 초기화하지 않는다.

수집기·라우터·응답 서버를 각각 독립 네임스페이스에 만들고, 외부 연결 없는 veth 두 쌍으로만 연결했다.
코드에 사용한 공인·사설 IP는 그 내부의 합성 주소다. 먼저 방화벽 없이 모든 목적지가
도달 가능함을 확인한 뒤 새 규칙을 적용했다. 단순히 경로가 없어서 실패한 것을 차단 성공으로 세지 않았다.

| 실제 커널 패킷 검사 | 기대 결과 |
| --- | --- |
| 공개 TCP/443 | 허용 |
| 사설 `10.0.1.1`, 메타데이터 `169.254.169.254`의 443 | 차단 |
| 보호 `3.39.166.84`, `8.8.8.8`의 443 | 차단 |
| 지정 DNS `1.1.1.1`의 TCP·UDP 53 | 허용 |
| 다른 DNS `8.8.4.4`의 TCP·UDP 53 | 차단 |
| 공개 TCP/80 | 차단 |
| 보호 IP와 겹치는 허용 Render 원본의 API/8443 및 응답 | 허용 |
| 허용 CIDR 밖 원본의 API/8443 | 차단 |

이 12개 검사에서 모두 기대한 결과가 나왔고, 각 DROP 및 conntrack REPLY 예외의
커널 패킷 카운터도 확인했다. DNS 검사는 실제 UDP·TCP 전달 정책 검사이며,
DNS 응답 데이터 자체는 합성 echo여서 인터넷 재귀 DNS 서비스 검증으로 해석하지 않는다.
초기 검사 서버의 UDP 응답 원본 주소가 별칭과 달랐던 가짜 서버 문제를 수정한 뒤 재실행했다.
제품 방화벽 코드 변경은 필요하지 않았다.

운영 중인 기존 규칙에서는 메타데이터·사설 IP·자체 공인 IP·호스트 게이트웨이·
미허용 공개 443·외부 DNS 53의 여섯 요청이 차단됐다. 타임아웃뿐 아니라
`KTC-FORWARD` DROP 5회, `KTC-INPUT` DROP 1회 증가를 확인했다.

## 검증 후 상태와 남은 범위

임시 컨테이너와 3개 네임스페이스는 종료·제거됐다. 운영 컨테이너의 ID·이미지·시작 시각과
실행 상태가 유지됐다. 카운터·핸들을 제외한 호스트 nft 규칙의 전후 SHA-256은 모두
`c71856b28881097998cc41015076d15e502a20bc9bfcb610acbd90887b6ba023`이었다.

서버의 검사 소스와 로그는 `/home/isolation-admin/ktc-runtime-ae641b4-20261017`에 보관했다.
합성 토큰 외 실제 인증값은 검사 디렉터리에 복사하지 않았다.

새 공개 정책의 **실제 EC2 커널 검사**와 새 브라우저의 **실제 EC2 실행**은 완료했다.
운영 공개 모드의 최종 검증에는 새 이미지·호스트 설정 적용, SG의 공개 443 및 지정 DNS 허용,
실제 DNS 조회·일반 사이트 수집·Render에서 들어오는 요청 확인이 남아 있다.
이번에는 SG·운영 정책을 유지했으므로 그 결합 경로가 완료됐다고 주장하지 않는다.
