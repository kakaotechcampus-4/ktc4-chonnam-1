# 지식베이스 관리

프로토타입은 case_examples의 검토된 피해 사례를 메시지 본문으로 검색하고 유사도를 참고 정보로 제공한다. 유사도는 악성 확률이 아니며 최종 판정이나 추가 검사 여부를 결정하지 않는다. 사례의 행동을 이번 링크의 관측 사실로 사용하지 않는다.

출처·게시일·검토자·검토일을 기록하고 승인된 레코드만 인덱싱한다. 사용자 입력은 자동 편입하지 않는다. README·template·미검토 자료는 검색에서 제외한다. 원문 변경 시 적용 범위를 재검토하고 평가셋 중복을 점검한다.

norm_rules의 검토 규범은 사례와 구별한다. 검색된 규범이나 사례만으로 실행 판정 규칙을 생성·변경하지 않는다. 구체적인 규범 활용 범위는 판정 규칙 확정에 맞춰 정한다.

메시지 검색에는 URL을 제외하고 개인정보를 마스킹한 본문을 사용한다. 사례의 분류용 키워드가 본문을 키워드로 압축한다는 뜻은 아니다. 검색 실패·자료 부족·텍스트 없음은 구분하며 유사도 0으로 대체하지 않는다.

AI는 원본·검토 이력과 KB 버전을 관리한다. 저장·인덱스 운영은 백엔드와 기존 역할 경계를 유지한다. 모델·척도·검색 개수·표시 방식·데이터셋은 후속 확정 사항이다.

`team_collected` 296건은 건별로 어느 쪽인지 구분할 수 없고 크롤링 출처 링크도 남아 있지 않다.
레코드마다 적힌 `팀 수집 실물 문자.` 는 일괄 등재 스크립트가 모든 레코드에 같은 값으로 넣은 문구라
구분 근거가 아니다. 평가용 `ai/eval/datasets/smishing.jsonl` 127건도 같은 원본에서 나눈 것이다.

이 때문에 생기는 한계:

- **평가셋과의 출처 겹침을 링크로 검사할 수 없다.** `test_kb_sources_do_not_overlap_rag_testset` 은
  `source` 가 있는 147건만 본다. 평가 스미싱 중 KB 에 거의 같은 문구가 있는 행은 사람이 판정해
  `near_dup_of` 로 표시하고 점수를 따로 낸다(`ai/eval/datasets/README.md`).
- **스미싱 라벨의 근거를 건별로 확인할 수 없다.** 크롤링분은 게시한 곳이, 팀원 수신분은 받은
  사람의 판단이 근거였지만 어느 레코드가 어느 쪽인지 남아 있지 않다.
- **개인정보.** 2026-10-07 에 이름+님·전화·이메일·주소·계좌 모양·7자리 이상 숫자·생년월일을 찾는
  자동 검사로 296건과 `smishing.jsonl` 을 훑었고 해당 항목은 없었다. 모양으로 찾는 검사라
  `님` 이 붙지 않은 이름 같은 것은 놓칠 수 있다. 데이터 테스트의 개인정보 검사도 같은 한계가 있다.

앞으로 추가하는 레코드는 `case_examples/template.md` 의 출처 규칙을 따른다.
